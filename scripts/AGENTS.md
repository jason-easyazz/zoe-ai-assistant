## Purpose

Operational scripting for Zoe hosts: setup, maintenance, deployment, migrations, testing helpers, and systemd unit templates.

- `maintenance/curate_voice_corpus.py` — the replay corpus's hygiene tool. `~/.zoe-voice-samples` is auto-captured (`ZOE_VOICE_SAVE_AUDIO=1`), so it is **untrusted input that grows by itself**, and the probe replays a *slice* of it (`--last N`) — an off-format or non-speech member inside that slice moves the gate's numbers with no code change. Measured 2026-08-04: 5 of the newest 20 were unusable. It audits every TOP-LEVEL WAV with a stdlib format probe plus a speech score from the **real** `voice_vad` Silero path — never a re-implementation, or it could evict audio the live VAD hears fine — and **moves** failures into `quarantine-format-YYYYMMDD/` + `quarantine-nonspeech-YYYYMMDD/` with a `manifest.json` (file, reason, scores, mtime, VAD model sha). Four contracts: **off-contract is NOT unusable** — the format quarantine covers ONLY audio the STT path itself refuses (unparseable RIFF, zero frames, `rate <= 0`), because `_prepare_audio_for_moonshine` (`voice_tts.py:2071`) resamples off-rate captures to 16 kHz and downmixes multi-channel before transcription, so a 24 kHz mono s16 file is a usable regression sample; missing the 16 kHz/mono/s16 capture contract is surfaced as **DRIFT and kept** (and scored through the same normalisation the replay path applies, so the VAD hears what STT hears). Quarantining the 95 drifted files cost the gate 95 real samples on the first executed run — fix capture drift at the SAVE path, not by evicting evidence. Then: **it never deletes** (AST-pinned — quarantine is a move, so every call is reversible with `mv`, and it refuses to overwrite an existing destination because an overwrite is a delete in disguise); the quarantine line is **0.20 peak, not the runtime 0.50** (the ~11% between them is quiet/clipped REAL speech — the hardest gate samples — so it is reported BORDERLINE and kept); and **quarantine subdirs must stay invisible to the replay set**, which holds only because every consumer globs `<corpus>/*.wav` non-recursively — proved executably in `tests/unit/test_curate_voice_corpus.py` against `replay_samples.py::_select`'s real source, so making it recursive reddens instead of silently re-admitting quarantined audio. Dry-run by default; run `--execute` under `flock /tmp/zoe-voice-harness.lock` so no probe enumerates the corpus mid-move — but note the lock does **not** serialise CAPTURE writes (`_maybe_capture_stt` copies straight to the final corpus filename without taking it), so `apply_moves` re-stats each source and refuses to move any file whose size/mtime changed since classification, **plus** any file modified within `MIN_QUIESCENT_S` (60 s) — two snapshots cannot see a writer that made no progress between them, so the quiescence window is what covers a paused `copyfile`. Both are NARROWINGS, not proofs; the proof is temp-file + atomic rename in `_maybe_capture_stt` (voice-path, replay-gated, deliberately not in this tool). A **VAD run whose hop count is SHORT of what the audio owes (`len(samples)//512`) is UNSCORED, never silence** — including a PARTIAL run, which is the dangerous shape because nothing about it looks wrong — `process_hops` never raises and `break`s on inference failure, returning what it already had: a model that loads but cannot infer scores every WAV at peak 0.0 (one `--execute` quarantines the whole corpus), and a mid-file failure yields a peak drawn only from the recording's opening. Manifest **entries carry their own `speech_threshold`/`vad_model_sha256`/`quarantined_at`** — the top-level copies describe the latest run only, and `entries` merges across runs. Provenance is written **before** each file is orphaned: a fsync'd `manifest.jsonl` line per move, so an interrupted run leaves at most ONE file without a record instead of the whole batch (`manifest.json` is still the readable artifact, written at the end; both rows come from one builder so they cannot disagree). And a **speech audit that scored ZERO files exits 2**, refusing to pass a broken VAD off as a clean corpus — `--skip-vad` remains the explicit format-only mode. `--speech-threshold` is validated as a probability in [0, 1] before anything is scanned or moved (a mistyped `20` would otherwise quarantine the entire corpus in one `--execute`; `nan` would quarantine nothing and report clean). **A curation pass changes the gate's INPUT** — re-run `voice_regression_probe.py` afterwards and decide explicitly about `--update-baseline`. Contract + census: `docs/knowledge/voice-pipeline.md`.

## Local Contracts

- Scripts belong in a category subfolder, never in the repository root.
- **One service-dir ladder, in `lib/service_dir.py`.** Every voice-harness entrypoint (`maintenance/voice_regression_probe.py`, `perf/measure_voice.py`, `perf/measure_tts.py`) resolves the live `services/zoe-data/.env` through `resolve_service_dir()`: explicit `--service-dir` always wins → this repo's `services/zoe-data` if it has a `.env` → the MAIN worktree's (via git's `--git-common-dir`, never a hardcoded `/home/zoe/assistant`). So a run from a git worktree — direct or via the probe — needs no flag. Do not re-implement or fork the ladder per script; that drift is exactly what it exists to prevent (the probe invokes measure_voice as a SUBPROCESS, so the shared module also keeps the import graph acyclic). When no `.env` resolves anywhere it returns the in-tree default so the EXISTING loud skip/error still fires (`status=error`, exit 2): the ladder fixes the DEFAULT, never the failure mode — **a skip is not a pass**. Pinned by `tests/unit/test_probe_dsn_resolution.py`.
- **The voice gate runs on the zoe-data SERVICE interpreter, and recall-off is never a pass.** `lib/service_python.py` resolves it: `--python` → `ZOE_PROBE_PYTHON` → the zoe-data unit's ExecStart (`deploy/zoe_data_python.sh` — systemd is the authority, not venv presence) → the B0.7 venv when systemd can't answer → the current interpreter. `voice_regression_probe.py` re-execs itself on it (same PID, so a parent `flock` still holds the harness lock) and passes it to `perf/measure_voice.py --python`, which hands it to the replay. The replay emits `memory_recall: ok|mismatch|load-failure|error|disabled` (the service's own palace-format guard + a log watch); the probe makes any state but `ok` `status=error` and never writes it as a baseline. Why: B0.8 → 2026-10-03 every probe ran on 3.10/chromadb 0.6.3 against the 1.x palace and scored brain turns without recall. To measure a candidate interpreter pass `--python` explicitly. Pinned by `tests/unit/test_voice_probe_interpreter.py` + `services/zoe-data/tests/test_replay_memory_recall.py`. `load-failure` = the palace opened in preflight but a recall read later failed and was swallowed (`load_for_prompt failed` / `packet fetch failed`) — brain turns ran without recall, so it is a verdict, not a diagnostic. `lib/service_python.py` and `setup/systemd/zoe-voice-regression.service` are voice-path files in `maintenance/voice_gate_check.py` (they choose which stack produces the evidence). The nightly unit LAUNCHES on `/usr/bin/python3` (stable) and the probe re-execs onto the ladder's answer — never hard-code the venv in `ExecStart` (a B0.7 rollback would then measure the wrong stack, or fail to launch). Every ladder candidate must actually run Python 3 (`runs_python`: it has to PRINT a token — `/bin/true -c …` exits 0, so exit status alone proves nothing); a non-Python `--python`/`ZOE_PROBE_PYTHON` is a hard error, a non-Python unit/venv answer falls through like a missing one.

- **Latency-critical user units must carry their cgroup memory guards IN THE TEMPLATE** (`MemorySwapMax=0` + `MemoryLow`, plus `MemoryMax` unless the unit is a large unified-memory process like llama-server where a ceiling turns a spike into an OOM kill). The mechanism, measured 2026-08-03: a leaf's *effective* `memory.low` is capped by its ancestors' and every ancestor **on this host** (`user.slice` → `user-1000.slice` → `user@1000.service` → `app.slice`) is `0`, so a leaf floor computes to 0 whatever it says — a slice-configuration property that is fixable by protecting the ancestors, not a kernel law, so re-measure on a rebuilt box rather than assuming, while `memory.swap.max` is enforced per-cgroup with no such propagation. Across six live units the split was total — every unit denying swap held **0** swap, every unit not denying it was **96-98%** out, at floors of 6G/3G/2G/512M/0 alike. ### cross_review.sh (maintenance)

`scripts/maintenance/cross_review.sh <PR#> "<contract>"` kicks an Omnigent polly
cross-review of a PR and prints the structured report. Constraints: the flock
(`/tmp/zoe-cross-review.lock`) serializes THIS wrapper only — other polly
launch paths (omnigent_issue_executor, the Flue heavy lane) do not take it,
so operators must still avoid overlapping those manually; advisory
only (never wired into greptile-gate); exit 2 = alarm (silent kick death,
error-status session, or unreachable server) and must never be read as a clean
review. Protocol + validation record: `docs/knowledge/omnigent-cross-review.md`.

**Never parse an HTTP body in the shell, and never fetch one ONE-SHOT.** Every
response — session create, poll, report — goes through
`scripts/maintenance/cross_review_poll.py`, which
checks HTTP status, emptiness and content-type BEFORE parsing, retries
transient faults (empty body / non-JSON / 5xx / connection refused / a truncated
read — `http.client.HTTPException` derives from `Exception`, so it escapes a
`URLError`/`OSError` handler and tracebacks) with bounded backoff, and treats a
404 `not_found` as a vanished session rather than a blip. **Type-guard every
container before iterating it, not merely its truthiness**: `d.get("items") or
[]` still lets a schema-drifted scalar (`{"items": 1}`) raise `TypeError`, which
reaches the operator as a traceback instead of the module's one alarm line.

**Detection speed and restart tolerance trade directly against each other — do
not retune one without the other.** The poller sleeps EXACTLY ONCE per
iteration (the interval on the healthy path, the backoff on a retry); sleeping
both is a silent 211s-instead-of-121s regression that a loosely-bounded timing
test will not catch. At the wrapper's defaults a mid-poll dead endpoint is
declared poll-lost after **121s of SLEEPS** (`30 + 1+2+4+8+16+30+30`) and a
vanished session after ~33s, while a **~60s server restart is still ridden
out** — `--max-transient` is 8 rather than 6 solely to keep that tolerance once
the padding interval is gone. **121s is the sleep schedule, not the wall**: it
is the whole wall only for faults that answer immediately, whereas a STALLING
endpoint burns up to `--http-timeout-s` per attempt on top (`121 + 8*60 = 601s`
at the defaults). That is documented rather than capped on purpose — shrinking
each request's timeout to the residual detection budget would hand a
slow-but-healthy Omnigent a sub-second timeout and manufacture a false
poll-lost. `poll()` always returns within `--timeout-s + --http-timeout-s`. All
of these numbers are pinned by `tests/unit/test_cross_review_poll.py`.

**The report fetch is bounded-retried too — it is the one that costs a whole
review.** `report` takes either `--server/--session-id` (FETCH: the same
`fetch_session` classification plus exponential backoff, default budget **90s**,
`--http-timeout-s` 60s, returns within `--budget-s + --http-timeout-s`) or
`--payload <file>` (read a payload the caller already holds; keep it — it is the
only way to drive an unusable payload shape offline). The wrapper uses the fetch
mode: the transcript GET used to be a one-shot `curl -sf … -o "$TMPJ"`, so a
502, a truncated body or an Omnigent restart in the second between "poll saw
idle" and "read the transcript" discarded a COMPLETED review — ~20 minutes of
worker — and forced a full re-dispatch. Fetches land at t = 0, 1, 3, 7, 15, 31,
61, 90, so a ~60s restart is ridden out here exactly as it is in `poll()`. A
200 that parses is a VERDICT, not a transport fault: an unusable payload shape
(non-list `items`, zero assistant messages) alarms on the FIRST response rather
than burning the budget re-reading it.

**A non-positive duration is a USAGE error, refused before the first request.**
`--budget-s`/`--interval-s`/`--timeout-s`/`--running-grace-s`/`--http-timeout-s`
are argparse floats, so `-30` parses happily — and a negative wait then reaches
`time.sleep`, which raises `ValueError`: a traceback and a raw exit 1, colliding
with the wrapper's public `exit 2` and breaking the one-terminal-line contract
(Greptile P2, #1625). Zero is the same class of bug wearing a different face —
every backoff becomes 0 and a bounded retry loop turns into a busy spin. Both
now exit `EXIT_USAGE` with one alarm line naming the flag. The arithmetic behind
that guard is TOTAL as defence in depth (`_nap` clamps the wait, `_backoff`
clamps its cap and bounds its exponent), and **every retry loop sleeps through
`_nap`** — a structural test fails on a raw `sleep(` anywhere below it, so a new
loop cannot reintroduce the hole.

**The wrapper's worst-case wall must stay BELOW its caller's timeout.**
`services/zoe-data/pipeline_cross_review.py` runs the script under
`subprocess.run(timeout=2500)`, which kills only the shell — the EXIT trap never
fires, so the detached polly worker outlives the released flock and the next
invocation runs a second polly beside the orphan. Every phase is therefore
explicitly bounded (the `flock -w` wait, create curl, registration budget + its
HTTP timeout, a `timeout(1)`-wrapped docker-exec kick, the poll budget + its
HTTP timeout, the report fetch budget + its HTTP timeout, a `timeout(1)`-wrapped
cleanup — **every `timeout` carries `-k`**, since without it TERM is sent and
then waited on forever, which is not a bound at all), and the wrapper
CHECKS the sum at startup and exits 1 on inversion — so raising
`CROSS_REVIEW_TIMEOUT_S` fails loudly rather than silently re-inverting. Default
poll budget is 1800s (not 2400) to leave real margin; the shipped worst case is
**2370s against the caller's 2500s**, i.e. 130s of margin (30s of which the
runner teardown below now spends). **A retried phase
costs its budget AND one request** — the report fetch adds `90 + 60`, not 90, so
count both terms or the startup check under-counts the wall. **The lock wait is IN the
sum**: the caller's timer starts at `subprocess.run`, BEFORE the lock is
acquired, so an unbounded wait leaves less than the post-lock worst case and the
run is then killed *after* it has created a session and kicked a worker.
Refusing at the lock (`exit 2`) is strictly better — a queued invocation would
have waited most of a full review anyway.

Its exit codes are diagnostic — 3 never-registered, 4 poll-lost,
5 timeout, 6 never-running, 7 dispatch-failed — and the wrapper collapses all of
them to its public `exit 2`. Every failure prints exactly one terminal line
carrying the session id and `re-dispatch required`; grep for that string.

The wrapper also confirms the session is READABLE before spending a worker on
it (`await-registration`, budget via `CROSS_REVIEW_REGISTER_TIMEOUT_S`, default
60s): a POST that returned an id is not proof a GET resolves it.

**Every dispatch MUST tear its session down, and a cmdline scan cannot do it.**
`stop_worker` signals container processes whose `/proc/<pid>/cmdline` CONTAINS
the session id. That reaches the `omnigent run` kick and the harness subprocess
(`omnigent.runtime.harnesses._runner --conversation-id <sid>`) and nothing else.
The process that holds the memory is the one `omnigent host` spawns per session
as literally `python -m omnigent.runner._entry`: **the session id travels in its
ENVIRONMENT (`OMNIGENT_PROCESS_LOG_FILE=…/runner-<sid>-<ts>.log`), never in its
argv**, and its parent is the live host daemon, so it is neither cmdline-matchable
nor an orphan. It leaked one per dispatch — worst on the SUCCESS path, where
`REVIEW_DONE=1` correctly suppresses `stop_worker` and nothing else ran.
MEASURED 2026-08-04: 19 resident, box at 0–245 MB available, and Omnigent's host
daemon then refused to come online under load (~20:08–21:00) and killed two
dispatches mid-flight. `cleanup` therefore runs `cross_review_poll.py stop`
(`POST /v1/sessions/<id>/events {"type":"stop_session"}`) **unconditionally and
BEFORE `stop_worker`** — Omnigent's own lifecycle verb, which resolves the runner
from the owner-gated session row and has the host stop it, so attribution is by
construction and no /proc heuristic is involved. Order is load-bearing: the route
forwards the stop to the runner and RAISES on a non-2xx, so killing the harness
first makes it abort before the host-runner teardown. A failed stop is a WARNING
(exit 8 from the poller, collapsed to a stderr line) — never a lost review; the
review is already paid for, and the reaper below is the safety net.

**Operator escape hatch: `docker restart zoe-omnigent`** clears every leaked

- `reap_stale_omnigent_runners.py` — dry-run-first sweeper for leaked

  answer is never permission, and neither is an answer we do not understand.

  of the server's vocabulary growing.
  **The classify verdict is a SNAPSHOT and is re-proved before any mutation.**

  session may have come back to life. `same_runner()` binds the pid to the

  `starttime` — because every runner's argv is byte-identical, so a marker-only
  recheck cannot tell this runner from ANOTHER SESSION'S and would signal a live
  one; `starttime` additionally catches a pid recycled by a relaunch of the
  *same* session (stops are non-sticky, so relaunch is the normal case). The
  harness set and the session status are then re-read — through the UNCACHED
  lookup, since the per-run cache would replay the very answer being
  re-checked — and a session that has since gained a harness or gone
  non-terminal is skipped, not stopped. Reaping prefers the same `stop_session`
  verb over a signal so the host records an intentional exit rather than a
  crash; SIGTERM→SIGKILL is the fallback, and identity is re-proved again
  between the graceful attempt and the first signal so a slow stop cannot defeat
  the check by simply taking long enough.
  Paired hourly user timer `zoe-omnigent-runner-reaper.timer` in
  `setup/systemd/`. Pinned by `tests/unit/test_reap_stale_omnigent_runners.py`,
  where every refusal has its own negative control and
  `test_negative_control_a_matching_identity_is_still_reaped` holds all of them
  true and requires the reap to PROCEED — so a guard cannot pass by the reaper
  simply refusing everything.

- `ma_idle_reap.py` — the STOP half of the Music Assistant idle reap (flag-dark
  `ZOE_MA_IDLE_REAP=1`; the START half is `services/zoe-data/ma_ondemand.py`).
  Dry-run by default, `--execute` stops; paired 10-min user timer
  `zoe-ma-idle-reap.{service,timer}` in `setup/systemd/` (operator opt-in; reads
  `services/zoe-data/.env` via `EnvironmentFile` so the flag + MA token have ONE
  home — a missing token makes MA unreadable and the reaper KEEPS, visibly, in
  `~/.zoe-logs/ma-idle-reap.log`). `decide()` is pure and keeps the container
  unless EVERY guard passes: flag on, container running, MA API readable (unknown
  is never idle), no `inflight` stamp younger than `ZOE_MA_INFLIGHT_GRACE_S` (120),
