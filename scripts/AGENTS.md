# scripts/ — operational scripts

## Purpose

Operational scripting for Zoe hosts: setup, maintenance, deployment, migrations, testing helpers, and systemd unit templates.

## Ownership

- `setup/` — host/platform provisioning, including `setup/jetson/` systemd unit templates.
- `maintenance/` — recurring operational jobs: `deploy_zoe_data_when_ready.sh` (readiness/watch gate with no working-tree/live mutation, but it fetches remote-tracking refs; deploy mode pre-flights target `origin/main` content, builds a temporary pinned remote whose `main` is exactly that SHA, and invokes blessed `deploy_live.sh` with `origin` pointed at the pinned remote; after `deploy_live.sh` returns, the wrapper aborts if live `HEAD` differs from the pre-flighted SHA; post-deploy liveness checks remain informational because `deploy_live.sh` owns restart/rollback), `prune_worktrees.sh` (stale worktree cleanup), `greploop_guard.py` (Greptile fix-packet loop), `serena_mcp_capped.sh` (Serena MCP launcher — resolves the serena binary and self-provisions `jedi-language-server`, then wraps the server in a systemd user scope with `MemoryHigh`/`MemoryMax` caps, default 1G/2G via `SERENA_MEM_HIGH`/`SERENA_MEM_MAX`, so a runaway language server gets OOM-killed instead of exhausting the host; falls back to an uncapped launch if the user manager is unreachable. **`SERENA_NO_SCOPE=1` skips the scope** — required when launching under `serena-mcp.service`, whose unit carries the caps natively: nesting a scope inside a service reparents Serena to PID 1 and moves it into `app.slice`, escaping the service cgroup, which breaks `Restart=` tracking and makes the process look like an orphan to the reaper), `serena_mcp_health.sh` (read-only health check for the shared server — drives a real MCP `initialize` round-trip rather than just checking the socket, and FAILS if the port is bound beyond loopback; `[port]` arg defaults to 9121. Pinned by `tests/unit/test_voice_probe_streak.py`.
- `perf/` — speed-regression harness: `measure_speed.py` (brain TTFT + gen tok/s probe vs the live llama-server), `measure_voice.py` (voice e2e latency + said-vs-did correctness, wrapping `services/zoe-data/tests/replay_samples.py`), and `measure_tts.py` (Kokoro TTS time-to-first-audio — times the live sidecar synth of the first speakable clause, reporting cache hit/miss; sources reply text from the replay corpus or a plain `--replies-file`). All are read-only and gated behind `ZOE_PERF=1`; see `perf/README.md` for the before/after workflow and the captured baseline. Plus `measure_endpointing.py` — the ONE probe that is not `ZOE_PERF`-gated and does not replay saved WAVs, because it covers what the replay gate structurally cannot see: the replay harness starts from a saved recording, so endpointing/VAD/barge-in are outside its boundary and an endpointer change leaves it green regardless. It loads the REAL daemon source (`setup/zoe_voice_daemon.py`, pyaudio stubbed) and feeds synthetic continuous streams built from corpus utterances plus known silence, reporting tail-after-speech, mid-utterance false-cut rate, and `natural_cuts` (closures inside a real utterance's own pauses — the realistic risk figure; the synthetic zero-gaps are a worst case for the deep-quiet tail because digital silence always scores "deep"). Runs on the Jetson too: when torchaudio is absent the probe stubs it (Silero only uses it for file I/O the probe never calls), so the real VAD path is measured off-Pi; if Silero itself is unavailable `_Endpointer` falls back to amplitude mode silently — the probe prints a loud WARNING and sets `mode_as_requested=false` rather than let a fallback pass as a measurement. **Baseline (live VAD path, 2026-07-26, n=12; reconfirmed 2026-07-27 n=150 on the Jetson): tail 800ms; mid-utterance false cuts small below the tail (5-18%), deterministic at gap>=tail.** `--tail-flag-ms` exercises the daemon's `ZOE_VAD_TAIL_MS` deep-quiet fast tail (`--tail-flag-ms 0` must reproduce the flagless baseline exactly). Prerequisite instrument for any endpointing change (e.g. porting Smart Turn v3 into the daemon).
- `lib/` — shared Python helpers imported by scripts across categories. `scripts/` is NOT a package: import a helper via the sibling-import convention (`sys.path.insert(0, str(Path(__file__).resolve().parents[1] / "lib"))`, then a plain module import), never a relative/package import. Currently `service_dir.py` — the ONE `--service-dir` resolution ladder shared by every voice-harness entrypoint (see Local Contracts).
- `deploy/`, `migrations/`, `testing/`, `train/`, `utilities/`, `preview/` — task-specific script groups.

## Local Contracts

- Scripts belong in a category subfolder, never in the repository root.
- **One service-dir ladder, in `lib/service_dir.py`.** Every voice-harness entrypoint (`maintenance/voice_regression_probe.py`, `perf/measure_voice.py`, `perf/measure_tts.py`) resolves the live `services/zoe-data/.env` through `resolve_service_dir()`: explicit `--service-dir` always wins → this repo's `services/zoe-data` if it has a `.env` → the MAIN worktree's (via git's `--git-common-dir`, never a hardcoded `/home/zoe/assistant`). So a run from a git worktree — direct or via the probe — needs no flag. Do not re-implement or fork the ladder per script; that drift is exactly what it exists to prevent (the probe invokes measure_voice as a SUBPROCESS, so the shared module also keeps the import graph acyclic). When no `.env` resolves anywhere it returns the in-tree default so the EXISTING loud skip/error still fires (`status=error`, exit 2): the ladder fixes the DEFAULT, never the failure mode — **a skip is not a pass**. Pinned by `tests/unit/test_probe_dsn_resolution.py`.
- `setup/kokoro_sidecar.py` persists its hot phrase cache under `~/.zoe/kokoro_cache/` (override `ZOE_KOKORO_CACHE_DIR`; disable with `ZOE_KOKORO_CACHE_PERSIST=0`) — `<sha256(key)>.wav` files plus `manifest.json` (hits/last_used/bytes), reloaded frequency-ranked on startup. Cache keys are VOICE-SCOPED (`<voice>|<lowercased text>`, `_phrase_cache_key`) so a voice switch (the panel's "Zoe's voice" setting or a `KOKORO_VOICE` change) never replays stale audio in the old voice — old text-only keys just miss and age out of the disk budget. Writes happen only off the synth hot path (periodic flush + shutdown) and are fail-open; disk budget via `ZOE_KOKORO_CACHE_MAX_DISK` / `ZOE_KOKORO_CACHE_MAX_DISK_BYTES`. Never point a temp/test instance at the live dir — use a `mktemp -d` dir and a non-10201 `KOKORO_SIDECAR_PORT`.
- Host install is orchestrated by `setup/install-jetson.sh` (idempotent: generates `.env` secrets → Docker spine → `deploy/migrate.sh` → `download_gguf_models.sh` → systemd spine → health gate) and touch panels by `setup/install-pi.sh` (SSH: wraps `touchscreen/install_touchscreen.sh` + `pi_voice_daemon_install.sh`). The installer copies opt-in unit templates (`OPTIONAL_UNITS`, e.g. `flue-executor.service`) but **never auto-enables them** — a fail-closed guard `die`s if one ever reaches the auto-enabled `SYSTEMD_SPINE` — and it is **side-effect-free with respect to dispatch control**: it never creates or touches the shared `~/.zoe/multica_dispatch_paused` sentinel (which the live zoe-data poll loop reads every cycle, so recreating it on a reinstall would halt live dispatch). Arming that pause is an operator go-live action, never a provisioning side effect. Shared bash helpers live in `setup/lib/common.sh` (logging, `gen_secret`, idempotent `env_set`) — `.gitignore` un-ignores `scripts/setup/lib/*.sh`. `download_gguf_models.sh` fetches the canonical Gemma 4 E4B-QAT + MTP rock (`unsloth/gemma-4-E4B-it-qat-GGUF`), NOT the old Llama/Qwen GGUFs.
- **Host-provisioned agent binaries are PINNED here, not installed ad hoc.** `setup/install_cursor_agent.sh` provisions `cursor-agent` at an exact version into `~/.local/share/cursor-agent/versions/<v>/` and points `~/.local/bin/cursor-agent` at it. It is separate from `install-jetson.sh` because the binary is a **host** install that the `zoe-omnigent` container bind-mounts read-only — not an image dependency — and because omnigent enforces a per-harness MINIMUM (`_CURSOR_MIN_VERSION`) and reports a too-old binary as the string `"version-too-low"`, which a truthiness check reads as present. Provisioning is atomic: it stages the download into a sibling temp dir, verifies the staged binary reports the exact pin, then renames it into place — so an interrupted run never leaves a partial version dir that the next run mistakes for installed. It never trusts an existing target on `-x` alone: an executable-but-wrong-or-partial version dir is re-verified via `--version` and reinstalled if it does not report the pin, so **the active symlink can never point at an unverified binary** (there is no version override — the installer always targets and verifies the literal pin). Run `--check` to audit a host without changing it (it audits against the literal `CURSOR_PINNED_VERSION`); it exits non-zero on drift or on an install that cannot report its version. The container honours this pin (`modules/omnigent/entrypoint.sh`) by preferring the host symlink's target **only if it reports the declared pin**, else the repo-declared pin (also `--version`-verified), never the newest directory — and if neither verifies it **fails closed NON-FATALLY**: it clears any stale active symlink, logs a WARNING, and lets the omnigent server boot with the Cursor harness simply unavailable (no `exit`, so the container never restart-loops). Keep the entrypoint's `DECLARED_PIN` equal to the script's `CURSOR_PINNED_VERSION`, and bump the pin in the same pass as an omnigent upgrade, since that is when the minimum can move. The fetched artifact is verified against a HARDCODED per-arch SHA-256 with **no env or argv override** — deliberately, so nothing an inherited environment can reach may swap the pinned digest (a spoofed `--version` would otherwise fake authenticity). Its offline test (`tests/unit/test_install_cursor_agent_verify.py`) injects a fixture digest by running a TEMP COPY of the script with the constants string-replaced, never by a production seam.
- `setup/zoe_voice_daemon.py` ships WITH a companion module: `setup/zoe_voice_announce.py` (P-W2.3, stdlib-only) holds the announce poll/defer/expire decision logic so it is unit-testable in slim CI (`services/zoe-data/tests/test_voice_announce_daemon_logic.py` — the daemon itself imports pyaudio/numpy and can't load there). **Deploy BOTH files together** to `~/.zoe-voice/` on the panel (live path: `/home/pi/.zoe-voice/`, user service `zoe-voice`); the daemon degrades loudly (announce polling disabled, one WARNING) if the module is missing. The poll claims `GET /api/voice/announcements` with the existing `DEVICE_TOKEN`/`X-Device-Token` (no new provisioning), speaks through the same `/api/voice/speak` + `play_audio_b64` path as replies (barge-in, wake suppression, post-play cooldown all identical), never speaks while a turn/TTS/cooldown is live (defer; server TTL expires stale rows), and backs off quietly (up to 60 s) while zoe-data is down/restarting — a failed poll must never crash the daemon or touch the wake path. Env: `ZOE_ANNOUNCE_POLL_ENABLED` (default on), `ZOE_ANNOUNCE_POLL_S` (default 5). **Speaker-ID shadow gate (W5):** `SPEAKER_ID_SHADOW` defaults **true** — with `SPEAKER_ID_ENABLED=true` the daemon identifies + logs every turn (journal + `~/.zoe-voice/speaker_shadow_metrics.jsonl`, metadata-only rows per the biometric retention policy) but never attaches `voice_user_id`/`voice_score` to the turn payload; flip shadow off only after the shadow week's FA/FR review (pinned by `tests/unit/test_voice_daemon_speaker_shadow.py`).
- Installed systemd user units live in `~/.config/systemd/user/`; the copies here are templates. Keep both in sync when changing a unit. `setup/systemd/*` are USER units; `setup/systemd/system/*` are the few that must be **system** units (installed to `/etc/systemd/system/`, root) — kept in a subdirectory so the documented `cp setup/systemd/*.service ~/.config/systemd/user/` glob can never install one into the user manager, where its privileged directives silently do nothing.
- **Latency-critical user units must carry their cgroup memory guards IN THE TEMPLATE** (`MemorySwapMax=0` + `MemoryLow`, plus `MemoryMax` unless the unit is a large unified-memory process like llama-server where a ceiling turns a spike into an OOM kill). Protection that exists only as a local drop-in is protection one host has and no rebuild reproduces — that was the #1409 finding, and it recurred on 2026-08-03 when both `flue-*` sidecars were found uncapped, `flue-zoe-brain` (the **top** brain lane under `ZOE_BRAIN_BACKEND=flue`) 87% paged out. **`MemoryLow` alone is not swap immunity** — it is reclaim ordering; only `MemorySwapMax=0` holds. The mechanism, measured 2026-08-03: a leaf's *effective* `memory.low` is capped by its ancestors' and every ancestor **on this host** (`user.slice` → `user-1000.slice` → `user@1000.service` → `app.slice`) is `0`, so a leaf floor computes to 0 whatever it says — a slice-configuration property that is fixable by protecting the ancestors, not a kernel law, so re-measure on a rebuilt box rather than assuming, while `memory.swap.max` is enforced per-cgroup with no such propagation. Across six live units the split was total — every unit denying swap held **0** swap, every unit not denying it was **96-98%** out, at floors of 6G/3G/2G/512M/0 alike. The same day the gap turned up a third time in `zoe-data`, whose `MemoryLow=2G` + `CPUWeight`/`IOWeight` `300` were real, live, and in **no** tracked file; treat "primary backend API" as voice-path (**Moonshine STT runs in-process**), and track scheduling weights alongside the memory guards — resident-but-descheduled is the same product bug. Pinned by `tests/unit/test_systemd_memory_protection.py`, which enforces the doctrine rather than the numbers: retuning a cap is fine, dropping one fails, and a new latency-critical unit must be added to its `NO_SWAP_UNITS`. **Size a ceiling from the RUNTIME's behaviour under it, never as a multiple of a `VmHWM` sampled on a starved box** — that method produced both `flue-*` ceilings on 2026-08-03 and was corrected the same day (a starved `VmHWM` is a *lower* bound on the unstressed peak, so every multiple inherits the error). Measured for Node: V8 reads the cgroup limit and sizes its JS heap to ~51% of it (4144 MB uncapped on this box), so a runaway *JS heap* self-limits gracefully — but **external memory (Buffers, stream chunks) is outside that budget** and gets SIGKILLed by the cgroup instead (exit 137 under `MemoryMax=1G`), which is precisely the streamed-response path a brain sidecar uses. Ceilings are leak backstops, not working limits: the test requires `MemoryMax` ≥ **3×** `MemoryLow` (3 and not 2 because the brain's original `512M`/`1G` was exactly 2×), with bounded non-growing workloads documented in `TIGHT_CEILING_OK`. **A `MemoryMax` exemption must state its reason** — `MEMORY_MAX_EXEMPT` maps unit → rationale and the test rejects an empty one, because the two live exemptions are not the same argument: llama-server's ceiling would be *unreliable* (GPU/NvMap pages escape cgroup accounting), zoe-data's would be *unsafe* (accounting is complete, but a ~1.1 GB-steady/3.16 GB-peak production surface plus denied swap makes an ordinary transient a total-outage OOM kill). **Applying to a live host is a drop-in, never a template copy** — installed units carry host-specific edits (llama-server's binary/model paths). Sizing evidence + operator runbook: `docs/knowledge/memory-pressure-profile.md`.
- **The shared Serena MCP server (`setup/systemd/serena-mcp.service`, port 9121) is ONE process for the whole agent fleet** — but only as far as every agent's OWN config points at it. The unit cannot enforce that: a `command =` entry in any agent config (`.mcp.json`, `.codex/config.toml`, …) still stdio-spawns a private ~200-270 MB Serena, and nothing alarms — the shared server stays healthy and `serena_mcp_health.sh` passes while the extra processes pile up. Measured 2026-08-02: seven such spawns (~1.4 GB) from two Codex sessions, beside a healthy shared server, because `.codex/config.toml` was never migrated with `.mcp.json`. `zoe-serena-reaper` does not catch them (live parents, not orphans). Audit with `pgrep -af "serena start-mcp-server" | wc -l` — >1 means an agent config was missed. Fleet-wide config table: root `AGENTS.md`. Three further rules are load-bearing:
  - **Never use Serena's default port.** `--port` defaults to **8000**, which is zoe-data's PRODUCTION port — the default would collide with the live API. The port must always be set explicitly; 9121 is free, outside Zoe's dense 8000–8123 block, and below the ephemeral range (32768–60999) so the kernel cannot transiently steal it.
  - **Bind 127.0.0.1 only, never 0.0.0.0.** This server can read the entire repo; a LAN-exposed code-intel server is a real exposure. `serena_mcp_health.sh` fails on a non-loopback bind (it tolerates exactly one listener that is not Serena's: the bridge below). **Serena's own bind is not negotiable — reach it from elsewhere with a proxy, never by rebinding it.** The one such proxy is `setup/systemd/system/serena-bridge.{socket,service}`, which fronts `127.0.0.1:9121` on `172.28.0.1:9121` — the gateway of `zoe-codeintel`, an `internal` Docker network whose only member is `zoe-omnigent` (pinned at `172.28.0.2`). It exists because the container used to spawn its own ~900 MB Serena per agent session. **The hop must be HTTP-aware, never L4** — see `maintenance/serena_bridge_proxy.py` below; with `systemd-socket-proxyd` the TCP path worked and every request came back `421 Invalid Host header`. Two things make it safe, and **both** are required:
    - `IPAddressDeny=any` + `IPAddressAllow=172.28.0.2/32` on the socket unit. **This is the actual access control.** The dedicated network is NOT: measured 2026-07-22, a container on `zoe-network` freely reached a listener on another bridge's GATEWAY, because host-local delivery is INPUT while Docker's isolation rules are FORWARD. A bare gateway bind is therefore no more private than binding on `zoe-network` — the option that was rejected for handing whole-repo read to `homeassistant` and the third-party `ghcr.io/multica-ai/*` images. (Cross-network access to *container* addresses IS blocked; only host addresses leak.)
    - **System scope, not user scope.** A `--user` unit logs `unit configures an IP firewall, but not running as root` and then starts with **no filtering at all** — silent fail-open, measured. Same fail-open if the kernel lacks cgroup-BPF firewalling, so the install is not done until the negative control in `setup/systemd/README.md` proves a non-member container is refused.
  - **The cap is now the FLEET bound, not a per-instance one.** The old stdio config capped each spawn at 1G/2G, which bounded each member but not the fleet (6 agents × 2G = 12G on a 15.6G box → the 2026-07-16 OOM). Keep `MemoryHigh`/`MemoryMax` on the unit; do not raise them to paper over a leak.
- **`maintenance/codebase_memory_capped.sh` bounds the OTHER per-agent code-intel server.** codebase-memory is the same memory hazard as Serena but needs the OPPOSITE fix, and conflating them is how it survived unnoticed: `codebase-memory-mcp` 0.8.1 is **stdio-only** (`--help` offers just "Run MCP server on stdio"; its `--port` is the UI graph viewer on 9749, NOT a transport), so it cannot be consolidated onto one shared server the way Serena was. Per-agent spawning is forced by the tool — what was wrong is that each spawn was UNBOUNDED. Measured 2026-08-02: fourteen live instances totalling ~1.27 GB, one at 473 MB, one resident **2.3 days**, on a box whose brain + TTS already hold ~9 GB of 15.6 GB (same afternoon: load 55, 45 GB swap). Both agent configs now launch it through this wrapper, which wraps each spawn in a systemd user scope with `MemoryHigh`/`MemoryMax`/**`MemorySwapMax`** (default 512M/768M, over the healthy 50-220 MB working set and under the runaway outliers). Swap is capped alongside RSS deliberately — capping RSS alone just relocates a leak into swap, as Serena's 2.1 GB swap leak proved. Falls back to an uncapped launch when no systemd user bus exists (container/no session) rather than breaking code-intel. **The reaper is not a substitute:** these processes have live agent parents, so they are never orphans. If a release ever adds an HTTP transport, consolidate it the way Serena was and delete this wrapper. Pinned by `tests/unit/test_agent_mcp_memory_bounds.py`.
- **`maintenance/serena_bridge_proxy.py` is the bridge's proxy half, and it must stay HTTP-aware, streaming, and socket-activated.** Serena constructs its `FastMCP` without `transport_security=`, so the MCP SDK auto-enables DNS-rebinding protection for its loopback bind (`allowed_hosts = 127.0.0.1:* / localhost:* / [::1]:*`) and 421s the container's `Host: 172.28.0.1:9121`. Four properties are contracts, all pinned by `tests/unit/test_serena_bridge_proxy.py` + `tests/unit/modules/test_omnigent_mcp_config.py`:
  - **Rewrite only the Host header, on every request.** Connections are kept alive and carry many requests; rewriting only the first leaves request #2 onward getting 421. Everything else — request line, header order/casing, bodies — is relayed byte-identically, and ambiguous heads (two `Host:` lines, obs-fold, `Transfer-Encoding` + `Content-Length` together) are refused rather than resolved.
  - **Stream both directions concurrently.** MCP replies are open-ended `text/event-stream`; a read-to-EOF-then-forward proxy hangs forever instead of failing, which is the worst failure shape available here.
  - **Never bind for itself** — no `--listen`, and it exits non-zero without `LISTEN_FDS`. For a socket-activated service the listening socket is covered by the SOCKET unit's access list, so a self-bind would silently drop `IPAddressAllow`, the bridge's actual access control.
  - **`ExecStart` runs the INSTALLED copy at `/usr/local/lib/zoe/serena_bridge_proxy.py`, never the checkout.** The unit sets `ProtectHome=yes`, so `/home` is invisible to it; re-install the script whenever the repo copy changes, exactly like the units. Stdlib only — no new dependency on this box.
  Trade-off, measured and accepted: Serena runs ALL tool calls through one `SerenaAgent` TaskExecutor queue, so the shared server **serialises** the fleet (6 concurrent cold calls = 6.15s wall for 4.53s of work; every caller waits for the full drain). Serialised code-intel beats an OOMed voice brain. Do not "fix" this by going back to per-agent servers.
- Scripts run by timers/CI have no login session: prefix user-service systemctl calls with `XDG_RUNTIME_DIR=/run/user/$(id -u)`.
- Graphify is **retired and fully removed**: `graphify-out/` is not committed (gitignored), and the auto-refresh (`refresh_graphify.sh` + the `zoe-graphify-refresh` systemd timer/service), the repo write-back wrapper (`graphify_local_refresh.py`), and the former observe-only probe + shard tooling (`graphify_local_probe.py`, `graphify_local_shard_matrix.py`, `graphify_shard_sync_plan.py`, `graphify_shard_merge_validate.py`, `graphify_local_model_matrix.py`, `graphify_openrouter_cli.py`) have all been removed. Code intelligence is now provided by the codebase-memory MCP, re-indexed on demand. Do not re-introduce any graphify script, timer, or committed `graphify-out/` artifact.
- `prune_worktrees.sh` is dry-run by default; never pass `--execute` without operator review of the candidate list. Skips dirty, locked, live-checkout, unmerged, and recently-active worktrees.
- Destructive maintenance scripts must be dry-run by default, require explicit execution flags, and print the candidate list before deleting or rewriting anything.
- **Memory-store resilience trio (2026-07-31 torn-HNSW incident: zoe-data crash-looped 37+ times, unnoticed, and recovery depended on documents living in SQLite — which nothing had ever verified).** All three read the palace **directly via SQLite `mode=ro`, never through `chromadb`**: the moment they matter is the moment the native index is damaged and `get_collection()` hangs or segfaults, so they must need neither the index nor an embedder.
  - `export_memory_store.py` — nightly plain-JSON copy of every collection (id/document/metadata). Retention prunes ONLY its own dated files via a strict `memory-export-YYYYmmdd-HHMMSS.json[.gz]` pattern; writes `.partial` then renames so a crash can't leave a truncated file that looks valid. Deliberately NOT ordered after `zoe-data.service`: it must still run on the nights zoe-data is crash-looping.
  - `check_memory_tombstones.py` — reports HNSW tombstones (`total_elements_added - len(id_to_label)`; Chroma never reclaims on delete). Read-only by default, **exit 2 = at/over warn threshold** so a timer can gate on it. Thresholds are measured, not invented: 2026-08-02 live baseline was drawers 0% (freshly rebuilt), audit 19.3%, one legacy segment 21.8% — so ~20% is NORMAL and `--warn` sits at 25%. `--execute` rebuilds a collection and is guarded three ways: refuses while zoe-data serves on :8000, takes a pre-compaction export first, and requires the collection name typed back.
  - `zoe_crash_loop_watch.py` — alerts via flue-zoe-telegram's bot token. **Polls; never `OnFailure=`.** zoe-data runs `Restart=always`, so a crash loop never reaches systemd's `failed` state and `OnFailure=` cannot fire; making it fire would need `StartLimitBurst`, i.e. telling systemd to STOP restarting Zoe, turning a self-healing transient into a permanent outage. Telegram is the channel because it is a SEPARATE process — zoe-data's own announce/voice path needs zoe-data up, so it can never report its own death. Alerts only on (restart delta ≥ threshold AND /health down); a counter reset must never read as a loop, and an undelivered alert stays pending so the next tick retries. Pinned by `tests/unit/test_zoe_crash_loop_watch.py`.
  Units: `setup/systemd/zoe-memory-export.{service,timer}` (02:40, `Persistent=true` — a missed backup is a real gap; runs the tombstone report on the same tick behind `-`) and `setup/systemd/zoe-crash-loop-watch.{service,timer}` (every 2 min, `Persistent=false` — an alert about an ended outage is noise). Both are operator opt-in.
- **`compact_pipeline_state.py` COMPACTS the pipeline state store; it must never ROTATE it.** `~/.zoe/engineering_pipeline_runs.jsonl` is event-sourced STATE, not append-history: `pipeline_store.save_state()` re-appends a full (growing) state snapshot every write, so the live store reached 1592 MB / 8421 records for 129 task_refs while the latest snapshot per ref totalled 1.3 MB. Rotation — correct for genuine append-history like `router_head_shadow.jsonl` (whose reports aggregate across lines) — would DELETE LIVE STATE here for any task_ref whose newest snapshot fell in the rotated-out segment. Do not bolt this onto the rotation mechanism. The tool's contract:
  - **Keep set = latest `state`-bearing record per `task_ref` UNION the last `--keep-tail` records.** Two readers, two needs: `pipeline_store._latest_state_from_lines` (last-match-wins) needs only latest-per-ref, but `engineering_harness_loop.parse_pipeline_findings` reads the last `DEFAULT_PIPELINE_TAIL` (200) lines as an EVENT STREAM and counts recurring `(task_ref, phase)` gate blocks — latest-per-ref alone collapses those counts to 1 and silently degrades triage. `--keep-tail` defaults to 200 to match; `tests/unit/test_compact_pipeline_state.py` pins the two constants equal. On the live store the union costs 14.2 MB vs 1.3 MB latest-only — still 99.11% reclaimed. Re-verify the reader set before narrowing the keep set.
  - **Rewrites IN PLACE under `fcntl.LOCK_EX`, never temp-file + rename.** flock is a property of the INODE: writers `open()` then flock, so a rename would leave an already-open writer appending to an orphaned inode — a silently lost state write with the lock excluding nothing. The inode must be preserved; the lock is held across the whole operation so writers block (correct) rather than race. The AST-level ban on `os.rename`/`os.replace`/`shutil.move` in the tool is pinned by test, as is the concurrent-writer survival property.
  - **Crash safety is by ordering, not atomicity:** compacted bytes are staged to a temp file and fsync'd, AND a full backup of the original is fsync'd, both BEFORE the original is touched; the backup path is printed first and retained for the operator to delete. A crash mid-rewrite is recoverable with a plain `cp` from the backup.
  - **Everything streams** — the store is never read into memory (peak RSS 21.6 MB scanning 1592 MB). That is the point: `load_latest_state` currently does `read().splitlines()` on the WHOLE file, which is the hazard being contained.
- `purge_orphaned_test_data.py` soft-deletes rows in the LIVE household DB, so its owner scope is a contract, not a heuristic: every owner pattern must be **fully anchored** and unable to match a real household id. Extend it only via `owner_pred()`/`TEST_OWNER_RE` — both are pinned by `tests/unit/test_purge_predicates.py`, which asserts the junk owners match AND that real ids (`jason`, `zoe-touch-pi`, …) never do. Verify any new pattern against the DB read-only before adding it; a past audit's assumed `test_calendar_*` rows never existed (zoe-data ignores the untokened `?user_id=` override and attributes such writes to `guest`). Note the `guest` arm is deliberately broad — it is the shared kiosk account, so a real panel-entered event is in scope; keep it dry-run-reviewed.
- Git history rewrites must run only in a disposable bare mirror clone with typed confirmation. Force-pushing rewritten history requires a separate explicit push flag, typed push confirmation, and exact confirmation of every resolved `origin` push URL. Pushing to multiple URLs is not atomic: every confirmed destination is attempted regardless of earlier failures, and the run exits non-zero with the full list of any destinations left divergent.
- Live deploy (`deploy_live.sh`) gates on TRACKED changes only, never on untracked files. Both the pre-pull clean-tree gate (`require_clean_tree`) and the pre-rollback guard (`require_no_tracked_dirt`) block only when uncommitted tracked worktree/index changes are present — a fast-forward or `git reset --hard` would clobber those. Keep those runtime paths gitignored (root `.gitignore`) and keep the gates tracked-only. Pinned by `tests/unit/test_deploy_live_clean_tree.py`.
- `deploy_live.sh` and the continuous-deploy runner (`.github/workflows/deploy.yml`, push-to-`main` → fetch + `reset --hard` + restart) double-drive the SAME shared `/home/zoe/assistant` `.git`/worktree. Fail-closed is intended — a blocked voice diff stays on `main` and blocks subsequent deploys until the probe is re-run (unwedge procedure: `docs/knowledge/merge-and-deploy.md`). Full CD mechanism: `docs/knowledge/merge-and-deploy.md`.

## Forbidden

Rules for the autonomous loops that run from this subtree. `router_selftrain.py` promotes a model into the live voice path without a human in the loop; the ratchet is the only thing making that safe.

- **Never add a promotion bypass to `router_selftrain.py`** — no `--force-promote`, no "operator override", no env escape hatch. A candidate that cannot pass the ratchet is not safe to serve; fix the model, not the gate. `tests/unit/test_router_selftrain_gate.py` fails if a bypass symbol appears in the source.
- **Never promote** a router model that regresses overall accuracy against the live-re-measured incumbent, has chat false positives > 0, exceeds the p50 latency gate, or whose voice replay gate did not **run and pass**. A skipped probe (exit 0 until its non-pass streak alarm trips) is NOT a pass.
- **Never train on the frozen eval corpus** (`labs/needle-benchmark/corpus.jsonl`). The candidate's held-out guard must be recorded *and* independently re-verified; abort otherwise.
- **Never delete the last-known-good GGUF** — rollback must always be possible (archive is copied, never moved; retention never drops below 1).
- **Never leave llama-server stopped**, and never leave the sidecar serving an unverified model.
- The loop's **only** permitted production mutation is swapping the sidecar model file and restarting `functiongemma-router.service`. It must never modify the live routing code path.
