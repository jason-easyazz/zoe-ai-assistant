# services/omi-sync — Omi pendant ring sync (Pi side, flag-dark)

## Purpose

"Record on the pendant, sync when in range of Zoe." The owner wears an Omi CV1 pendant that records to its own SD storage while powered. When he comes within Bluetooth range of the panel Pi, this small service connects (to the Pi, NOT the Omi phone app; stock firmware needs no bond, phase-2 Zoe firmware needs the owner-made bond and this service only CHECKS it), drains the storage, decodes Opus to 16 kHz WAV, uploads each recording to zoe-data, and — on ring firmware — frees the pendant's ring only after zoe-data confirms it stored that recording. The owner's pendant runs firmware 3.0.18, which predates the ring protocol: see the legacy-file contract below. Nothing goes to Omi's cloud. Design + status: [`docs/architecture/omi-integration-plan.md`](../../docs/architecture/omi-integration-plan.md) (section 4 and the operator runbook).

One Pi may sync SEVERAL pendants (`OMI_PENDANT_ADDRESSES`); **who owns which pendant is zoe-data's `omi_devices` registry, never this service's business** (owner requirement 2026-10-13: link a certain Omi to a certain user, sync no matter who is logged in, as long as it is in range of the Pi, and only to the user it is registered for).

It runs as its OWN process and unit (`scripts/setup/systemd/omi-sync.service`, operator opt-in, never auto-enabled) — **not** inside `zoe_voice_daemon.py` — so a BlueZ fault cannot touch the voice path.

## Ownership

- `omi_sync/ring_protocol.py` — the ring wire format as pure functions (UUIDs, commands, notifications, 444-byte records, the 3.0.20 firmware gate). No `CMD_RING_CLEAR` encoder exists, deliberately.
- `omi_sync/legacy_protocol.py` — the firmware-**3.0.18** multi-file SD protocol (`LIST_FILES` / `READ_FILE`), as pure functions. Verified from `storage.c` at the commit that shipped 3.0.18 only; 3.0.19 is NOT covered. No encoder for its `DELETE_FILE` (`0x12` — the same byte as the ring's ADVANCE).
- `omi_sync/spool.py` — the durable local custody spool (SQLite, `synchronous=FULL`): every received record, until Zoe confirms its recording.
- `omi_sync/recordings.py` — deterministic segmentation of spooled records into recordings, time resolution (device clock vs host), Opus → WAV.
- `omi_sync/engine.py` — one drain session and THE CUSTODY RULE (`Drain`, `advance_target`, `ring_label`).
- `omi_sync/uploader.py` — HTTP upload + the mapping of Zoe's answer to a custody outcome (`classify`: CONFIRMED / REJECTED / UNAVAILABLE / NOT_REGISTERED). `device_hash(address)` is THE device identity (16 hex, never the address).
- `omi_sync/runner.py` — the sync loop over every configured pendant: `Rotation` (round-robin, per-pendant next-visit time) + `Runner.visit/step`. A visit is one old-style session (shared radio lock per visit, connect, drain, release); one pendant's absence, drop or "not assigned yet" never holds up another.
- `omi_sync/ble_link.py` — the only module that needs a pendant (bleak 0.22.3). Everything else is tested on fixture bytes. Connection recipe (verified on the real pendant 2026-10-12): `sudo -n hcitool lecc --random <addr>` first (32 s supervision timeout; BlueZ's 420 ms default dies at this range), then bleak on the connected device; no scan, no pairing, no agent; retry with backoff. A failed `lecc` is ALWAYS followed by LE Create Connection Cancel (`hcitool cmd 0x08 0x000E`) — hcitool never cancels, and a pending initiation wedges every later `lecc` and re-creates an owner-less link on every drop — and an LE link to the pendant that is already up (`hcitool con`) is CLEARED (cancel first, then `ledc` — the reverse order lets the controller re-create it within ~110 ms) before our own `lecc`; it cannot be adopted, because bleak's BlueZ connect scans first and a connected pendant does not advertise. Pinned by `tests/unit/test_omi_sync_ble_link.py`.
- `omi_sync/link_security.py` — bonded-only enforcement for phase-2 (Zoe) firmware (`labs/omi-firmware`), READ-ONLY: BlueZ `Device1.Paired` AND `Bonded` (`busctl get-property`) before connecting, the kernel link's `ENCRYPT` flag (`hcitool con`) after subscribing, and the bond again; `ble_link.connect(require_bond=True)` raises `NotBonded` / `InsecureLink` and tears the link down before any storage command. Pinned by `tests/unit/test_omi_sync_bonded_only.py`.
- `omi_sync/radio_lock.py` — the panel Pi's one-radio advisory `flock` (`ZOE_BLE_RADIO_LOCK`, default `~/.zoe-ble-radio.lock`), a deliberate copy of `services/panel-bluetooth/panel_bt/radio_lock.py` (same path, same semantics; two venvs, no import). `ble_link.connect` takes it first and raises `ConnectError("radio busy ...")` if the Settings > Bluetooth agent holds it (a scan, an open link, a FIRMWARE UPDATE) — so a sync can never take the pendant's single connection in the gap after a firmware reset. Pinned by `tests/unit/test_omi_sync_radio_lock.py`.
- `omi_sync/health.py` — the pendant health heartbeat as pure functions + a small throttle: `build_report` (numbers only), `away_wait` (the exponential back-off, capped), `Reporter`. The engine only COLLECTS the facts (`DrainResult.battery_pct/firmware/ring_*/dropped_total`, informational, never read by a custody decision); `runner.py` sends the report after a visit through `HttpUploader.report_health`. Zoe side: `services/zoe-data/omi_health.py`, migration 0056, `docs/knowledge/omi-pendant-health.md`.
- `omi_sync/check.py`, `omi_sync/cli.py`, `omi_sync/config.py` — the read-only device check (`check -p N` picks the Nth configured pendant), the entry points (`run | check | status`), env config (`OMI_PENDANT_ADDRESSES` comma list, the single `OMI_PENDANT_ADDRESS` as fallback; `OMI_SYNC_UNREGISTERED_RETRY_S`).
- `THIRD_PARTY_NOTICES.md` — the MIT notice for the Omi source the protocol is ported from. Keep it with any substantial new port.
- The Zoe side lives in `services/zoe-data/omi_recordings.py` + `omi_devices.py` + `routers/omi_recordings.py` (migrations 0045, 0047).

## Local Contracts

- **Custody: audio is freed from the pendant only after Zoe CONFIRMED it stored that exact recording** (HTTP 200, `ok`, and the echoed SHA-256 of the bytes sent — `uploader.classify`). Delivery over Bluetooth is not custody. The ring is advanced only to `engine.advance_target(...)`: never past the first unconfirmed record, never past what we hold or confirmed contiguously from the pendant's own read pointer. A dropped link, refused READ, inconsistent DONE, unavailable Zoe or rejected recording advances nothing.
- Every received record is committed to the spool BEFORE anything else happens to it; a record leaves the spool only through `Spool.mark_confirmed`. Idempotent by `(device, ring, seq)`; a confirmed range is a tombstone.
- Which protocol runs is decided by DIS `2A26` BEFORE any storage command: **≥ 3.0.20 → ring**; **exactly 3.0.18 → the legacy file protocol, only with `OMI_SYNC_LEGACY_FILES=1`** (its firmware deletes each file itself on delivery — a free we can neither gate nor defer, so the spool is the ONLY custody; default off); anything else is refused with GATT reads only (the same opcode byte is ADVANCE on one protocol and DELETE_FILE on the other). An unknown codec id (the owner's pendant reports `0x0f`; the source says 21) is refused unless `OMI_SYNC_ASSUME_CODEC` names one; a recording whose frames do not decode is HELD (raw records stay in the spool), never uploaded. Durations come from the decoded PCM, not the codec id. Every freshly rendered recording logs its decoded `level peak=… rms=…` in the sync line's notes (diagnostic, never a gate) so a pendant that heard nothing is tellable from one that did not decode.
- The pendant is never written to except: the storage commands above (list/read/advance/stop) and, only with `OMI_SYNC_SET_DEVICE_TIME=1`, one clock write at the start of a session. No pairing, no agent, no OTA/SMP traffic, no settings or haptic writes.
- The last recording of a session stays OPEN (not uploaded, not freed) until it has been quiet for `OMI_SYNC_GAP_S`, hit `OMI_SYNC_MAX_RECORDING_S`, or the pendant is fully drained; a tail we have not caught up with (dropped READ) is held however old it is.
- The pendant address never leaves the Pi: uploads carry `device_hash(address)` (`X-Omi-Device`). That id is ONE identity shared with Settings > Bluetooth: `panel_bt.model.device_id` is the same derivation (copied, two venvs, no import), pinned by `tests/unit/test_omi_device_identity.py` incl. a golden value — changing it orphans every stored and spooled recording.
- **Several pendants, one Pi.** Each configured address is visited in turn; spool rows, staged WAVs and the next-visit time are per pendant (the spool key already includes the device id). The radio lock is held per visit, never across visits, so Settings > Bluetooth can always get in between; if it holds the radio every visit is `ConnectError("radio busy ...")` and the rotation moves on without touching a pendant.
- **A pendant nobody owns keeps its audio.** Zoe answers 409 `device_not_registered` (an admin has not assigned it): `classify` -> `NOT_REGISTERED`, the engine stops uploading for the session, nothing is confirmed so nothing is freed (ring ADVANCE stops at the first unconfirmed record; legacy files are held by the spool), and the runner retries after `OMI_SYNC_UNREGISTERED_RETRY_S` (default 900 s, floor 60) instead of the 30 s unavailable cadence. Assigning the pendant is all it takes; the next visit uploads everything. Nothing about who is signed in on the panel is sent, read or used here.
- **Health heartbeat + away back-off.** After each visit (and at least every `OMI_SYNC_HEALTH_HEARTBEAT_S`, 900 s, while the pendant is away) the runner POSTs `/api/omi/device-status`: `reachable`, the miss count, the last clean sync as an AGE, battery (standard Battery Service), firmware, ring fill / stored / capacity bytes (END of session) and the pendant's cumulative `dropped_packets`. NUMBERS ONLY - no audio, transcript, address or note (zoe-data's model is `extra=forbid`). Best effort after the custody work: a refused or failed report is retried at the next visit and can never fail a visit or change custody; only Zoe's own `{"ok": true}` counts as delivered (a 200 with any other body is retried). The engine records the firmware and battery BEFORE the firmware gates, so a pendant refused for unsupported firmware still reports both. Kill switch `OMI_SYNC_HEALTH=0`. A pendant that does not answer (`ConnectError` other than `radio busy`) is retried at the scan interval doubling up to `OMI_SYNC_AWAY_BACKOFF_MAX_S` (600 s); any connection resets it; a busy radio is not "away". The spool is `VACUUM`ed at start and after an uploading visit when it is mostly free pages (`Spool.compact_if_sparse`; no row changes).
- **Bonded-only pendants (`OMI_SYNC_REQUIRE_BOND`, default off; `all` or a list of addresses).** For a listed pendant: no BlueZ bond (`Paired` and `Bonded` both READ true; an unreadable property is not a bond) -> no connection attempt; after the subscribe the link must be `ENCRYPT`ed and the bond still present, else it is torn down unread. Never a fallback to an open link. Turn it on only after the pendant runs phase-2 firmware and is bonded (`labs/omi-firmware/RUNBOOK.md` E); on stock firmware it refuses every visit, by design. Refusals log at WARNING (`refused: ...`) and back off like an absent pendant. `OMI_SYNC_BLUEZ_ADAPTER` (default `hci0`) names the adapter whose bond is read.
- Flag-dark: `OMI_SYNC_ENABLED` unset/0 → `python -m omi_sync run` exits 0 without importing bleak or creating state. Opt-ins that default OFF: `OMI_SYNC_LEGACY_FILES`, `OMI_SYNC_SET_DEVICE_TIME`, `OMI_SYNC_ASSUME_CODEC`. Zoe-side, `ZOE_OMI_SYNC_ENABLED` unset → the routes do not exist (404).
- Stock-firmware caveat (read from `storage.c`): firmware without the custody capability frees records as the link layer acknowledges them; the spool is what makes that safe. Custody firmware (`CAP_APP_ACK_RECLAIM`, `ring_id`, `ADVANCE_ID 0x15`) is supported when the pendant advertises it.

## Forbidden

- Never send `CMD_RING_CLEAR` (`0x13`) or the legacy `DELETE_FILE` (`0x12`), and never add an encoder for either. Never ADVANCE on anything but confirmed state.
- Never pair, bond, unpair, trust, set an adapter property or register a BlueZ agent from this service (tests pin `ble_link.py` and `link_security.py`): stock firmware needs no bond, and the phase-2 bond is created ONLY by the owner-run `omi_bond` in `services/panel-bluetooth/panel_bt/bond.py`. This service only reads that the bond exists and that the link is encrypted. Never touch the MCUmgr SMP service (`8d53dc1d-…`): a firmware update is an owner-run operation (plan 4.10) done through Settings > Bluetooth devices (`services/panel-bluetooth`, which holds the radio lock for the whole update), never this service.
- Never send, derive or guess an OWNER from the Pi (no user id in an upload, no reading of the panel's session or binding): ownership is the registry's, resolved by zoe-data from `X-Omi-Device` alone.
- Never upload to any host except the configured `ZOE_URL`; never log audio, transcripts, the device token or the pendant address. The health report carries the hashed device id and numbers only: never the address, a note, a file name or any text the pendant or Zoe produced.
- Never import from `labs/` or `services/zoe-data`; never run inside the voice daemon, the Orin or a Docker image.
- Never delete a spool record or a staged WAV except via a CONFIRMED upload (or the confirmed-range prune).
- Never write the pendant's clock unless `OMI_SYNC_SET_DEVICE_TIME=1` (default off), and then only once, at the start of a session, after the offset was measured.

## Work Guidance

- Keep all decisions in `engine` / `ring_protocol` / `recordings`; `ble_link` stays thin. A new behaviour gets a fixture-byte or fake-pendant test with a break-the-fix control.
- Third-party API: check `opensrc path pypi:bleak@0.22.3` before changing `ble_link.py`; port Omi protocol facts from `~/.opensrc/repos/github.com/BasedHardware/omi` and cite the file in the code.
- Deploying to the Pi is an operator step (never from CI or an agent): copy `omi_sync/` from a worktree of merged `main` with a timestamped backup, then `systemctl --user restart omi-sync.service`; the exact commands and rollback are in [`docs/knowledge/omi-pendant-health.md`](../../docs/knowledge/omi-pendant-health.md).
- Hardware-only facts are marked UNVERIFIED in the plan until the operator has run `python -m omi_sync check` on the pendant (see the plan's section 4.7).
