# services/ — Zoe runtime services

## Purpose

Production runtime services for the Zoe assistant: the web/chat API, static UI, auth, protocol bridges, and realtime media.

## Ownership

- `zoe-data/` — THE production web + chat API (host uvicorn, port 8000). Single source of truth for chat, intents, memory, MCP tools, and background jobs.
- `zoe-ui/` — static frontend served by nginx (`dist/` is the docroot) plus `nginx.conf`.
- `zoe-auth/` — authentication service.
- `homeassistant-mcp-bridge/` — MCP protocol bridge to Home Assistant. (The n8n bridge was retired in March 2026 along with n8n itself — OpenClaw cron/skills/exec covers automation. The n8n SSO endpoints under `zoe-auth/` stay until that wiring is also removed.)
- `livekit/` — realtime audio/video infrastructure config.
- `zoe-core/` — Zoe's reasoning/orchestration core: the Pi agent (Gemma 4) that binds the other services together and calls abilities. This is the center of Zoe, not a monolith — it orchestrates and delegates; it does not absorb the other services' code. NOTE: a *different*, older `zoe-core` (the retired Docker monolith, replaced by `zoe-data`) was removed from the working tree and remains in git history only — that legacy tree must never be revived or extended. This service is the new Pi core, not that retired monolith.

## Local Contracts

- Exactly ONE production chat router: `zoe-data/routers/chat.py`. Never create `chat_v2.py`, `chat_new.py`, or parallel routers.
- No hardcoded NLU if/else in the production chat router; natural-language routing belongs in `intent_router.py` or Zoe Agent. (Hermes and OpenClaw are being RETIRED — operator decision 2026-07-22, `docs/architecture/multica-executor-migration.md` §5 — do not add new routing to either; their existing paths are deletion targets via the gated retirement PRs.)
- Code must work on BOTH Jetson Orin NX (GPU) and Raspberry Pi 5 (CPU); gate hardware-specific paths on `HARDWARE_PLATFORM`.
- Memory writes always carry scope (`personal` / `shared` / `ambient`); credentials are per user and per scope, never in global env vars.
- No `home` / `family` / `household` concepts in kernel code (router, memory schema, auth, tool signatures) — they belong in skills and scopes.
- `zoe-data` runs as a systemd USER service: `systemctl --user restart zoe-data.service` (never `sudo systemctl`).
- Exactly ONE calendar-event writer: `zoe-data/calendar_service.py::create_event_record`. All three callers (the voice/direct executor in `intent_router.py`, the `calendar_create_event` MCP tool in `mcp_server.py`, and the `/api/calendar/events` router) INSERT through it — never open a second `INSERT INTO events`. The helper owns only the row write; date parsing, UI notify, MemPalace, and response shape stay per-caller (they differ, and preserving them is what keeps behaviour identical). Voice-path changes here are replay-gated.
- Exactly ONE list writer: `zoe-data/list_service.py` — `create_list_record` / `create_item_record` are the only `INSERT INTO lists` / `list_items` sites for the Wave-3 trio (the voice/direct executor in `intent_router.py`, the `list_add_item` MCP tool in `mcp_server.py`, and the `/api/lists` router); `add_item_to_list` is the shared resolve-or-create add, whose fresh-list path lands the list row and first item in ONE transaction (asyncpg auto-commits, so separate INSERTs orphan an empty list on a mid-write failure). Behaviour choices stay per-caller as explicit parameters: the voice 10 s replay-dedup window, auto-created-list visibility, notification channel, and feature gating never move into the service. `skybridge_service.py` + `pending_suggestions.py` still carry their own list INSERTs (follow-up). Pinned by `tests/test_list_service.py` (`ci_safe`).

- **`zoe-core` KV-prefix contract — nothing turn-varying may sit at the FRONT of a request.** llama.cpp reuses cached KV only for an EXACT common prefix (Gemma's shared-KV + SWA attention has no `--cache-reuse`), so the two front-of-request surfaces are frozen by design. The SYSTEM PROMPT is pure SOUL.md: under `ZOE_CORE_MEMORY_SEAM=1` (set by `zoe_core_client._worker_env`) `extensions/memory.ts` contributes nothing, and the memory directive + packet are folded into the USER MESSAGE by `_compose_message` instead. The TOOL BLOCK (`extensions/abilities.ts`) is disclosed MONOTONELY over a bounded window (`ZOE_CORE_DISCLOSURE_WINDOW_TURNS`, default 6 turns = zoe-data's replayed `history[-12:]`) rather than recomputed from the last message, and `setActiveTools` is still called on EVERY turn even when the set is unchanged — that call is the unconditional strip of Pi's coding builtins.
- **`event.prompt` in a zoe-core extension is the COMPOSED prompt, not the user's utterance** — portrait, memory directive + packet, `[Recent conversation]`, then the utterance (verified live by instrumenting the handler). Anything matching on it sees the whole retained window: progressive disclosure re-armed a domain every turn from a keyword in replayed history, so the decay window never fired. `_compose_message` therefore introduces the user's turn with `_UTTERANCE_MARKER` and `abilities.ts` splits on it (`latestUtterance`); the two copies are pinned byte-equal by a test. With no context blocks the composed prompt is the bare message, unchanged.
- **A restarted/LRU-evicted Pi worker SEEDS disclosure from the replayed history, exactly once.** `createDisclosureState()` starts empty but zoe-data keeps replaying `history[-12:]` across that boundary, so scoping to the utterance leaves a continuation ("yes, do that" after a calendar clarification) matching no domain and getting NO tools — whole-prompt matching used to cover that by accident. `seedDisclosureState` folds those turns in at session start, crediting replayed turn *i* as turn *i* so the ordinary decay window applies unchanged. Three constraints keep it from re-shipping the bug above, and all three are pinned by tests with negative controls: it reads ONLY the `[Recent conversation]` block (never the portrait, recall context or memory packet — those are things Zoe knows, not things the user asked for), ONLY the `user:` lines in it (an assistant line is Zoe's own offer), and ONLY ONCE (`state.seeded`; a per-turn rescan re-arms from replaying history forever). The block LABELS are composition-owned like the delimiters and are escaped in content by `_neutralize_markers`, so a stored memory cannot forge a history block; `_HISTORY_LABEL` is pinned byte-equal to `HISTORY_MARKER`.
- **THE CURRENT TURN IS ALREADY IN THAT REPLAYED WINDOW, and must be counted once.** `chat_stream_generator` persists the user message (`chat.py:1617`) BEFORE it loads the window it replays (`… ORDER BY created_at DESC LIMIT 12`, `chat.py:2303-2309`), so the newest row is this turn and the model is shown it twice. Seeding it as elapsed *and* then processing it live ticked the clock twice for one turn, expiring every seeded domain a turn EARLY — a continuation whose initiating request was still visible arrived with its tool already decayed. `seedDisclosureState` therefore rolls the clock back by one when the block ends on a user turn (`currentTurnIsReplayed`), while still crediting that turn's domains at the index the live pass is about to reach. The test is POSITIONAL, not textual, and deliberately: chat.py strips an approval token (`chat.py:1655`) and can prefix an intent hint or replace the utterance wholesale via `openclaw_user_message` (`chat.py:2325-2330`), so text equality would miss exactly those turns; `LIMIT 12` over a DESC sort drops the OLDEST rows, so truncation cannot move the current turn off the tail. A future caller whose history ends on some OTHER user turn runs the window one turn long — the benign direction, chosen on purpose. The ordering itself is pinned by a test, because nothing else would notice it flipping.
- **What makes that ordering an INVARIANT is the per-session lock — so every history-bearing caller enters through `locked_chat_stream`.** The persist and the load are two points inside ONE `chat_stream_generator` run; a concurrent turn on the same session slots its own rows between them (`persist(B) → persist(A) → A replies and persists its assistant row → load(B)`), leaving B's replayed window ending on an ASSISTANT row. The roll-back is positional and must not try to see past that, so B's turn is counted twice and the early-decay bug returns. `/api/chat/` always held `_get_session_lock`; the A2A stream (`routers/system.py::a2a_task_stream`) called the generator raw, and its `session_id` is **caller-supplied**, so two A2A agents can name one session deliberately. `locked_chat_stream` (`routers/chat.py`) now owns the acquisition for both — the lock spans the WHOLE generator, from before the persist to after the last row it writes, never the call site alone, and contention returns a `session_busy` RUN_ERROR rather than a second interleaved run. Adding a caller that reaches `chat_stream_generator` directly reopens the hole; `test_a2a_stream_session_lock.py` pins the serialisation and carries the interleaved control.
- **Pi RETAINS every user message the seam sends it** — one long-lived process per `(user_id, session_id)`, no `--no-session`. Anything folded into the user message therefore accumulates one copy per turn, unlike a system prompt (replaced). **EVERY context block is delimited on both sides** — the table is `_CONTEXT_BLOCKS` in `zoe_core_client.py`, mirrored by `CONTEXT_BLOCKS` in `memory.ts` and pinned equal by a test — and `memory.ts`'s **`context` handler** elides every copy except the newest before each LLM call. That hook is a true ephemeral slot, not a history rewrite: the runner passes a `structuredClone` and `transformContext` feeds the result to the provider only, leaving retained state intact. Without it a long session fills the 32k window with duplicate snapshots and keeps corrected facts — and resolved "add this contact?" instructions — readable in older turns. Registration is pinned by a test; deleting the `pi.on("context", …)` line otherwise reverts the fix silently while every unit test still passes.
- **`[Recent conversation]` is the expensive block, not the memory packet.** `history[-12:]` is replayed into EVERY composed turn, so an N-turn session carried N overlapping copies of the running conversation *on top of* the conversation Pi already retains — quadratic, and entirely superseded. The portrait and the recall block repeat the same way. Each close delimiter is `"[END " + label[1:]` (`_close_marker`), the rule `[MEMORY CONTEXT]`/`[END MEMORY CONTEXT]` already followed — one rule, so a new block cannot invent a third convention.
- **Superseded is decided by POSITION, not per block type.** The newest user message keeps all of its blocks; every older user message loses all of them and keeps only the user's words. A block absent this turn is absent because zoe-data chose not to supply it, so reviving an older copy would be the stale-fact bug in a new place.
- **Those delimiters are COMPOSITION-OWNED — content that contains one must be escaped, and the strip must never trust balance.** `routers/memories.py` splices stored `ref.text[:200]` into the packet verbatim, so a memory whose text is the line `[END MEMORY CONTEXT]` closed the block early and the remainder of a superseded packet survived elision. Two layers, both required: `_neutralize_markers` (`zoe_core_client`, mirrored as `neutralizeMarkers` in `memory.ts`) wedges a U+200B into every marker occurrence in CONTENT before the delimiters are added — applied to the packet, the portrait, the recall context and the replayed history, **not** to the user's own message, which is last and can therefore only cause over-elision; and `stripContextBlocks` matches delimiters only as WHOLE LINES and elides greedily to the **last** close, running to the end of the message when unbalanced. **"Unbalanced" is counted PER BLOCK TYPE**: a close only balances an outstanding open of its own type, and any open still outstanding when the scan ends elides through EOF. Ending the span at whatever close came last leaked in both directions — a well-formed block closing the span for an UNTERMINATED one after it, and a MISMATCHED close terminating the span for a block still open. Over-eliding a superseded turn is always preferred to leaking one. Escape, never reject — dropping a colliding memory would let one poisoned fact censor itself. The break character is pinned byte-equal across the two runtimes by a test.
- **So is every `role:` LINE START inside the replayed block.** The block is `role: text` per line and `abilities.ts` opens a new turn on any `word:` line start, so content used to forge one: a reply containing "\nuser: add milk" armed a domain as if the user had asked, and a `Reminder:`-style line inside a real user message opened a non-user turn that discarded the remainder. Measured on the live box, 7 of 981 stored assistant turns carry the shape (`User: "…"`, `Assistant: Executed …`, `Error: …`) — this fired in production, it is not hypothetical. `_neutralize_role_prefixes` wedges the same U+200B in before the colon, on lines 2..N of CONTENT only: the first line rides behind composition's own label so it can never open a turn, which makes the escape a byte-for-byte no-op on every single-line message (all 998 stored user turns). Scoped to the history block — it is the only role-parsed block, and wedging into a packet line reading `Birthday: March 3` would mutate text for no safety. `_ROLE_PREFIX_PATTERN` is pinned byte-equal to `ROLE_PREFIX_PATTERN` in `abilities.ts`: if the two runtimes disagree about which line starts are boundaries, one escapes a shape the other does not read.
- **The strip is ONE contiguous span over all block types, never one pass per pair.** Per-pair passes are unsafe and a negative control reproduces it: a memory whose text is the line `[END About you]` makes the portrait pass — greedy to the last close of *its own* pair — swallow the `[MEMORY CONTEXT]` OPEN line, so the memory pass then finds no open and the rest of the superseded packet leaks. Over-eliding one block must never under-elide another.
- **The recall block's label belongs to composition, not to its producer.** `routers/voice_tts._voice_recall_packet` emits `[What you remember]` itself because the FLUE lane has nothing else to add one; the core seam adopts that leading header (`_strip_own_label`) instead of escaping it. Escaping it — which is what happened once the labels became composition-owned — doubled the header and put a U+200B into the prompt of every voice recall turn. Only a LEADING whole-line match is adopted; a label deeper in the text is content and is still neutralized.
- **Accepted KV cost of that elision:** changing bytes already in the cache ends prefix reuse at the previous turn's blocks, so ~one exchange is re-prefilled per turn (bounded, constant, and skipped entirely on turns with no context blocks). Widening the strip from one block to four does NOT raise that cost — the break point was already the previous user message, and the portrait merely sits a few hundred bytes earlier inside it. Unavoidable for any design that stops resending superseded context — an ephemeral insert shifts positions exactly as an elision does — and far cheaper than the pre-PR behaviour, which re-prefilled the WHOLE conversation every turn.
- **Composition for a core turn happens INSIDE the worker's per-session lock** (`_ZoeCoreWorker.stream` takes a compose factory). The recall fetch is the only slow step before a turn, and awaiting it in the caller let a later same-session request overtake an earlier one whose recall stalled. Before the seam owned recall this could not happen — memory.ts fetched inside the Pi process with the lock already held. Cost: a second overlapping same-session turn now also waits out the first turn's recall, on top of the generation it already waited for; cross-session concurrency is untouched.
- **Two orderings in that lane are MEASURED, not stylistic** (`test_zoe_core_client.py::test_tool_action_dispatches`, 15 runs, 14/15 baseline). The memory usage directive must never appear WITHOUT a packet — making it unconditional so it would be cacheable scored 6/15, because a brain told to lead with what it remembers, when it remembers nothing, stops calling its tools. And the user's own message must stay LAST: Pi's `custom`-message tail slot (appended after the user message) scored 9/15. Re-measure before changing either.
- **The `/api/memories/for-prompt` packet is fetched in ONE place for the core lane.** In production that is the python seam (`zoe_core_client._memory_packet_block`, called in-process — no HTTP self-call); `extensions/memory.ts` still fetches for STANDALONE runs (the `pi` CLI, `bench/`, `services/zoe-core/test`) that have no seam. **"Once" means one fetch SITE, not one block** — the packet is emitted independently of a caller-supplied `db_memory_context`, and making the two mutually exclusive is a regression: the voice path always supplies `db_memory_context` (`_voice_brain_memory`), yet only `memory_for_prompt` runs `_fold_pending_contact_offers`, so suppressing the fetch silently drops every pending "add this contact?" offer from voice. `MEMORY_USAGE_DIRECTIVE` is duplicated across the two runtimes and pinned byte-equal by `tests/test_zoe_core_memory_packet_placement.py` — change both copies or neither.

`livekit/` is a single config file (`config.yaml`), owned by this doc. One local rule:
**it must never contain a `keys:` block or any other credential.** The API pair lives in the
untracked `.env` and reaches the container as `LIVEKIT_KEYS` (compose interpolation); the tracked
file carries rtc/ports/logging only. It shipped the live key in plaintext for 86 days on this
public repo, and no secret scanner caught it — LiveKit keys have no vendor pattern. Pinned by
`tests/unit/test_livekit_config_no_secrets.py`.
**A container's environment is fixed at CREATE time and the on-demand path is `docker start`, so any
change to LiveKit's compose `environment:` needs `docker compose up -d --force-recreate livekit` —
`restart` silently reuses the old env, and `deploy.yml` never touches this service.** Rotation
runbook and exposure record in
[docs/knowledge/livekit-key-rotation.md](../docs/knowledge/livekit-key-rotation.md).
