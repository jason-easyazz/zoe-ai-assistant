# services/zoe-data/routers/ — API routers

## Purpose

FastAPI routers for every Zoe API domain: chat, calendar, lists, memories, reminders, notifications, push, voice, weather, skybridge, system, and more.

## Ownership

- `chat.py` — THE ONLY production chat router (intent fast path + agent path via `intent_router`, `ag_ui_stream`; it still CONTAINS the explicit OpenClaw lane (`openclaw_ws`) and the Hermes lanes, but those are retirement targets per the 2026-07-22 decision — do not extend them; Hermes provider mechanics moved to `../chat_hermes_stream.py` (W4-C3), re-exported here). CRITICAL FILE.
- `system.py` — system/status endpoints. CRITICAL FILE.
- `panel_config.py` — per-panel config (`GET`/`PUT /api/panels/{device_id}/config`): the panel's room, its default speaker, and its pinned dock controls. Storage is the `panels` row (`location` + `default_player` + `pinned`), keyed by `panel_id` == the panel's `device_id`. Also serves `GET /api/panels/{device_id}/sleep-gate` — whether the kiosk should stay awake because its room looks occupied. Auth (2026-10-18): both GETs need a member or THE PANEL (`panel_principal.require_member_or_panel`, the `/api/ha/*` rule: they carry live HA state, and sleep-gate is presence); `PUT /config` needs a MEMBER (`panel_principal.require_member`); `/push-status` stays open (a count). Pinned by `../tests/test_house_state_routes_auth.py`.
- `rooms.py` — Zoe-owned rooms (`/api/rooms`): create a room, put devices in it. Storage is `rooms` + `room_devices` (alembic 0026), plus `panels.room_id`. GETs need a member or the panel (`require_member_or_panel`: every device carries its live HA state); every write needs a MEMBER (`require_member`: a rename/delete/re-stock re-targets "the light in here"; it refuses any principal carrying `device_token_role`/`panel_id`, so even the `ZOE_DEVICE_TOKEN_BINDS_MEMBER` rollback's member-role device token cannot write). Never `Depends(get_current_user)` alone for either - it resolves an anonymous LAN caller to `guest`. Pinned by `../tests/test_house_state_routes_auth.py`.
- `ha_control.py` — `/api/ha/control`, `/api/ha/entities`, `/api/ha/state/{entity_id}`: a signed-in MEMBER or THE PANEL only (`panel_principal.may_control_home`), never an anonymous LAN guest - the reads too (HA state is presence, locks, cameras). `/state` refuses anything that is not a `domain.object_id`. `skybridge.py /resolve` applies the same rule to a `smart_home` intent before resolving. `ZOE_HA_CONTROL_SCOPE=open` is the operator rollback. Pinned by `../tests/test_ha_control_auth.py`.
- `panel_kiosk.py` — the kiosk credential (panel-remote-access design 4.2; mechanics in `../panel_kiosk_credential.py`). `POST /api/panels/{panel_id}/kiosk-ticket` needs `X-Device-Token` for THAT panel and an active row -> a single-use 60 s ticket; `POST /api/panels/kiosk-enter` (form body, a cross-site top-level POST from the panel's `http://127.0.0.1` gate by design - the ticket is the credential) spends it, re-checks the token and the row, sets `zoe_panel_kiosk` (HttpOnly, Secure, SameSite=Strict, host-only) and 303s to a same-origin `/touch/` path only (open redirects are refused). A bad ticket still lands on the estate as a plain guest kiosk, logged. Both 404 while `ZOE_PANEL_KIOSK_CREDENTIAL` is off and 403 over the Cloudflare tunnel. `skybridge.py`'s display identity accepts the credential for its own `panel_id`, and its address check uses `panel_principal.trusted_client_ip` (never a raw `X-Real-IP`: :8000 answers on the LAN). Pinned by `tests/test_panel_kiosk_credential.py` + `tests/test_skybridge_status.py`.
- `panel_provision.py` — first-boot pairing (`/api/panels/provision/*`). **`/confirm` requires a real member SESSION** (`_require_member_session`: no `X-Session-ID` → 401, degraded auth → 503, guest → 403) — never `Depends(get_current_user)` alone, which resolves an anonymous caller to guest and let any LAN device pair a panel. **The status poll releases the device token only to the device that started the attempt**: `/request` returns a `poll_secret` (sha256 in `panel_provision_codes.poll_secret_hash`, alembic 0029) that the poll must send as `X-Provision-Secret`; an uncollected token is revoked after `ZOE_PROVISION_PICKUP_GRACE_S`. Codes come from `secrets`. **Schema is Alembic-only**: the live DB never had the table (0005 did not land there; 0029's first deploy failed on a bare ALTER), so 0029 re-asserts 0005's table + indexes with `IF NOT EXISTS` before adding the column, and its downgrade drops only the column. Never create this table at request time. The minted device token follows the lifecycle in `panel_auth.py` (expiry from `new_token_expiry`, no scopes) and its INSERT names `name` (NOT NULL, no default - live Postgres refused every pairing until 2026-10-18); the test schema is the real column contract. Pinned by `tests/test_panel_provision_auth.py` + `tests/test_migration_0029_missing_table.py`.
- `music_setup.py` — the QR→phone "connect a music source" flow (`/api/music/setup/*`). Panel `/start` is auth-gated (owner action) + mints a one-time token/QR; phone endpoints are gated ONLY by that token. **The token never rides in a query string** (nginx logs them): the phone link keeps it in the `#fragment`, phone GETs send `X-Setup-Token`, POSTs carry it in the body, and the panel's QR image is `GET /qr/{handle}` — an opaque single-use handle (consumed on the first image fetch; the touch card renews once via `/start` on image error) from `setup_qr.py` (`music_setup.qr_path()` / `smart_home_setup.qr_path()`), never `?token=`. `smart_home_setup.py` (`/api/home/setup/*`) follows the same rule. ## Local Contracts

- NEVER create `chat_v2.py`, `chat_new.py`, `chat_optimized.py`, or any parallel chat router. Use git branches, not file duplication.
- No hardcoded NLU command detection (if "add" in message and "shopping" in message...) in `chat.py` or any router; natural-language understanding goes through `intent_router.py` patterns or Zoe Agent. (Hermes/OpenClaw are retirement targets — never new destinations.)
- Validate user input at the API boundary; parameterized queries only.
- Routers hold domain policy; reusable mechanics (provider calls, parsing, payload transforms) belong in service-layer helpers, not duplicated across routers.
- **`Depends(get_current_user)` RESOLVES a principal; it does not ENFORCE one** — a credential-less request comes back as `guest`, so a route depending on it alone is open to any LAN client. Wrapping it in a bare `try/except Exception` is worse: it also swallows the 401 raised for an INVALID or EXPIRED session, making a bad credential indistinguishable from none. Use `require_admin` / `require_signed_in`, or the voice routers' own gates.
  - `voice_tts._require_voice_auth` — device token OR a signed-in non-guest session. The default for every voice endpoint.
  - `_require_livekit_auth` — the same, PLUS a validated guest SESSION, for `GET /livekit-token` only. The estate kiosk has no device token and boots as a guest (`/api/auth/guest`), so anything stricter breaks the panel's Talk button; the header, not the resolved role, is what separates a real guest session from a credential-less request. It closes the anonymous path — a `roomJoin` grant for `zoe-voice` must never be mintable by an unauthenticated caller — but it does not make the room private while `/api/auth/guest` is open. Tighten it to `_require_voice_auth` once the kiosk browser carries a device token.
  - `voice_livekit._require_livekit_media_auth` — the same, PLUS a validated guest SESSION, for `POST /livekit-audio` + `/livekit-cancel`. Those run the full STT → brain → TTS pipeline, so anonymous access is free Jetson compute plus a brain turn attributed to `guest`. The kiosk has no device token and boots as a guest (`/api/auth/guest`), so anything stricter breaks the panel's voice turn; the header PRESENCE, not the resolved role, separates a real guest session from a credential-less request. The brain turn's user is always the server-resolved principal, never a request field. Pinned by `../tests/test_livekit_media_authz.py`.
  - **Device-token lifecycle (`panel_auth.py`, 2026-10-18).** A NEW token expires `ZOE_DEVICE_TOKEN_TTL_DAYS` (default 365, `0` = none, per call) after minting; a NULL `expires_at` never expires (no live panel is forced off); an unreadable one refuses the token. `POST /api/panels/device-token/renew` lets the holder push ITS OWN token's expiry forward IN PLACE (one token is shared by every process on the panel, so never rotate it); it never shortens one and never adds one to a no-expiry token. `issue_token` refuses an admin role and any `scopes` (never enforced: a device token is the panel principal whatever it says; the column stays, unread). Even the `ZOE_DEVICE_TOKEN_BINDS_MEMBER` rollback resolves a token to `member`, never `admin`. Pinned by `../tests/test_device_token_lifecycle.py`.
  - **A device token authenticates the DEVICE, never a person.** `voice_tts._validate_device_token` hardcodes `user_id="voice-daemon"` — an authorisation fact, not an attribution one. `auth.get_current_user` resolves the same raw token to the PANEL principal (guest + `panel_id`, `panel_auth._resolve_device_token_user`) - never the panel's `panel_user_bindings` owner since 2026-10-17 (that made the token on the panel's disk a member credential, and an `admin`-role token an admin one; `ZOE_DEVICE_TOKEN_BINDS_MEMBER=1` is the rollback only, pinned by `../tests/test_device_token_principal.py`); the declared owner is NOT a voice identity on any voice lane (`voice_command`, `/ambient`, `/livekit-audio` + `/livekit-cancel`): the acting member comes only from the freshness rule two bullets down, and with no fresh source the turn is a guest sentinel (`guest` on `voice_command`, the device id `voice-daemon` on the LiveKit lane) — never the declared owner, and never the shared `guest` principal on the LiveKit lane.
  - **The SERVER decides a voice lane's panel and member, never the device's payload (relay blocker, 2026-10-18).** `voice_tts._lane_panel_id` is the panel on every lane (`/transcribe`, `/command`, `/turn`, `/turn_stream`, `/wake`, `/ambient`, `/enroll`): a device token's OWN panel (a payload naming another is overridden + logged; only a `replay-` instrument id may narrow it, on the LAN), the internal PIN replay's panel, or - for a member's own session - the payload id for display only. A raw `identified_user_id` counts ONLY on the internal PIN replay (`caller.source == "pin_resume"`, `panel_auth.submit_pin`); over HTTP it is ignored and logged. A member's own session is that member and never inherits the fresh member of a panel it names (`_resolve_fresh_panel_member` runs for panel callers only). Over the relay (`_request_via_relay` -> `relay_ingress.is_relay`, #2095; absent module = no relay, a raising check = relayed) the panel's own speaker claim is refused (`_accept_panel_voice_claim`: the score is the panel's word), as are `/enroll`, `/adapt` and `/api/face/enroll` (403): a member there comes only from a fresh PIN / voice session the server issued. Pinned by `../tests/test_voice_path_identity.py` (negative-controlled). Voice-path change -> replay-gated.
  - **A guest sentinel is the ABSENCE of an identity — never cache or compare it as one.** `""`, `guest`, `voice-guest`, `voice-daemon` (`voice_tts._GUEST_SENTINEL_USERS`) are all TRUTHY strings, so any of them parked in an identity slot wins every `or`-chain and passes every `bool()` check. That is not a style point: it made a real panel login invisible to voice for a whole session (2026-08-10). `_VOICE_SESSIONS[panel]["bound_user_id"]` was stamped `"guest"` while nobody was signed in, survived every session rollover, out-ranked the freshly-logged-in `panel_recent`/`panel_default`, and blocked its own `if not _bound_user` refresh — so the voice lane kept re-challenging a signed-in user. The same truthiness let a guest SATISFY `_has_scope_identity` and walk through the `user_scoped` gates. Normalise at every store/read boundary with `voice_tts._real_user_or_none`; absent identity must be `None`. Pinned by `../tests/test_voice_panel_binding_sentinel.py`.
  - **A voice turn's member identity never outlives its source (privacy, 2026-10-13, default on).** In `voice_tts.voice_command` a member identity comes ONLY from THIS turn's identification (an accepted voice claim, or `identified_user_id` on the internal PIN replay - never a payload field, see "The SERVER decides" above), a FRESH PIN panel session (`_resolve_fresh_panel_member` → `_resolve_recent_panel_session_user` — the panel idle-logout window is the expiry authority; do not add a second TTL), or the caller's own signed-in member session — plus, with `ZOE_VOICE_SESSION` on, the panel's OPEN, unexpired voice session (next bullet), which only ever names the member this turn's own verified voice claims and closes on any other voice. Anything else is `guest`. `_VOICE_SESSIONS[panel]["bound_user_id"]` only MIRRORS the fresh session — rewritten every turn, cleared when it lapses — and a voice claim never writes it. The panel's LAST signed-in member (the retired `_resolve_panel_default_user` — do not reintroduce it) and the operator-declared `panel_user_bindings` owner are NOT voice identities, and the public `calendar_show` / `list_show` shortcut runs as the same fresh identity. Before this, one PIN or one claim bound the panel to that member until a restart and every later voice read their data. Pinned by `../tests/test_voice_identity_freshness.py` (each case negative-controlled). Voice-path change → replay-gated.
    - **One resolver, every lane (2026-10-14).** `voice_tts._resolve_fresh_panel_member` is the ONLY way a voice-shaped lane learns a panel's member (`voice_command`, the wake prewarm, `voice_livekit._require_livekit_media_auth` for a device token); `voice_tts._accepted_voice_claim` is the only claim gate (threshold + live consent). Do not open-code a third copy.
    - **The wake prewarm runs on EVERY wake - identity only scopes its member half (2026-10-14).** `voice_tts._prewarm_brain_for_panel` once `return`ed when no fresh member resolved, so after strict identity (#2034) an idle panel's first turn paid the cold ~2.7k-token system+tools prefill (`FLUE_PROMPT_CACHE first_cache_n=0`, TTFT ~4.8 s vs ~1.1-1.7 s). The live Flue lane's prefix is the same bytes for every user and session (the member's words, memory, persona and identity ride the user message behind it), so `zoe_flue_client.warm_kv_prefix` primes llama-server's one slot with a throwaway turn run as an EXPLICIT guest (` zoe-uid:guest` envelope + a fixed instruction, nothing else: a turn with NO envelope is not anonymous - the sidecar falls back to its own `ZOE_BRAIN_USER_ID`, fetches that member's user-model card into the system prompt and lets tools act as them, measured offline; the guest envelope gives a prefix byte-identical to a real guest turn's). The turn runs on a `kvwarm-*` session reused for 8 warms then rotated (Flue persists every turn and never deletes; a failed warm rotates at once), skipped while `brain_slot_guard` says the slot is hot, and a warm that misses its 10 s deadline is ABORTED through the guarded `/abort` route (the request opts in with `x-zoe-abort-on-cancel`) rather than left decoding in the one slot (`ZOE_BRAIN_KV_WARM_ON_WAKE`, default on). Only the member's facts cache is member-scoped, and a guest's core worker key is `guest` (what `effective_user` gives a guest turn). The old core (Pi) worker prewarm never touched the KV (the 06:03 wake warmed it and the turn still logged `first_cache_n=0`), so it is spawned only when the core lane can serve (not on the Flue lane unless `ZOE_BRAIN_FAILOVER`). A wake never refreshes a PIN or voice session. Pinned by `../tests/test_wake_prewarm_guest.py`.
    - **Only a turn that identifies ITSELF as the member extends the member's session.** `voice_command` refreshes the `ui_panel_sessions` heartbeat (`_touch_panel_session`, #1349) only when `_turn_own_identity(caller, identified_user_id)` (an accepted claim, the PIN replay, the member's own session) equals the fresh session's member. An unidentified voice USES a fresh session but never extends it, another member's claim neither extends nor rewrites it, and the LiveKit lane never heartbeats. The touch PIN flow (`panel_auth.submit_pin`) is unchanged. Pinned by section 7 of `../tests/test_voice_identity_freshness.py`.
    - **Ambient room audio is filed only under its OWN speaker, else not at all.** `POST /api/voice/ambient` files a segment under `_turn_own_identity(caller, _accepted_voice_claim(...))` — a claim that passes the server gate, or the caller's own signed-in session. A panel's member (fresh PIN session, last sign-in, declared owner) is never the speaker of overheard room speech, and `guest` is a scope every guest session's `ambient_search` reads, so an unidentified segment is neither transcribed nor stored (P-F4: never ownerless). A bare `identified_user_id` passed no server gate and is not an identification here. Pinned by `../tests/test_ambient_memory_scoping.py`.
  - **With `ZOE_VOICE_SESSION` on, a panel device's SPOKEN turn takes its member scope from the voice, not from `bound_user_id`.** `voice_session.observe_turn` (`../voice_session.py`) returns the verified member while that panel's TTL'd voice session is open (model-gated, closed by any other voice), else the panel's FRESH PIN sign-in, else nobody; the turn's step-up actions still go through the PIN challenge. Off, the freshness chain above stands (no voice session is ever a source). Record: `docs/knowledge/voice-verified-session.md`.
  - **Header PRESENCE only substitutes for "validated" while the header was actually validated.** Under `ZOE_AUTH_FAIL_CLOSED=false` an auth-service outage resolves ANY nonblank `X-Session-ID` to a plain guest, so a presence check alone re-opens the endpoint to anonymous callers for the length of the outage. `auth.get_current_user` marks that principal `auth_degraded: True` (the private `__zoe_degraded__` flag never leaves `auth.py`); any gate that reads presence as proof MUST refuse it — 503, matching the fail-closed default. A device token is unaffected: it never depended on zoe-auth.
  - The LiveKit participant identity and room come from the server-resolved principal, never from a request argument. Pinned by `../tests/test_livekit_token_authz.py`. The room lane's client-asserted `identify` data message may only CONFIRM that minted identity (a member's own session); naming anyone else leaves the participant `guest` (`voice_livekit._build_room_handlers`, pinned in `../tests/test_livekit_media_authz.py`).
  - The idiom is currently duplicated between `voice_tts.py` and `voice_livekit.py` (different modules, landed separately). Consolidate to one shared helper once both are on `main` — do not add a THIRD copy in the meantime.
- **Panel-facing flows are voice → touch → phone handoff; nothing on the panel needs a keyboard** (`docs/VISION.md` principle 8). A router serving a new touch surface must not require typed input from the panel beyond the PIN (sign-in / identity step-up) and short search; credentials, long text, forms and codes are collected by a phone-side endpoint reached through a QR or a Telegram "send to my phone" link.
- **App/account connections go through `auth_handoff` + `routers/handoff.py`, and the panel learns completion by push.** A new kind registers a phone-link minter in `auth_handoff._KINDS`, adds its policy to `handoff_start`, and has its phone endpoints report by token nonce (`mark_ref` / `complete_ref`, or hand `auth_handoff.reporter(...)` to a background task via that flow's `watch()`). Do not add another QR/status/panel-push mechanism, and never persist, broadcast or return the token-bearing phone URL. Status is forward-only; `done` and expiry are final. Not about the panel PIN.
- **Panel-scoped settings live in ONE place per concern — do not add a second store.** `panels.location` is THE panel location (it predates `panel_config.py`); `display_preferences` (`system.py`) stays the *display* store (brightness/idle/off). A new panel-scoped fact goes in the `panels` row.
- `panel_config.py` invariants (each is load-bearing and non-obvious — a "cleanup" that flattens one reintroduces a shipped bug):
  - **A pin is a read/write PAIR.** The thermostat is two entities (`sensor.current_temperature` read + `input_number.thermostat_temperature` write); a single `entity_id` cannot express it. The `{entity_id}` input form is sugar that canonicalises to an equal pair — the response is ALWAYS the pair.
  - **Never validate `entity_id` against a domain allow-list.** This house has zero `light.*`/`climate.*`; its controls are `input_boolean.*`/`input_number.*`/`scene.*`. Shape (`domain.object_id`) only.
  - **`kind` and `icon` resolve server-side, never from the domain.** `input_boolean.fan`/`.tv` share the lights' domain; HA's own `attributes.icon` is the truth.
  - **`pinned` NULL != `[]`.** NULL = never configured (dock falls back to its own default); `[]` = the operator explicitly pinned nothing. `pins_configured` carries the distinction.
  - **An empty MA player list means "cannot validate", not "no players".** `music_service._ma` never raises — it returns None on transport failure, which `get_players()` turns into `[]`. Treating `[]` as an empty set rejects every id and locks the operator out during an MA outage.
  - **The sleep gate FAILS TOWARD SLEEPING.** `GET /{device_id}/sleep-gate` answers "is this panel's room occupied" from the room's own toggles (`light`/`switch`/`input_boolean` = `on`), resolved via `rooms.room_entity_ids_for_panel` — there is NO presence sensor in this house (44 HA entities, zero `binary_sensor`), so do not "improve" this to look for one. Every unknown (HA unreachable, panel in no room, stale entity) returns `block: false`, i.e. SLEEP: a panel that latches awake because a lookup failed burns its screen all night. Readings (`sensor`/`input_number`) are never occupancy. The client races this against the music check with a timeout that decides on the votes ALREADY RECEIVED — a hard `false` there would discard a "music is playing" vote and sleep mid-song.
  - **PUT writes ONLY the columns the request supplied** (`ON CONFLICT DO UPDATE SET` built from the fixed `_WRITABLE` whitelist, never from body keys) and returns the post-write row via `RETURNING`. Do not "simplify" this back to a read-merge-write that always writes all three columns — concurrent PUTs of different fields would clobber each other.
- `rooms.py` invariants — **a room is a ZOE record, not a mirror of Home Assistant.** Zoe is the product; HA is an organ she hides for a normal user and opens for a power user, so a room must be creatable with no HA involvement at all.
  - **`ha_area_id` is OPTIONAL enrichment, never the source of truth.** NULL is a completely normal room, not an unconfigured one. It exists so a power user who already keeps HA areas can link one (and later import its devices); nothing may start requiring it.
  - **A device is in exactly ONE room** — `room_devices.entity_id` is UNIQUE across the whole table, not per-room. "The light in HERE" needs a single non-arbitrary answer. Consequently linking a device that already sits in another room MOVES it (the writer deletes the old row first); a plain INSERT would 500 on an ordinary move, and rejecting it would make the user hunt for its previous room.
  - **Never validate `entity_id` against a domain allow-list** — the same rule `panel_config.py` carries, for the same reason (this house has zero `light.*`).
  - **A device HA does not return is KEPT and marked `available:false`, never dropped** — the opposite of a stale *pin*. A pin that cannot resolve is unrenderable, but a room membership is the user's own record and must outlive HA's current view of it, or an HA blip silently empties their rooms.
  - **`slug` is not re-derived on rename.** It is the stable key a panel or intent points at; rotating it on a rename would silently unbind them.
  - **`GET /unassigned` filters to `_PICKABLE_DOMAINS`; storage does NOT.** The picker is a suggestion list, so it hides the diagnostic noise (this house exposes 48 entities — `event.backup_automatic_backup`, every `sensor.backup_*`, the assist-satellite plumbing — and offering those made it unusable). `normalize_entity_id` stays shape-only, so anything remains storable by an importer or a power user with an odd device. Narrowing storage to the picker's list would be the domain allow-list this file forbids twice over.
  - **A panel's room is `panels.room_id`, written through `PUT /api/panels/{id}/config`** (whitelisted in `panel_config._WRITABLE`). `panels.location` is the older free-text label and is deliberately NOT mirrored — nothing reads it for behaviour, so syncing them would be a dual-write with no consumer. `room_id` is authoritative; the config payload carries `room_id`/`room_name`/`room_slug` flat.
  - **A deleted room degrades a panel to "no room", never an error.** `_load_room` returns None for a dangling id, because a panel that cannot boot its own config over a room someone deleted is worse than one that reports having no room.
  - Rooms are the eventual replacement for `smart_home_service._room_of()` name-parsing (which cannot see a device like `switch.bedroom_1_switch_1`), but that path is still live — do not delete it until the Rooms surface and `_group_rooms()` read this model.
  - **Room CRUD is API-only by design today — the chat/voice intent path is DEFERRED, not forgotten** (`.greptile` `chat-voice-first`, the same deferral the music-grouping entry below carries). Nothing is user-visible yet: no surface consumes these endpoints, so there is no feature to operate by voice. The sequencing is deliberate — the settings UI comes first, then voice *uses* rooms to resolve "the light in here" (voice-path work, so it must be replay-gated). Speaking room ADMIN ("create a room called Bedroom") is a separate, weaker case and is not planned: naming a room and assigning devices to it is fiddly configuration rather than a glance-and-speak action, and a mis-heard name creates a duplicate room the user then has to hunt down. `GET /api/rooms` is unauthenticated precisely so an integration or the kiosk can already read the resolved state without one.
- **Every answered panel voice turn broadcasts `voice:transcript` → `voice:responding` → `voice:done`** (push channel `all`, `panel_id` in the payload). The kiosk's text for a brain/chat turn arrives ONLY this way — nothing is queued for the 2 s ui_actions poll — so a `/turn_stream` early return (the "let's talk" opener/ender fast path) must broadcast them itself (`conversation_opener.broadcast_conversation_turn`), with `conversation_mode` / `conversation_end` on both events so the estate holds the text for the life of the conversation. Inside a speculative turn (B1.1) that push is deferred to the verdict and dropped on cancel, like any other side effect. Pinned by `../tests/test_conversation_fast_path_ui.py`. Voice-path change → replay-gated.
- **A conversational turn's Skybridge call must carry the router verdict.** `voice_tts.voice_command` passes its `_router_decision` (`router_decision=`) and the `/ws/voice/` lane (`main._resolve_voice_cards`) passes `ROUTE_ON_DEMAND`, so the fast path can be VETOED when the two-stage router says `chat` (flag `ZOE_SKYBRIDGE_ROUTER_VETO`, default on; contract + reasons in `../AGENTS.md`). When the STT snap rewrites a turn's words (`stt_snap`, `ZOE_STT_SNAP=on`: an acted snap, or a "yes" to its "Did you mean ...?"), `_router_decision` is recomputed on the SNAPPED words (`stt_snap.route_for`) so the veto judges what will actually run. A vetoed result is `handled: False` and the caller must fall through exactly as for an unclassified utterance — never answer from it, never raise a PIN challenge for it. Touch/tap endpoints (`routers/skybridge.py` `/resolve`) stay ungated: a tapped button is an explicit command. Voice-path change → replay-gated.
- Per-panel `default_player` OVERRIDES the household-global `/api/music/preferred-player`, which remains the fallback and an unchanged public contract.
- **`GET /api/music/players` resolves device TYPE server-side** via the pure helper `music.py::resolve_player_kind(player)` — the panel gets flat `kind` (`speaker`|`tv`|`display`|`group`|`computer`) + `kind_label` fields alongside the raw player, and never parses a vendor model string (the same flat-resolved-fields doctrine as `panel_config.py`'s dock pins). MA's own `icon` is useless here (`mdi-speaker` for almost everything); derive from `type`+`provider`+`device_info.model` ONLY, never the user-editable `name`. There is deliberately no `airplay` kind — AirPlay is a transport, not a form factor, and every AirPlay device here is an Apple TV (→`tv`) or a Mac (→`computer`). This exists so the panel can tell the two identically-named **"Bedroom"** players apart (a live Sonos Beam → speaker/"Sonos Beam" vs a dead AirPlay Apple TV → tv/"Apple TV", `available:false`). Keep the resolver pure + unit-tested (`tests/test_music_player_kind.py`, `ci_safe`, fixtures matched against live) — do not inline the mapping into a test.
- `music.py` multi-room grouping (`GET /groups`, `POST /group`, `POST /ungroup`) is **additive to `/transfer`, never a replacement**: transfer MOVES playback to one speaker, grouping SPREADS it across several. Both stay.
  - **The panel never re-derives grouping from MA's payload.** MA spreads it over five fields with non-obvious semantics, so `music_service.build_group_view()` resolves them into flat fields (`role`, `leader_id`, `group_member_ids`, `can_group_with`, `name`). Read the field notes above `build_group_view` before touching it — each was verified against MA 2.8.7 source, not guessed:
    - a sync **leader**'s `group_members` includes its OWN id FIRST; a `type=="group"` player's does NOT include itself;
    - `synced_to` (sync member) and `active_group` (permanent-group member) both mark a FOLLOWER, and `active_group` wins — the group player owns the queue;
    - `static_group_members` non-empty = provider-FIXED membership (the Chromecast "House" group): not editable, so never offer a member picker for it;
    - `can_group_with` has TWO documented shapes — player ids, or a single provider instance_id meaning "all of that provider's players".
  - **`/group` and `/ungroup` are deliberately separate.** Unjoin is not "group with an empty add": the caller does not know which target to remove FROM, and it differs by topology (sync member → its leader, permanent member → its group player, leader → dissolves the group). MA's `players/cmd/ungroup` owns that; don't re-derive it.
  - **An empty MA player list means "cannot validate", not "no players"** — the same rule as `panel_config.py` above. `group_players()` only rejects unknown ids when it could actually SEE the list; otherwise it forwards and lets MA arbitrate. Reversing this locks the operator out of their own speakers during an MA blip.
  - Unavailable players stay LISTED and stay groupable (`available: false`), so a flapping speaker never disappears from the picker.
  - **Grouping is panel-only by design today — the chat/voice intent path is DEFERRED, not forgotten** (`.greptile` `chat-voice-first`). Voice grouping needs multi-speaker name resolution that this house actively breaks: two players are both called **"Bedroom"** (a Sonos zone and an AirPlay endpoint), so "group the bedroom and the kitchen" has no unambiguous referent, and `_match_player_by_name` (`music_service.py`) returns the first name hit — fine for the existing single-target `transfer` intent, wrong for a set. Shipping voice grouping needs a disambiguation strategy (room-scoped resolution via `panels.location`, or a spoken clarifying question) first; that is its own change, and it is voice-path work that must be replay-gated. The read endpoint `GET /api/music/groups` already gives any future intent the resolved state it needs.
- **Memory hard-deletes: admin `/forget` for anyone, internal `/forget-synthetic` for test ids only.** `POST /api/memories/users/{id}/forget-synthetic` (`memories.py`) accepts ONLY a valid `X-Internal-Token` (missing 401, wrong/unprovisioned 403 — loopback and admin sessions do not qualify) and ONLY ids passing `user_filters.synthetic_forget_refusal` (harness-SHAPED `^(demo|test)_[a-z0-9]{1,16}_[0-9a-f]{6,32}$` — the exact `demo_bar_<hex>` / `demo_b08_<hex>` shapes the harnesses mint, never a bare prefix since Zoe Auth ids are usernames; case-sensitive, not a guest sentinel, not in `ZOE_SYNTHETIC_USER_ALLOWLIST`) that are NOT a registered Zoe Auth account (`_registered_account` reads `auth_users`, the account store — never zoe-data's `users` mirror, which `/api/chat` fills for every id; registered = 403 `refused_registered`, lookup failure = 409 `refused_unverified`, fail closed); anything else is 403/409 with the reason and deletes nothing. `GET /api/memories/capture-status?user_id=` (same internal-token gate) returns `memory_capture_stats` counters for the post-turn memory capture — `started`/`completed`/`failed`/`in_flight` — because `chat.py` schedules `_persist_memory_candidates` with `ensure_future` (the wrapper counts start before any early return and completion in `finally`; the impl returns True only when every memory pass ran cleanly and its swallowed exceptions are counted as `failed`, so `completed` advancing is not by itself success; the latent-suggestions writer is scheduled asynchronously but tracked as its own unit under the same per-user counters via `_tracked_suggestions`, so `in_flight == 0` means every writer of the turn has finished); it is the only way a caller can observe that a turn's extraction + digest finished, and `scripts/perf/samantha_bar.py` polls it before scoring S7. No memory content is returned. It exists so harnesses (`scripts/perf/samantha_bar.py`) can tear down without an admin credential or opening the store. Every call past the id check logs one `MEMORY_FORGET_SYNTHETIC` line with the id and outcome — `removed=<n> outcome=ok`, `refused … reason=`, or ERROR `outcome=error` when `delete_user` raises (it deletes memory rows before audit rows, so that can be a partial delete; the 400 is kept). Never widen the pattern to the batch filter's `probe|ci|e2e|bench` or make it case-insensitive — `../tests/test_memory_forget_synthetic.py` carries a loosened-pattern negative control.
