# services/zoe-data/ — production web + chat API

## Purpose

THE production Zoe API: FastAPI app served by host uvicorn on port 8000. Owns chat, intent routing, memory, MCP tools, auth integration, and background jobs. (It also still CONTAINS the OpenClaw/Hermes agent bridges, but those are retirement targets — see Local Contracts — not owned capabilities to extend.)

Both go through `router_heads_numpy.load_head()`: the default `ZOE_ROUTER_HEADS_BACKEND=numpy` serves `models/router_head_{logreg,mlp}.npz` + `.json` with pure numpy — **zoe-data never imports scikit-learn/scipy/joblib** (pinned by `tests/test_router_heads_numpy.py`, which also holds sklearn parity ≤1e-6 on a committed 50-vector corpus fixture, a negative control, and a joblib-sha drift check); `joblib` is the one-release fallback that unpickles the `.joblib` training artefacts. - Browser surface: `browser_broker.py` — plan/executor registry over ONE Zoe-native CloakBrowser surface (stealth Chromium, Playwright-compatible; `zoeCloak`, with `hermesCloak`/`harness` as execution aliases). Two output modes, and the mode is chosen by the PLAN ACTION: any action returns a base64 PNG (`image_base64`), **except** `extract_text`/`fetch_text`, which return page TEXT and deliberately skip the screenshot. Text mode is opt-in precisely so existing callers (chat.py research screenshots, the MCP browser tool) are byte-identical — pinned by `tests/test_browser_text_extract.py`. Extraction is `extract_main_text(html) -> ExtractedText`, a **pure stdlib function** (`html.parser`, no `readability`/`bs4`/`lxml` — none are declared deps here, so requirements.txt is untouched) doing readability-lite main-content selection: drop-list for `script`/`style`/`nav`/`header`/`footer`/`aside`; then the semantic shortcut over `<article>`/`<main>` containers clearing the 200-char floor — a `<main>` wrapping a qualifying `<article>` is DROPPED first (it always holds more text than the article inside it, so pure length could never pick the tighter node and the shortcut returned article + related-cards), then longest wins among the survivors. The drop is deliberately wrapper-shaped and NOT "any ancestor": `<article>` inside `<article>` is the spec's idiom for COMMENTS, and demoting the parent there would return one comment and discard the post; then container scoring by text volume discounted by **quadratic** link density plus a deepest-near-tie tie-break — linear discounting lets the outer wrapper beat the article by a hair and drags every nav/footer line in with it. Every tree walk is ITERATIVE (explicit stack, `_BLOCK_END` sentinel for the post-order newline): page depth is publisher-controlled, a recursive render raised `RecursionError` at ~1000 nested elements, and nothing on the text path catches it — pinned by `test_a_deeply_nested_page_extracts_instead_of_raising`. It reports its own `strategy` (`semantic:<article>` | `scored-container` | `fallback:whole-document` | `empty`), which is what the tests assert on. Callable three ways: the pure function (the offline test seam), `await fetch_page_text(url)` in-process, or `await execute_text_extraction(broker, url=…)` through the normal plan pipeline. Both live paths SSRF-guard via `assert_public_url` + `guard_browser_page` and return `{"ok": False, "error": …}` rather than raising, so a failed enrichment degrades a search packet instead of breaking the turn. NOT a voice-path file (verified against `voice_gate_check.VOICE_PATH_PATTERNS`) — no replay gate.

- **`flue > core > legacy` is CONFIGURED LANE SELECTION, not runtime failover.** The order is resolved once per turn from `ZOE_BRAIN_BACKEND`/`ZOE_USE_CORE_BRAIN`; with `flue` selected and `:3579` down, every brain turn is answered by `zoe_flue_client._FALLBACK_TEXT` while the healthy core lane sits unused (#1613). Bounded runtime failover lives behind `ZOE_BRAIN_FAILOVER` (default OFF — brain dispatch is a gated voice path, so the operator flips it only after the three-step gate spelled out in `.env.example`: failover suite green, head-bound replay PASS with the flag exported, live stop-the-sidecar drill read from `BRAIN_LANE`; `ZOE_BRAIN_FAILOVER_COOLDOWN_S` default 45 s). Its trigger is deliberately narrow and must stay that way: **only** `zoe_flue_client.FlueTransportError`, which the client raises **only** under the opt-in `raise_transport_errors=True` and **only** for a pre-admission connect failure with no text yielded and no 2xx admission — proof the sidecar never executed the turn. A model error, an HTTP status error, a read timeout, or an empty 200 all mean the sidecar RAN the turn: they keep the sentinel and never re-dispatch (the #1137 duplicate-write class). **An HTTP 400 from a wire-mismatched sidecar is a REFUSAL, not an unreachable host** — the sidecar answered, so it is a config error to surface, never evidence a retry is safe. **The trigger is per-ROUTE, and `ZOE_FLUE_WIRE` adds routes:** wire 2 has no `?wait=result`, so its turns run through `_run_turn_aggregated_wire2` (non-streaming) or the streaming block's own wire-2 pre-admission branch. Each needs its OWN pre-admission raise, ordered BEFORE the wire-2 sentinel return — put it after and failover is silently dead on `ZOE_FLUE_WIRE=2`, the wire the 2.x sidecar actually speaks. Classification by exception class is never sufficient on its own: every raise site is also gated on `admitted`, because a connect-class error after a 2xx looks identical to a refusal and is not one. **A turn that has streamed its first token is NEVER re-dispatched under any condition** — the panel speaks each delta, so a replay makes Zoe say the reply twice. One retry, on the next configured lane; a short-TTL in-process circuit breaker then skips the dead lane so only one turn per cooldown pays the failed connect, and the first turn past the TTL re-probes. **Turns overlap, so the breaker is concurrency-safe by construction and must stay that way:** it is a `(deadline, generation)` pair, every mutation is a compare-and-set against the generation the turn OBSERVED (`_observe_circuit` → `_open_circuit`/`_close_circuit`), and the half-open probe is claimed by exactly one turn. Never make the close unconditional — an earlier turn's success would erase a later turn's open, and two turns crossing the same lapsed TTL would both re-probe a dead sidecar. This governs only WHETHER flue is attempted; the replay and exactly-one-retry invariants above do not depend on it. Every turn logs ONE greppable `BRAIN_LANE lane_attempted=… lane_served=… outcome=…` line (ids only, never message text) in BOTH flag states — that is observability, and it is how an operator asserts which brain answered (`grep BRAIN_LANE ~/.zoe-logs/*`; this service does NOT log to journald). Three properties keep that line trustworthy rather than merely present, and all three are easy to regress. **(1) Exactly one, on every path a turn can leave by — ONE-SHOTS INCLUDED.** The streaming wrapper is an async generator, so a consumer that disconnects after the first delta throws `GeneratorExit` at the yield and skips everything after it; a one-shot has the same hole with no generator to close, because it is routinely CANCELLED (the LiveKit lane awaits it under `asyncio.wait_for`, chat disconnect cleanup cancels its task) and cancellation exits the await without reaching any terminal branch. Both shapes emit through the once-only `_LaneRecord` wrapped in `try/finally`, so an interrupted turn logs `outcome=interrupted` (`reason=caller_cancelled` / `consumer_disconnected`, read from the live exception so an unexpected error is not mislabelled a cancel) instead of vanishing. Never put the only emission after the loop or after the await. **(2) The outcome is the client's verdict, not "the generator finished", IN BOTH FLAG STATES.** `zoe_flue_client` renders an HTTP error, a read timeout, an empty 200, a rejected wire-2 body and a post-admission stream death alike as its canned sentinel and ends the stream normally, so an INFERRED label calls every one of them `ok` — success reported for exactly the failed turns the line exists to diagnose. The client reports its terminal verdict through the opt-in `outcome_sink` and the line carries it (`ok`/`fallback`/`error`). The default-OFF flue path takes the same sink (`_flue_streaming_labeled`/`_flue_oneshot_labeled`) — it is the deployment actually running, and a pre-request `outcome=dispatched` label there was identical for a healthy turn and every failure mode. Its DISPATCH is unchanged: one client call, never `raise_transport_errors` (which would let `FlueTransportError` escape into a route with nothing to catch it), no lane hop, and **no breaker state touched in either direction**, so a later flag flip still starts from a closed breaker. The core/legacy lanes keep `outcome=dispatched`: they have no verdict to report, and wrapping them would move `_drop_flue_only_kwargs`'s fail-closed raise from call time to first-iteration time. Labels only: nothing in the sink is read before a dispatch decision, so a wrong label can misinform an operator but can never re-run a turn. `outcome_sink` and `raise_transport_errors` are both dispatch-INTERNAL kwargs, stripped from caller kwargs by `_sanitize_kwargs`. **(3) Breaker state must match the EVIDENCE, not the exit path.** The half-open probe re-arms the deadline as it claims the lapse, so only the probe's own outcome closes it — and reaching `_close_circuit` after the loop is not enough, because a consumer that disconnects after the first delta skips it and leaves a demonstrably reachable sidecar in the penalty box for another full cooldown. The streaming cleanup therefore closes the breaker (CAS against the observed generation, as always) when the turn YIELDED a flue delta before unwinding. The evidence is the yield and nothing else: `served_any` is set only inside the flue loop, a consumer that cancels before the first delta proved nothing and leaves the claim armed, and a one-shot never closes from cleanup at all (it yields nothing incrementally, so a cancelled await is not evidence flue answered). Pinned by `tests/test_brain_lane_failover.py` (`ci_safe`), whose load-bearing cases are the negative ones — the replay invariant, the four non-transport failure classes, the wire-2 route parity, the interrupted-consumer and cancelled-one-shot lines, and the guard-the-guard case where a probe that yielded nothing must NOT close the breaker.

- Background loops must not fork on the event loop thread. `asyncio.create_subprocess_exec` forks synchronously on the loop; in this large multi-threaded process a fork can deadlock pre-exec and freeze the whole API (live outage 2026-06-29: one wedged `hermes kanban` spawn made every endpoint, `/health` included, time out for days). The two safe patterns are centralised in `async_subprocess.py`: `run_to_completion` (spawn+communicate+timeout+kill entirely inside a thread pool via `subprocess.run`) and `spawn_pipe_process` (off-loop `subprocess.Popen` fork+exec, then wrap the already-open pipe fds in asyncio stream transports via `connect_read_pipe`/`connect_write_pipe`, which don't fork, so the rest of the worker keeps its async stdin/stdout interface). Prefer these for any new spawn — a coroutine-side `wait_for` alone cannot fire when the loop thread itself is blocked, which is why the fork must happen off-loop. Run-to-completion sites: `executors/kanban_adapter.py`'s `_spawn_cli`, `tts_waterfall.py`'s `_spawn_tts_cli` (espeak-ng/ffmpeg TTS fallbacks), `pi_intent_classifier.py`'s print-transport governor (`run_to_completion`), and `intent_router.py`'s `_run_mcporter` (MCP fallback subprocess). Long-lived streamed sites: `pi_intent_classifier.py`'s Pi RPC governor worker (`async_subprocess.spawn_pipe_process`) and `zoe_core_client.py`'s Pi RPC brain subprocess (its own `_spawn_pi_process` — a pre-existing specialised copy of the same logic; a follow-up may migrate it onto the shared helper).
- The bash tool runs commands via argv (`create_subprocess_exec`), never a shell. Outbound fetch/browser tools and panel proxies must route through `agent_safety`: HTTP fetches use `guarded_urlopen` (IP-pinned, env proxies ignored), Playwright pages must `await guard_browser_page(page)` before any `goto` (per-hop pre-connect validation), panel hosts go through `assert_panel_host`, and panel-display navigation (e.g. `panel_browser_screenshot`) goes through `assert_panel_url` (LAN-panel-only). Don't reintroduce raw `create_subprocess_shell`, unguarded `urlopen`, or a `page.goto` on a user URL without the route guard. Validating `page.url` only AFTER `goto` is insufficient — the request was already sent.
- Every WebSocket endpoint in `main.py` (`/ws/push` and the `/api/*/ws*` channels) must call `_enforce_ws_origin(websocket)` before accept/auth to block cross-site WebSocket hijacking. Allowed origins come from `_allowed_browser_origins()` — the base `ALLOWED_ORIGINS` list plus `ZOE_ALLOWED_WS_ORIGINS` (comma-separated extra panel/kiosk hosts) — which is the single source feeding BOTH this WS guard and the HTTP `CORSMiddleware`, so an operator-added origin can't be allowed for one and rejected by the other. Policy: a present-but-unlisted Origin is rejected (close 1008 / HTTP 403); a **missing** Origin is allowed (non-browser native kiosk/voice client — browsers always send Origin on a WS handshake). Don't add a new WS endpoint without this guard.

(2) `panel_browser_screenshot` constrains the initial `navigate_to` to a LAN panel host via `assert_panel_url`, but the navigation runs in the out-of-process Hermes broker, so an allowed LAN page that redirects to loopback/metadata inside the broker is only closeable broker-side. Closing either needs CDP `Fetch.requestPaused` resolved-IP inspection or a pinning proxy in the browser/broker.

- Reminders write + fire seam (`reminder_service.py`, `routers/reminders.py`, `proactive/triggers/reminder_scan.py`): `due_date` is normalised to ISO at WRITE time by `reminder_service.normalize_due_date` (relative days via `intent_router._parse_date`; non-dates → 422) on BOTH the API and the `reminder_create` intent path the brain's `add_reminder` tool dispatches — never store the model's literal. Relative days resolve against the HOUSEHOLD clock (`reminder_scan.zoe_now`, `ZOE_TIMEZONE`), never the server's local date. `normalize_due_time` rejects non-clock times (`25:00`) with 422 on write. The scan schedules date-only rows at `ZOE_REMINDER_DEFAULT_TIME` (default 09:00 local); a date-only row for TODAY whose default time has passed fires `_SAME_DAY_GRACE_MIN` (2) minutes from now once (fired-today guard), while an explicit past due_time is still skipped; a STORED out-of-range due_time keeps firing at the default time (legacy leniency — strictness is write-side only); a legacy non-ISO due_date WARNs once per id instead of being skipped silently; recurrence is an RFC 5545 RRULE subset (`reminder_recurrence.py` — pure/stdlib, FREQ=DAILY|WEEKLY|MONTHLY|YEARLY + INTERVAL/BYDAY/BYMONTHDAY; anything else is REJECTED, never half-honoured): `reminder_service.normalize_recurrence_fields` stores `recurring_pattern` as canonical RRULE (a phrase like "every weekday" is converted; unsupported → 422) and sets `due_date` to the FIRST future occurrence, which the scan then treats as the rule's ANCHOR (never "past-due") and schedules each next occurrence; the intent path parses the recurrence phrase in code (`extract_recurrence`) BEFORE the regex/NLU slot fillers and carries it as the `recurrence` slot — the fillers never see it; a recurrence CUE it cannot turn into a supported rule ("every 53 days", "every hour", or a modifier left beside a supported one — "except friday", "until june", "for 2 weeks" — `find_unsupported_recurrence`) becomes an `unsupported_recurrence` slot the executor REFUSES in words, writing nothing (never a silent one-off); a recurring intent whose direct write fails is refused too, never handed to the MCP writer (no recurrence arg → one-off); DST follows RFC 5545 §3.3.5 (a nonexistent wall time shifts forward, an ambiguous one is its first instance; candidates compare as UTC instants); `GET /api/reminders/today` uses the HOUSEHOLD date (`reminder_scan.zoe_now`) and keeps an RRULE row on every day its rule fires (its due_date is the anchor, not the due day); `POST /{id}/acknowledge` on an RRULE row is done-for-this-occurrence (row stays live, next occurrence rescheduled — stopping the series is delete/deactivate), one-offs are acknowledged for good as before; the MCP `reminder_snooze`/`reminder_update` tools still overwrite due_date/due_time and are NOT recurrence-aware (no live brain registers them — fix before exposing them); `PUT` re-anchors an RRULE row when due_date changes (cleared → next occurrence from today; the stored anchor re-sent unchanged is kept, never 422); chat skips the one-off reminder form for both (`routers/chat._shows_form`) because the form carries no recurrence; next-occurrence search steps whole periods, never a fixed day window (a 3-yearly or Feb-29 rule is years away); a date-only row whose recurring_pattern is legacy free text (not an RRULE) is excluded with a once-per-id WARN (time-only rows stay daily); a bare month-day already past ("june 3" in September) resolves to NEXT year, an explicit past date (ISO or with a year) is 422. Scan log lines name the reminder ID and the problem class only — never the title or raw stored text (2026-09-25 audit §2.2; Greptile/Codex threads on #1686). `proactive/scheduler.py` logs the jobstore DSN only through `redact_url` — never log a DSN raw.

## Forbidden

- **The startup memory probe checks RECALL CORRECTNESS, not just plumbing** (`_run_memory_capture_startup_probe` + `memory_recall_probe.run_self_recall_check`). The 2026-07-31 torn-HNSW corruption reported `memory_capture: ok` for ~8 hours because `search()` returned *something* — the probe only proved the call path worked, never that it returned the RIGHT row. The check now samples one real stored row and requires it (or an exact-duplicate embedding, distance < 1e-3) back in its own top-10; a MISS marks memory `degraded` on `/health`. It is read-only (`collection.get`/`query` directly, never `MemoryService.search`) so it ticks no access counters. **A self-recall MISS is deliberately NEVER fatal — not even under `ZOE_MEMORY_STARTUP_STRICT`** (it sits in its own try/except, outside the strict re-raise): a corrupt index is exactly when the service must stay up and observable, since lexical recall may still answer and an operator needs a live `/health` to diagnose from. Crash-looping on a bad index is the failure being detected, not a response to it. Strict mode still governs genuine plumbing failures, unchanged. Pinned by `tests/test_memory_recall_probe.py` + `tests/test_memory_startup_probe_wiring.py`. Independent backup/compaction tooling: see `scripts/AGENTS.md` (memory-store resilience trio).
- Memory Lint (`memory_lint.py`) is REPORT-ONLY. It must never delete, merge, edit, archive, supersede, or otherwise mutate stored memory, and must never trigger such mutation. It reads through the `MemoryService` facade and returns flags/reports for human or curation review only.
- Lint must not run inside the nightly dreaming cycle by default. Emitting a lint report from dreaming is opt-in via `ZOE_MEMORY_LINT_IN_DREAMING` and stays report-only even when enabled.
- No DB schema migration, no destructive ops, and no cloud/LLM dependency from the lint detectors (they stay offline-safe heuristics).
- The local merge queue (`run_merge_queue` in `greploop_guard.py`) is DISABLED by default (requires `ZOE_MERGE_QUEUE_ENABLED=1` and no `merge_queue.disabled` kill file). It must NEVER use `--admin` or force-merge, never bypass branch protection, never merge a PR not assessed READY, never act on PRs lacking the `auto-merge` label, never resolve rebase conflicts automatically (abort + report), never touch the live checkout (rebases run in a disposable worktree), and act on at most one PR per cycle.
