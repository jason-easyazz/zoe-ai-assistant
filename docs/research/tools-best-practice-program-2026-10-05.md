## A. The honest answer (one page)

**Are we using our tools the way their docs say?** Mostly for the tuning, mostly not for the logic and the trust boundaries. The six records agree on a shape: the vendor tools are configured sensibly (nginx streaming, Telegram long polling, Chroma persistence, Postgres pooling, Moonshine on CPU, the llama.cpp flags), and the defects sit in three places that are Zoe's own: (1) **memory logic** written by Zoe that is weaker than what the docs or the field describe, in particular a ranker that lets an LLM paraphrase outrank the user's own words, a dedup that drops exactly the new names, and name resolution by substring; (2) **credential scope and who can reach what**, not performance; (3) **no measurement** of the properties that make a memory trustworthy. Per tool:

- **MemPalace: Zoe never used it as software.** **[src]** `mempalace` is pinned (`services/zoe-data/requirements-py312.txt:65` `==3.10.0`; `requirements.txt:106` still `==3.3.1`; the `scripts/setup/build_py312_venv.sh:83` smoke list; `scripts/setup/jetson/install-jetson-agent.sh:49` `MEMPALACE_PIN`) and installed, but no production module imports it: a grep for `import mempalace` and `from mempalace` finds only a test assertion (`services/zoe-data/tests/test_palace_drawers_opener.py:105` asserts the opener does not use its wrapper) and an unrelated local module named `mempalace_baseline`. What Zoe shares with it is a collection name (`mempalace_drawers`), a metadata vocabulary (wing = user id, room) and a Chroma layout. The runtime import was removed in the 2026-09-28 B0.8 cutover (PR #1745, `d346aa90`); since then retrieval, ranking, dedup, the graph and sanitising have been Zoe's own code (MC section 1.3), and the pin is dead weight that only adds version churn and a wrong-model onboarding default (3.10's own default embedder is `embeddinggemma`, 1.4 GB; `config.json` is pinned to `minilm` so it cannot re-point the palace). MemPalace is a reference to borrow four ideas from (BM25 plus metric-aware similarity, the `num_threads=1` pin, a query sanitiser, half-open validity intervals), not a dependency.
- **Chroma 1.5.9** is a fine store of record; Zoe's departures are the unpinned HNSW threads (a documented race on 1.5.x), a score formula that assumes `l2`, a whole-metadata rewrite on every read, and a nightly second `PersistentClient` from another process (MC C1-C6, IN section 10). At 284 rows HNSW is the wrong tool: exact numpy search is 0.03 ms against 4.0 ms and removes a failure class. The 2026-10-04 "filtered query wrong" incident could **not** be reproduced, so its mechanism is **[unverified]** (MC section 2.5).
- **Brain stack (llama.cpp, Gemma 4, FunctionGemma, Flue):** Flue is used as documented. The headline gap is that **no memory extractor uses constrained decoding** (the docs support `response_format: json_schema`), a reply cut off by `max_tokens` parses as "no facts", and a deterministic stage after the model is lossy (BX section 0). Constrained decoding alone cannot make extraction lossless (a schema fixes shape, not completeness); the fix needs a schema with slots for lists, a coverage invariant in code, and no lossy stage after the model.
- **People graph and Postgres:** the schema and pool are sound at this size; the history the temporal flag stores cannot be read, one list endpoint shows closed edges as current, supersede is not atomic, "invalidate, never delete" holds in one writer and is violated by five, and the one name resolver is `LIKE '%name%'` with no `ORDER BY` (PG section 1, gaps G1-G6).
- **Speech:** the Pi is the weakest link and the documented one (throttling from 80 C, idle 76-82 C, no fan device); the Pi's Silero VAD is fed non-contiguous windows; Moonshine keyterms are plumbed and off; the Kokoro "streaming" endpoint emits one item (SP section 0).
- **Integrations:** tuning mostly sound; the weak spot is trust (a tunnel hostname with no Access app, a bridge holding three LLM keys it never uses, a bot token in the journal, `:8000` answering on the LAN, a public repo with a non-ephemeral self-hosted runner) (IN preamble and G1-G7).

**How do we become better than mem0 / Zep / Letta / ChatGPT memory / Nomi?** Not with a better vector index, and not with a LoCoMo number. Vendor LoCoMo figures are self-reported and disputed (the same system scores 58 or 75 depending on who ran it; an independent audit finds 6.4% corrupt gold answers, ZMB section 2), and **no competitor has been run on any Zoe scenario, so no "better than X" sentence is supportable today** (ZMB section 6). What the sources do support is a shape the field does not publish: mem0 v3 is ADD-only and lets ranking resolve conflicts, and its own weakest BEAM cell is contradiction resolution; Zep's rule is "newest wins" with no user-versus-inferred class; Letta blocks are read-only or last-write-wins; ChatGPT is undocumented and Nomi says "one does not supersede the other" **[secondary, from FA section 5]**. Zoe can win on seven properties, each of which is a program item below:

The definition that makes "better" checkable (ZMB section 6): Zoe's pass rate on an axis has a Wilson lower bound above system X's upper bound, on the same scenario spec, with the negative control proven red on Zoe's driver. The honest superlative, true the day items 10-13 land and checkable by anyone: **"to our knowledge the only published memory benchmark with authority, forgetting and poisoning axes, each with a proven negative control"**, with the known-failing targets (unverified-speaker self-facts, pasted third-party text, as-of queries) printed in the same table. Authority, forgetting and poisoning are axes the field cannot score because its designs have no provenance class to read; that is a statement about their designs, not a measurement of them.

Item 1 keeps a regression test for it and no more. (2) BX gap G1 (the substring word-overlap dedup) is **still open** at both sites (`memory_digest.py:671` and `:859`; line numbers moved from the record's 605 and 771 because `main` moved).

1. **Drop the mempalace dependency?** Recommended yes: delete the four pins (`requirements-py312.txt:65`, `requirements.txt:106-107`, `build_py312_venv.sh:83`, `install-jetson-agent.sh:49`) after confirming nothing shells out to its CLI, and port the four ideas listed in section A first. No runtime cost (nothing imports it); rollback is a pin.
2. **Memory embedder: keep MiniLM or move to the router's bge-small ONNX?** Recommended: keep until item 12 exists. bge-small is already loaded by the router, about 6x faster (7.5 against 45 ms) and equal on recall in the pilot; a swap buys latency and one fewer ONNX session, not recall, and an un-stamped swap is silent garbage (same 384 dimensions). EmbeddingGemma is rejected on RAM.
