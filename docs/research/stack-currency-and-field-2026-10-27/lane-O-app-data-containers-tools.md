## 4. Postgres / Chroma
Recommended server params for a 16 GB box shared with LLM brain (values are standard practice; Postgres 17 docs; [S/background]): shared_buffers 256MB (DB is 38 MB: even 128MB is plenty), effective_cache_size 1GB, work_mem 8MB, maintenance_work_mem 128MB, max_connections 40 (asyncpg pool per process; one worker), wal_compression on, checkpoint_timeout 15min, max_wal_size 2GB, random_page_cost 1.1 (NVMe), jit off (small OLTP; avoids latency spikes), synchronous_commit on (keep), autovacuum defaults fine, log_min_duration_statement 250ms, and
 TIMEOUTS (the actual gap): `idle_in_transaction_session_timeout=30s`, `statement_timeout=15s` default for the app role (override per-session for migrations/analytics), `lock_timeout=5s`, `tcp_keepalives_idle=60`. Container: `shm_size 256m`, mem_limit ~1GB, `restart: unless-stopped`.
 Roles: create a non-superuser app role owning the schema (superuser blocks nothing today but breaks isolation and is exactly what CVE-2026-6471-type bugs need); keep a separate migration role. Text timestamps: migrate lazily to timestamptz on new tables; do not mass-convert.
 pgvector 0.8.6 vs Chroma 1.5.9 in-process: crash isolation is the real argument. A Chroma HNSW segfault takes down the whole zoe-data process (it did on 0.6.3). Chroma 1.5.9 is the latest and hasn't moved in 5 months; Rust core since 1.0 [S]. Options: (1) keep Chroma but run it as the Chroma server container so a crash restarts only it (recommended minimum; auth is not built in per 1.0 migration notes -> keep it on the docker network); (2) move vectors into pgvector (HNSW, halfvec) in the existing Postgres: crash-isolated, transactional with the relational rows, one backup path, one less engine; cost is a re-embed/ETL and a lab recall comparison. Given "adopt, don't rebuild" and a 38 MB DB, option 2 is the better end state; do (1) only if the lab slips. No Chroma 1.6/2.0 exists; the migration risk question is moot today.
 fastembed 0.9.x: see table; embeddings model must not change silently.

## 7. Cloudflare / nginx
cloudflared: see table. Access best practice (background [U]): one Access app per hostname, policy by identity (email/IdP group) not IP; service tokens only for machine clients (Omnigent runners) with short expiry and a "Service Auth" policy; require device posture (WARP + OS-up-to-date) only for the admin surfaces; session duration 24h or less for the panel; validate the `Cf-Access-Jwt-Assertion` JWT at the origin (cloudflared does not do it for you) so a LAN bypass cannot spoof; tunnel config `originRequest.noTLSVerify` false, `connectTimeout` 10s; WebSockets pass through by default, TCP needs `cloudflared access` client or WARP. nginx for kiosk+PWA: `Content-Security-Policy` with nonce-less `script-src 'self'` and `connect-src 'self' wss:`, `frame-ancestors 'none'` (or 'self' for the panel), `X-Content-Type-Options nosniff`, `Referrer-Policy strict-origin-when-cross-origin`, `Permissions-Policy` for mic/camera `(self)` only, HSTS at the tunnel edge, `limit_req_zone` on /auth and /api/voice (e.g. 10r/s burst 20), `limit_conn`, `client_max_body_size` per location, and `proxy_read_timeout` raised only for SSE/WS locations. No-store on the service worker script. Patch nginx first (sec. 1).
