# zoe-data contract detail: Memory recall, floors and person memory

Each section below is the **full text, verbatim**, of one bullet of `services/zoe-data/AGENTS.md` as it stood before the 2026-10-18 DOX pass (roadmap task B10). The short binding form lives in the contract and links here. If the two ever disagree on a rule, the contract bullet wins and this record is stale; record new rationale and measurements here, never new rules. Part of the [bundle index](index.md).

### ZD20 Honest forget and teach

- Conversational forget + honest teach confirmations (QA review F13/F14): `expert_dispatch.store_fact` replies track the ACTUAL inline store outcome — a raised or scrub-refused write gets an honest "couldn't save" reply, never a false "Got it — I'll remember…" (`_ingest_or_supersede` now returns stored|skip|dropped); async extractor lanes (`routers/chat.py` `_persist_memory_candidates`, `routers/voice_tts.py` `_run_voice_memory_passes`) keep their replies but count per-pass failures via `memory_metrics.memory_async_extract_fail_count`. `intent_router` handles both forget-LAST ("forget that") and entity-scoped forget ("forget everything about X", `memory_forget_entity`): deterministic, name-validated (`person_extractor._looks_like_person_name` + stoplist), strict whole-word matching, archive-only (soft-delete, never hard-delete), guests fail closed. Pinned by `tests/test_honest_confirm_entity_forget.py` (`ci_safe`).

### ZD21 Memory capture status

- Memory capture completion signal: `memory_capture_stats.py` — per-user started/completed/failed counters around `routers/chat.py::_persist_memory_candidates` (`failed` = the impl reported a memory pass that raised, which it swallows so the turn never crashes; the async latent-suggestions writer is tracked as its own unit, so `in_flight == 0` covers every writer of the turn) (scheduled with `ensure_future`, so the turn returns first), exposed by `GET /api/memories/capture-status` (internal token) for harnesses to WAIT on instead of sleeping; in-process, bounded, reset on restart.

### ZD22 Two memory timelines

- Two timelines on every memory row (audit P2.1, no flag; `memory_temporal.py`, `docs/knowledge/memory-authority.md` -> *Two timelines*): `valid_from` is written on EVERY ingest (the event time the person STATED — "since 2018" — from a `user_stated`/`user_confirmed` write only, never a model's paraphrase; else the capture time), `invalid_at` + `expired_at` on every supersede/archive (the row is kept), intervals are half-open `[valid_from, invalid_at)`; `MemoryService.search(as_of=...)`/`history()` read them, and a history question ("where did I live before?") adds the replaced facts labelled "Before that (...)" (a forgotten name never resurfaces; the forget sweep archives `superseded` rows too). `memory_supersede.cue_applies`: "used to <verb>" retires only the row that verb is about. `scripts/maintenance/memory_validity_backfill.py` is dry-run only.

### ZD23 Owner retraction by key

- The owner's retraction / correction retires the older row BY KEY (2026-10-09): `memory_supersede.owner_key_match` pairs by (subject, attribute) - a one-valued slot or the same predicate + everything the retraction names - when the new row is the owner's word (`is_owner_word`), never by sentence overlap (the 6n defect: "User no longer gets migraines" named 1 of 3 words of the older row). Every row the turn/nightly digest stores or parks logs one `MEMORY_ROW lane= outcome= user= id= class= promoted= basis= status= type= wording=` INFO line (`memory_digest.log_row`; row text only, post-turn). See `docs/knowledge/memory-supersession.md`; pinned by `tests/test_owner_retraction_retires_old_row.py` + `tests/test_memory_digest_row_log.py`.

### ZD24 Memory ops and for prompt

- Memory ops: Ingest (`memory_digest.py` dreaming), Query (`memory_service.py` search), and Lint (`memory_lint.py`) — the report-only scan for contradictions/stale/orphan/duplicate rows. The `/api/memories/for-prompt` recall packet (`routers/memories.py`, shared by chat + voice) selects bullets by relevance but PRESENTS conflicting bullets (same fact, changed value — ≥0.6 token overlap, non-subset) newest-first by `added_at`, so a user correction always appears above its stale sibling; no-conflict packets are byte-for-byte unchanged (`test_memory_for_prompt.py`).

### ZD25 Named person recall floor

- Named-person recall floor (S21, `ZOE_PERSON_RECALL_FLOOR` = enforce (default) | shadow | off, per-call; a shape of the seam recall floor, so `ZOE_SEAM_RECALL_INJECT` still gates it): a question-shaped sentence that names a person THIS user knows (`people` rows with `user_id = ?`, or an owner-scoped `person_pending` entity; exact whole-name match, `memory_gate.person_names_in_question`) forces the for-prompt packet and the people-graph block led by that person (`person_recall_floor.resolve_named_people` -> `memory_for_prompt(force_recall, focus_people)` -> `zoe_memory_compose` focus). Logs `RECALL_FLOOR reason=named_person`. Voice-path files; replay gate. Detail: `docs/knowledge/samantha-bar.md` (S21 reply leg).

### ZD26 Role guess guard

- Roles on the ASK path (S22, `role_guess_guard.py`, `ZOE_ROLE_GUESS_GUARD` = on (default) | shadow | off, per-call): since the named-person floor a question naming a known person reaches memory, and a packet row with a name and a date but no role let the 4B brain answer "Anika Reyes is your mother" (3 of 4 live runs, 2026-10-07; store and packet role-free). When the floor fires, `zoe_flue_client._recall_context_block` appends `Relationship not stated for: <names>` (+ the never-guess rule) INSIDE the block for each named person no packet row relates to the user, and fills a sink; `run_flue_brain_streaming` wraps the turn in `role_guess_guard.filter_stream`, which holds the reply ONLY on such a turn and rewrites a family/partner role the packet and the user's own words never tie to that person ("is someone you've told me about" + one who's-who question). Every other turn streams byte-identical; `off` also drops the marker. Voice-path file (`zoe_flue_client.py`): lands via the replay gate.

### ZD27 Structural memory floors

- Structural memory floors (`ZOE_STRUCTURAL_CLAIMS` = off | shadow (default) | enforce, per-call; `structural_claims.py`, `lexicons.py` + `lexicons_data/<lang>.json`, `role_triples.py`, `structural_verifier.py`; operator note `docs/knowledge/structural-floors.md`, research `docs/research/structural-floors-2026-10-09.md`): the turn digest also asks the extractor for a CLAIM ROW per fact (subject, predicate, value, polarity, modality, tense, the owner's verbatim quote), stored on the row (`metadata["claim"]`). `shadow` logs the structural decision beside the lexical one (`STRUCTURAL_FLOOR` lines, labels only) and the lexical one decides; `enforce` makes the claim row decide promotion (language-independent checks authorise - quote is a substring of the owner's turn, value in quote and fact by edit distance, modality, subject, speaker - the lexicons only VETO), retires older rows by claim key (`memory_supersede.retire_by_claims`), and makes the role guard read ONLY people-graph id triples (`role_guess_guard.neutralise(..., triples=, ids=)`). The English word lists now live in `lexicons_data/en.json` (pinned byte for byte by `tests/test_lexicon_english_identity.py`); a language is `enabled` only while its rows in `tests/test_structural_floors_labelled.py` pass. `ZOE_STRUCTURAL_VERIFIER` (shadow default | off): the post-turn 4B yes/no judge, bounded, logs only, never on the voice path. Voice-path file touched: `zoe_flue_client.py` (one bounded triple read on a turn that already named a person).

### ZD28 Ask to remember

- Ask-to-remember (S11, `ask_to_remember.py`, `ZOE_ASK_TO_REMEMBER` = on (default) | off, per-call): the owner's explicit "remember that ..." / "don't forget that ..." / "keep in mind ..." / "note that ..." / "for future reference ..." is ONE deterministic tier in `fast_tiers.resolve` (before the router and the brain; chat, voice, LiveKit, Telegram) and the executor of `memory_remember`. Stores the owner's words VERBATIM as a `user_stated` row (writer `explicit_teach`, tag `ask_to_remember`, the utterance as `source_excerpt`) through `expert_dispatch._ingest_or_supersede` (idempotent; a changed value supersedes); the reply is ONE short sentence chosen AFTER the outcome (never "I'll remember" without a row; PII / pasted-or-quoted / unverified-speaker / a name (the account's) / a dropped write each say nothing was saved). "Do you remember what I asked you to remember?" lists the tagged rows; "forget that" (`memory_forget_last`) retracts the row AND the capture's near-identical twin (`siblings_of`). "Forget that." is no longer vetoed by the router head (`fast_tiers.intent_gate`: a command that starts with the forget verb is explicit; live 2026-10-09 the head said chat@0.84 and the brain answered instead). Not claimed: "remember to ..." (reminder), questions, instructions to the assistant. Guests: not handled (the intent lane's sign-in message). VOICE-PATH (`fast_tiers.py`).

### ZD29 Personalisation hop

- Personalisation hop (S9a / S9b, `personalisation_hop.py`, `ZOE_PERSONALISATION_HOP` = on (default) | off, per-call): a GENERIC-ADVICE request ("any tips for sleeping better?", "what should I wear ...") gets the owner's <= 2 DURABLE facts that change the answer (a night shift, a 6am dog walk, a diet, an allergy, a child's age) under `## Shape the answer by` plus one rule line, in the `/api/memories/for-prompt` packet and on the Flue seam (`zoe_flue_client._hop_context_block`; one block per turn, never beside a recall / continuity / verify / raise / brief block). Reads `MemoryService.load_durable_for_hop` (approved, owner-stated rank, owner's own rows, no age cut/no decay (#1911), no moods/changes/pasted rows) under a 1.2 s cap; a non-advice turn reads nothing. Logs `PERSONALISATION_HOP` counts only. VOICE-PATH (`zoe_flue_client.py`, `routers/memories.py`). `ZOE_PERSONALISATION_HOP_PLACEMENT` = `block` (default, measured best) | `suffix` (one parenthetical line after the words) | `preamble` (the block before the words) chooses where it rides on the Flue wire (`scripts/perf/hop_placement_ab.py`, table in `docs/knowledge/samantha-bar.md`); `ZOE_PERSONALISATION_HOP_WORDING` = `natural` (default: the rule line + block opener ask the brain to name the fact in a few natural words) | `legacy` (the old "use it silently" / "do not recite" text; kill switch) chooses what the hop SAYS (`personalisation_hop.rule()`, `zoe_flue_client._hop_block_open()`; A/B via `hop_placement_ab.py --wordings legacy,natural`). `fast_tiers._hop_owns_turn` keeps a domain expert (the weather expert answered S9b) from answering an advice request the hop owns.

### ZD30 Person half guards

- The person half, in code (person bench P5a/P7/P8/P12; `docs/knowledge/person-half-guards.md`; three per-call flags, each `shadow` (DEFAULT: log `HOLD_THE_FACT` / `ASK_WHEN_AMBIGUOUS` / `CLEAN_GOODBYE`, change nothing) | `enforce` | `off`): `hold_the_fact.py` (`ZOE_HOLD_THE_FACT`) keeps an OWNER-STATED row (`memory_authority.row_authority` user_stated/user_confirmed, found in the session history however long the day) against a bare "No, I'm sure it's Thursday." - one kind disagreement, the stored value, an offer to change it - updates it on evidence or on the owner's second explicit confirmation (`MemoryService.review(edit)` as the owner's account, reply only after the edit), leaves a neutral "are you sure?" alone, and the held turn is not mined (`is_own_reply` skips the extractors in `routers/chat.py` + `routers/voice_tts.py`); `ask_when_ambiguous.py` (`ZOE_ASK_WHEN_AMBIGUOUS`) asks ONE question naming the choice when a request names a first name two of THIS user's `people` share and nothing settles which ("Which Marisol do you mean: ...?"), before the router or any tool, and the owner's short answer reaches the brain as the original request with the full name (`zoe_flue_client._resolve_clarification`); `clean_goodbye.py` (`ZOE_CLEAN_GOODBYE`) is a reply guard in `run_flue_brain_streaming` that holds the reply ONLY on a farewell / "are you there?" / content-free turn (two short sentences, no question, no hook; a plain "Yes, I'm here."; silence never remarked on) and leaves a question Zoe owes (the pending contact offer, S16) alone. The first two are tiers in `fast_tiers._person_half_tier`. Voice-path files (`fast_tiers.py`, `zoe_flue_client.py`, `routers/voice_tts.py`): land via the replay gate. Offline replay of the guards over a bench run's kept replies: `scripts/perf/person_half_replay.py`.

### ZD31 Voice lane parity

- Voice lane parity (`docs/knowledge/voice-lane-parity.md`, `scripts/perf/lane_parity.py`, `tests/lane_parity_rig.py` + `lane_parity_cells.py`, `tests/test_voice_lane_parity.py`): the spoken and typed lanes run the SAME conversation tiers in the SAME order. `fast_tiers.resolve(phase="conversation"|"domain"|None)` splits the run: `voice_command` calls the conversation half FIRST (distress, provenance, feedback, self-model, correction, pull, person half, identity, "remember that") before its confirmation gate, Skybridge cards and keyword intents, and the domain half (Tier-0, router, experts) where it always was; a new conversation tier goes in `fast_tiers`, never in a lane. `conversation_feedback.py` (`ZOE_CONVERSATION_FEEDBACK`, default on) is the ONE writer of `chat_feedback` (the thumbs endpoint calls `record_feedback` too): a bare "that was wrong" writes thumbs_down and lets the turn go on, "that's wrong, it's X" writes `correction`, "good answer" writes thumbs_up and answers in four words; guests, a rejected speaker and a dry replay write nothing. `correction_apply.maybe_swap` (under `ZOE_CORRECTION_APPLY`): "that's wrong, my sister is Marisol not Marisa" rewrites the one note (twin rows too) that holds the old value, renames the one matching contact and reads back "Got it, your sister is Marisol."; no stored note to change = the brain answers. A waiting spoken write is confirmed only by `voice_tts._pending_decision` (a short yes; a question, a negated "correct" or a correction is never one). Contacts READS (`people_search`) on voice use the shared executor for an identified speaker, through the head's veto, and a "nobody called X" miss still goes to the brain. VOICE-PATH (`fast_tiers.py`, `routers/voice_tts.py`): replay-gated; the replay harness mirrors `fast_tiers.resolve` only, so the lane-parity rig is what covers `voice_command`'s own stage order.

### ZD32 Memories screen API

- Memories screen API (`memory_space.py`, `routers/memories.py` `GET /api/memories/mine` + `POST /api/memories/mine/{id}/forget`; the touch estate's "What Zoe knows about you" stage): the SAME own-rows read as the voice "what do you know about me?" (`provenance_answers.gather`) as data for a screen, with the same walls. **Identity is the server's**: `memory_space.require_member` refuses (401/403, no row, no member name) a request with no `X-Session-ID` (`get_current_user` resolves a device token to the panel's bound user - a standing binding is not a person), a degraded auth check, a guest role or a guest-shaped id; there is NO `user_id` parameter. Private classes (health, money, personal, feelings) are returned as COUNTS only; responses are `no-store`. People are merged entries with no row id (forgetting a person stays the voice `memory_forget_entity`, which asks for the PIN); every other item carries a row id and a `told`/`inferred` provenance. Forget runs the steps of the voice "forget it" (reject row + twins, physical erase, owner's verbatim words) and answers 404 for an absent / someone else's / already-gone row (no oracle); a step that could not finish is 503, never "forgotten". Pinned by `tests/test_memory_space.py` (guest / device-token / degraded / other-member / private-word walls, each with a break-the-fix control).

### ZD33 Provenance and memory control

- Provenance answers + memory control (BM5, bar S23/S24/S25, `memory_provenance.py` + `provenance_answers.py`, `ZOE_MEMORY_PROVENANCE_ANSWERS` = on (default) | off, per-call; the fix verb also needs `ZOE_CORRECTION_APPLY`): ONE deterministic tier wrapped around `fast_tiers.resolve` (defined last in `fast_tiers.py`, so every caller - chat, voice, LiveKit, Telegram - gets it through the unchanged name; it also records every OTHER tier's reply as "a deterministic tier answered", so "why did you say that?" never explains the wrong reply). (1) "why did you say that?" / "where did you get that?" / "how do you know that?" right after a reply names the source row's DAY and the owner's own words VERBATIM: the ledger (`memory_provenance`, in-process, per user, IDS only) is fed by `/for-prompt` (`routers/memories.memory_for_prompt` -> `note_served`: the rows and exact-words turns the brain was handed) and committed by `brain_dispatch` (`brain_streaming` / `brain_oneshot` wrap every brain turn, text and voice: of the rows served during the turn, the ones the reply restates, best first); `provenance_answers.explain` re-reads each row (ownership, approved, not forgotten, not unverified) and quotes `source_excerpt` only for a writer whose excerpt is by contract the owner's turn (own-words wall applied), else the owner's verbatim turn from `exact_words`, never a paraphrase; a reply that used no memory says so; NO record of the previous reply (another lane, a restart, a stale turn) says it cannot tell - it is never "no memory used". A sensitive row's words are not spoken on voice. (2) "what do you know about me?" is a bounded grouped summary (people, places, routines, preferences, recent; counts + newest; voice = about three sentences in the second person - the people COUNT (an entry with a name or relation; an unrecognised people-group row is a fact, never a person) with the newest NAMED one, one short recent example per standing group, an offer to go on - chat/Telegram = the longer list with dates); a happening or a plan ("is back in their office", "plans to eat") is `other`, never a place or a preference (`group_of`/`_EPISODE_RE`), and a row stamped `authority_basis=unanchored` is counted (`Known.unconfirmed`), never said back (with nothing else known the reply is `UNCONFIRMED_ONLY_REPLY`, never "I don't know much about you yet"); `second_person` conjugates every coordinated verb under "User" too ("likes tea but hates coffee" -> "like tea but hate coffee"; only a known verb from `present_verbs` with an object after it, never a noun list, an infinitive or another subject's clause) and skips the subject adverbs in `lexicons_data/en.json` -> `subject_adverbs` ("User usually walks" -> "you usually walk") and rewrites "their" only when no other person is named before it; health / mood / money / other private rows are COUNTED, never read, until pulled by name ("what do you know about my health"); another member's file is refused, a guest gets nothing. (3) The one-sentence fix: on the turn right after an answer named a row, "that's wrong, it's X" / "actually X" edits THAT row through `correction_apply.apply_row_correction` (`review(edit)`, supersedes, twins retired) and says what it now holds; a fragment is swapped in only when exactly one slot of that kind exists, else it asks for the whole sentence; "forget it" forgets THAT row + its twins + the quoted turn in the exact-words index (not the newest row). (4) Off the record: "off the record: ...", "don't remember this", "this stays between us" - a cue with a payload marks that turn, a bare cue arms the next; a marked turn reaches no extractor, digest, person extractor, suggestion detector, exact-words index or nightly catch-up (its `chat_messages` row, and the reply to it, carry `"off_record": true`; every transcript reader that rebuilds memory filters it - `memory_provenance.off_record_sql`), and `MemoryService.ingest` blocks any write whose content is mostly the marked turn's (so the brain's own memory tool cannot store it); the only trace is one `OFF_RECORD` audit line without the words. Honest gaps: the turn stays in the SESSION transcript (the conversation's own history, and the sidecar's session), the voice daemon's audio corpus is separate, and a brain tool that writes to lists / contacts rather than memory is not walled. VOICE-PATH (`fast_tiers.py`, `brain_dispatch.py`, `routers/memories.py`, `routers/voice_tts.py`, `routers/chat.py`): replay-gated.

### ZD35 Unknown name and challenges

- Named-person recall floor reaches an UNKNOWN name (2026-10-12): an identity-shaped question ("Who's Brannock?", "Do you know Brannock?", "Tell me about Brannock", `memory_gate.person_identity_names`) whose name is neither a contact nor a person-fact entity still resolves to `NamedPerson(name, "", "unknown")` in `person_recall_floor`, so the for-prompt search runs before a denial; other capitalised questions ("What's the weather in Northcliff?") are untouched. The turn-digest relationship validator (`memory_quality.user_relationship_claim_unsupported`) accepts a bare kin address word in the owner's turn ("seeing dad") as the owner's own parent (`_bare_kin_stated`; "her dad" / "Pell's dad" / "the dad" / a bare "wife" do not). **Memory challenges are a recall trigger (2026-10-12)**: "don't you remember?", "we've already talked about it" (plain past conversation like "we talked to the electrician" is NOT a challenge: "we talked" needs already/before/earlier or "about it/this/that"), "I told you about that" (`memory_gate.is_memory_challenge`, per-language data `lexicons_data/<lang>.json` -> `memory_challenge.patterns`, en + es) make `zoe_flue_client._recall_question_shape` return `challenge`; `_challenge_context_block` sends the continuity-mode packet (the last days pinned) PLUS `_CHALLENGE_RULE` ("answer only from the notes; if none covers it say you don't have it noted; never describe something the notes do not contain") and, when nothing matched, `_CHALLENGE_EMPTY` - so the denial stands on a looked-at record and an invented memory has no room. **No subjectless row (same day)**: the turn digest settles a fact that opens on he/she/his/her from the owner's own recent words (`memory_quality.resolve_subjectless_fact`: "my <relation>", exactly one compatible, newest message first, NEVER past a nearer named person - a capitalised name said after the newest relation, in a later turn or later in the same message, holds the fact; a place after a locative word, a day, a sentence opener and "my sister Quillan" are not blockers) and rewrites it to "User's <relation>..."; otherwise it holds the fact (`guard_subjectless_pronoun` in the reject ledger).

### ZD42 Relationship graph traversal

- Relationship graph: `relationship_graph.py` — READ-ONLY, flag-gated (`ZOE_RELATIONSHIP_GRAPH_ENABLED`, default OFF) bounded multi-hop traversal over `person_relationships` (portable recursive CTE, owner-scoped, cycle-safe, depth≤4/limit≤200). Explicit-query only (`GET /api/people/{id}/graph`), OFF the chat hot path. ADR: `docs/adr/ADR-relationship-memory.md`. **Graph-adjacency recall boost** (`memory_service._semantic_search`, design `docs/architecture/gbrain-memory-graph-recall.md` Part B): a 7th additive blend term that lifts facts stored under people 1–2 hops from the person a recall query names (surfacing "my sister's husband's job" when the fact lives on the husband node). Gated behind BOTH `ZOE_RELATIONSHIP_GRAPH_ENABLED` AND a new sub-flag `ZOE_GRAPH_RECALL_BOOST` (default OFF); weight `ZOE_GRAPH_RECALL_WEIGHT` (default 0.30). The neighbourhood is fetched best-effort on the ASYNC side (`search` → `_graph_depth_by_pid`, reusing `person_extractor._resolve_person_uuid` + `relationship_graph.neighbors`, no new NLU) and passed as a plain `{people.id: depth}` dict into the sync blend; any failure → empty dict → no boost. OFF is byte-identical to pre-2b (term neither computed nor added, zero DB work). Proven by `tests/test_graph_recall_boost_eval.py` (multi-hop P@5/R@5 ON-vs-OFF + no-regression). Enable in prod only after the W0 RAM/replay gate on `ZOE_RELATIONSHIP_GRAPH_ENABLED`.

### ZD43 Person merge

- Person merge / entity resolution: `person_merge.py` — flag-gated (`ZOE_PERSON_MERGE_ENABLED`, default OFF) fold of an `is_partial` stub into a real contact, re-pointing all its data (satellite tables + `people.introduced_by_person_id` self-FK + `person_relationships`). Resolves the two conflicts a re-point creates under the partial current-edge index: drops self-edges (a==b) and de-dups colliding CURRENT edges (pre-checked before UPDATE so `person_relationships_pair_active` is never violated); target-wins field merge, source soft-deleted. Roadmap item 4 of `docs/adr/ADR-relationship-memory.md`.

### ZD44 Contacts from known people

- Contacts from known people: the `person_create` pending-suggestion action (`pending_suggestions.py`, flag `ZOE_PERSON_SUGGEST_ENABLED`, default OFF) turns a confirmed proposal into a full editable `people` row (deduped, `_looks_like_person_name`-guarded, private by default). `contact_backfill.py` (`backfill_contacts`, flag `ZOE_CONTACT_BACKFILL_ENABLED`, default OFF) is the one-shot admin pass that feeds it: reads the user's person knowledge from BOTH the narrative layer — the user's OWN `person`/`fact`/`relationship` MemPalace memories (family-shared rows owned by another user are excluded, so a household member's people don't leak in) AND the synthesized third-person `user_portraits` prose — then extracts distinct name (+relationship) with two complementary passes (deterministic regex borrowed from `person_extractor` PLUS an LLM extraction over the combined text, reusing the local Gemma client idiom; malformed/failed LLM response falls back to regex-only), dedups against existing contacts, and emits a batch of `person_create` proposals — never a silent contact write. Internal/loopback endpoint `POST /api/memories/backfill-contacts` (`require_internal_token`); pass `session_id` = the user's ACTIVE session (suggestion retrieval filters by session, so the default `backfill` session just parks them for an out-of-band accept flow). Byte-for-byte no-op when the flag is off.
