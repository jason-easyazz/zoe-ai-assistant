### ZD36 Seam recall floor

- Seam recall floor: `zoe_flue_client.py` — flag-gated (`ZOE_SEAM_RECALL_INJECT`, default OFF, per-call env read) deterministic injection of the `/api/memories/for-prompt` packet into the outbound flue message on conservative recall-question turns — personal ("what's my…", "do you remember…") OR, with `ZOE_RECALL_PRESENT_STATE_SHAPES` on, **present-state** / **event-time** (shapes `present` / `event_time`, see the day-sim bullet below) OR **evidence-shaped** (`memory_gate.is_evidence_question` — "What exactly did I say about Marisol?", "are you sure?"; shape `evidence`, checked after personal and event) OR, since Samantha bar S1 round 3, **event-shaped** (`memory_gate.is_event_question`, the ONE predicate shared with the composer's semantic-search gate `message_needs_memory`: a people-movement verb — flying in, arriving, visiting, staying, leaving… — anchored by a time cue ("Who is flying in on Thursday, and where from?", and the bare present tense when it opens the question: "Who arrives on Thursday?"), a my/our relation word ("when is my sister arriving") or a he/she/they subject ("where is she flying from"); never general knowledge — "who is the prime minister", "who is playing on Sunday", "when does the train leave" — and never a who+time question about a public event or venue ("Who is coming to the game on Friday?") unless the user's own people are named too; the anchors and the public-event exclusion are judged per SENTENCE (`memory_gate.event_sentences`, split on . ! ? ; only), so an unrelated sentence neither vetoes nor vouches for the question), decided by `zoe_flue_client._recall_floor_shape` (which the continuity exclusivity check and the offer ager share). **Precedence:** a personal my/I question is always recall; an event question EMBEDDED in a first-person feeling — the same sentence carries both ("I'm anxious about who is flying in on Thursday") — is a continuity turn while continuity is on, while a standalone question beside a feeling in another sentence ("I'm exhausted. Who is flying in on Thursday, and where from?") stays recall — the user is sharing a feeling, and the continuity packet still carries the event because continuity mode runs the semantic search on the user's words, each match logging `SEAM_RECALL user=… shape=personal|event bullets=… chars=…` at INFO — fetched in-process via `routers.memories.memory_for_prompt`, capped (12 bullets / 1600 chars), placed AFTER the ` zoe-uid:` identity line so the sidecar's single-line strip regex is untouched. A floor under the ~97% recall_memory tool-invocation ceiling, not a replacement for the tool. Fail-open: any fetch failure continues the turn without the block. Operator enables via env only after the replay gate. Pinned by `tests/test_flue_seam_recall_inject.py`. Companion seam: `ZOE_SEAM_OFFER_INJECT` (default OFF, per-call env read) injects JUST the pending-contact offer directive (`_pending_offer_block`, ≤2 offers, sanitized, `[PENDING CONTACT OFFER…]` block) into the outbound flue message on ANY turn while an unresolved `person_create` offer exists — closing the QA-F5 gap where offers reached the brain only on recall-shaped turns. Skipped when the recall packet already carries the `[pending-contact]` directive (never double-asks); surfacing stays non-destructive, aging stays per-user-turn; fail-open. Pinned by `tests/test_flue_seam_offer_inject.py`. Second trigger class: `ZOE_SEAM_CONTINUITY_INJECT` (**default ON** — the Samantha bar S4 fix; `false`/`0`/`off`/`no` is the kill switch, per-call env read) — on a first-person emotional/state STATEMENT (`_CONTINUITY_RE`: "I've been feeling a bit on edge", "I'm so stressed", "today was rough", "I can't stop thinking about…"; never "I feel like pizza", third-person moods, or questions) it injects the for-prompt packet composed with `memory_for_prompt(mode="continuity")` — rows captured in the last 72 h pinned first — read DIRECTLY via `MemoryService.load_recent_for_prompt(emotional_first=True)` — a store-BOUNDED query (scope AND numeric `added_ts >= cutoff`, hard `limit` 300; `_build_metadata` stamps `added_ts`, the epoch twin of `added_at`, because chroma `$gte` compares numbers only), ordered emotional-first then newest over that whole candidate set BEFORE the ≤50 cut, no access ticks; rows without `added_ts` (pre-field) are reached by a full-scan fallback only when the bounded query finds nothing; never filtered out of the ranked `load_for_prompt` prefix, where a heavy user's yesterday can rank past any cut — merged with the ranked rows, then `_pick_recent_for_continuity` (emotional rows then newest, ≤6, `(recent)`-tagged, `(recent, felt <affect>)` when the row carries a captured feeling), capped 12 bullets / 1600 chars including the closing ask — plus one flattened, bracket-stripped portrait line (≤240 chars). The block rides AFTER the user's words (still inside the latest user message; the sidecar prefix / #1725 prompt cache is untouched) and closes with ONE concrete ask: when the composer returns `continuity_focus` (`_continuity_focus`: the top recent EMOTIONAL row in the packet — never a neutral fact) it is "The user recently told you: <focus> (they said they felt <affect>). If it fits, briefly and warmly ask how that is going…", else a generic check-in line. **A bare mood report is never the focus** (`memory_digest.fact_has_topic`: content words minus stopwords, time words, feeling words and mood fillers — including past/perfect report forms like "felt", "seemed", "a rough time" — must be non-empty) — the digest stores today's "User has been feeling a bit on edge today" seconds after the turn, so without the check it becomes the newest emotional row and displaces the real worry on the next mood turn (Samantha bar S4 round 3: live 1/5, the focus flipped after sample 0). **Offers are DEFERRED on a continuity turn:** the turn is decided by the TRIGGER (`zoe_flue_client.is_continuity_turn`: flag on, real uid, recall floor not claiming it, `_CONTINUITY_RE` match — pure, no I/O), never by whether a packet came back, so an emotional turn whose packet was empty or timed out still defers. The continuity composer omits the pending-contact fold (`_fold_pending_contact_offers` runs in relevance mode only), the seam skips `_pending_offer_block` and logs `SEAM_OFFER user=… deferred=1 reason=continuity` when `ZOE_SEAM_OFFER_INJECT` is on, the composer applies the same deferral to a RELEVANCE-mode packet built for a continuity turn (the core brain's in-process packet and memory.ts pass the user's message), and `latent_intent_detector.detect_and_store` skips the per-user-turn aging tick only when the offer was actually deferred: a continuity turn AND no offer shown that turn (`pending_suggestions.consume_offer_shown_mark` — `surface_pending_contacts_for_prompt` marks the user whenever it shows an offer, on any path; in-process, single uvicorn worker). So "shown" always means "aged" and "hidden by deferral" means "not aged": a run of emotional turns can never expire an offer it hid, nor keep showing one that never expires, and the next non-emotional turn offers it (measured: with the offer present, 5/5 check-in replies ended in "add Marisol as a contact?"). Pinned by `tests/test_continuity_round3.py`. Measured on the live S4 flow (Samantha bar S4 round 2): the soft "connect if relevant" over an 11-bullet block was 0/6; the focused ask after the words passed 7/8. **Affect is captured, not inferred:** `memory_gate.extract_affect` reads a FIRST-PERSON feeling from the user's own words at turn-digest time (quoted spans and reported speech — "my sister said 'I'm so stressed'" — are stripped first, the reported span ending at its CLAUSE so "my sister said she is fine, but I'm stressed" keeps the user's own clause: someone else's words are never the user's feeling) and `run_turn_digest` stores it beside each fact attributed to that sentence (`_affect_for_fact`: ≥1 shared content word with the feeling sentence — stopwords, time words and feeling words excluded, so the digest's shortened "User has a job interview on Friday" still carries it — and the feeling sentence must win UNIQUELY over every other sentence, a tie attaching nothing, so "…interview on Friday. My sister arrives Friday" never tags the sister fact) on BOTH the ingest and the supersede path (`svc.review(..., metadata={"affect": …})` — the updated row's feeling is always THIS turn's: carried onto a superseded neutral fact, and cleared with `""` by a neutral update rather than inherited from the edited row) (`metadata={"affect": …}` → `candidate_affect`; `memory_service.memory_affect` reads it back sanitised, and `is_emotional_memory` counts it), because the digest model flattens "I'm anxious about my interview" to "User has an interview"; the turn-digest prompt also asks it to keep a stated feeling (never add one). **The turn digest keeps who/what/where/when for events** (Samantha bar S1 round 3): when the user names a person AND something is happening with them (a trip, visit, arrival, move, plan) the prompt asks for BOTH facts — who the person is ("User's sister is named Marisol") and the event with the place and day kept ("User's sister Marisol is flying in from Lisbon on Thursday"); the old prompt kept only the name on 1 of 5 samples. Pinned by `tests/test_s1_event_recall.py`. The recall floor owns any turn `_recall_floor_shape` claims (never both blocks); guest/blank ids skip; packet + portrait fetch concurrently but are awaited independently — packet 3 s, portrait best-effort 1 s from the same start, so a slow portrait never drops a completed packet, and a `finally` cancels both reads when the turn itself is cancelled — fail-open; a portrait with no packet injects nothing. The "had a rough day" form needs an explicit `I`/`we` subject (or a sentence-initial "Had a…"), and the "today was rough" form is sentence-initial, so third-person days never match. Every real-user turn logs `SEAM_CONTINUITY user=… matched=… bullets=… chars=… focus=…` at INFO. `ZOE_SEAM_CONTINUITY_DEBUG` (default OFF) additionally logs the full injected block and the first 200 reply chars (`SEAM_CONTINUITY_DEBUG`) — ONLY for harness-minted ids that are provably not real accounts — the same two checks `forget-synthetic` makes: shape (`user_filters.synthetic_forget_refusal(uid) is None`: `demo_<tag>_<hex>` / `test_<tag>_<hex>`, not allowlisted) AND not registered (`routers.memories._registered_account`, zoe-auth `auth_users`; a lookup failure means no logging — fail closed); a real user's block or reply is never logged whatever the flag says. The reply log lives in the thin `run_flue_brain_streaming` wrapper (which always `aclose()`s the inner `_run_flue_brain_streaming_turn`). `mode` defaults to `relevance`, and an in-process caller that omits it (`zoe_core_client`) keeps the relevance packet. Pinned by `tests/test_flue_seam_continuity_inject.py` + `tests/test_memory_continuity_mode.py` + `tests/test_continuity_affect.py`.

### ZD39 Flue history hygiene

- Flue history hygiene (flag-dark, SIDECAR env `ZOE_BRAIN_ELIDE_STALE_BLOCKS`, default OFF): Flue persists each user message verbatim — blocks included — and replays it every later turn of the session (the Flue instance IS the zoe-data `session_id`: voice `voice-panel-<panel>-<hex>` rolls over after 5 min idle, Telegram `telegram-<chat>` lives until `/new`, `/api/chat` callers (web, Samantha bar) the request's `session_id`; the store has no retention), so the sidecar's `src/context-blocks.ts` elides every block in `_FLUE_CONTEXT_BLOCKS` (this file's (open-prefix, close) table, pinned equal to `FLUE_CONTEXT_BLOCKS` by `tests/test_flue_context_blocks.py`) from all but the newest user message on the wire. **A new block this seam folds into the user message MUST be added to both tables** or it is replayed forever. The sidecar's `{"done"}` terminal carries `context_budget` (chars/4 estimate of the first call's system / tools / history / tail + `stale` block tokens + `elided`), logged as `FLUE_CONTEXT_BUDGET session=…` by `_log_prompt_cache` in both flag states. The sidecar's history window (`context-window.ts` `windowHeadIndex`) never drops the last `MIN_KEEP_TURNS` (3) earlier turns while the budget can still be met, and budgets against the tool block the model is actually offered (a 1.7k-token quantum used to wipe a whole 1.2-2k-token voice history for a few tokens of overshoot: `history=0` on 8 live turns, a slot-filling follow-up lost its context; `labs/flue-zoe-brain-2x/test/history_floor.test.ts`).

### ZD40 Flue wire version

- Flue wire version: `zoe_flue_client.py` — `ZOE_FLUE_WIRE` (default `2` since B6.5, per-call env read) selects the Flue HTTP contract; `ZOE_FLUE_BRAIN_URL` defaults to the live `:3579` sidecar for the same reason (a missing env var must land on the brain that runs, never on the retired `:3578`). `1` is the retired 1.x beta wire, opt-in (`?wait=result` + `{"message": …}` + whole-result reply); `2` is the Flue 2.x wire served by `labs/flue-zoe-brain-2x` — NO `wait` param (2.x rejects any, HTTP 400), body `{"kind": "user", "body": …}` at the TOP level (upstream's migration guide documents a nested shape that is refused — the top-level form is the measured one), and no whole-result call at all, so the non-streaming turn is served by reading the turn's own Seam-A NDJSON stream to completion (`_run_turn_aggregated_wire2`, the same mechanism the port's parity client uses). Wire 2 collapses that read to ONE delta with sentinels suppressed, so it is observably identical to wire-1 `?wait=result` — `ZOE_FLUE_WIRE` changes the wire and `ZOE_FLUE_STREAM_ENABLED` changes delta granularity, independently. Wire 2 NEVER re-POSTs (a 2.x turn is fire-and-forget: the wait=result fallback is skipped, and a guard in front of that block makes it unreachable). A wire mismatch is loud, never a silent parse: wire 2 refuses a 1.x `{"result": …}` body and names it, and an unrecognised flag value logs and degrades to wire 2. Wire-1 byte-identity (when selected) is pinned against a recording of `origin/main`'s own requests (`tests/fixtures/flue_wire1_golden_requests.json`, replayed by `tests/test_flue_client_wire.py` under `ZOE_FLUE_WIRE=1`); the defaults themselves (`:3579`, wire 2) are pinned by that file's section 0 with the retired `:3578`/wire-1 pair as the negative control. Any test whose httpx double is post-only (`?wait=result`) must select wire 1 explicitly. Voice-path module: the 2.x cutover happened 2026-08-09 (own port + own store — 2.x is schema v8 vs the beta's v5, no in-place migration OR rollback) and the 1.x lane is gone, so `ZOE_FLUE_BRAIN_URL`/`ZOE_FLUE_WIRE` in `.env` are overrides, not what makes the brain reachable; history in `services/zoe-data/.env.example`.

### ZD41 Flue abort on cancel

- Flue abort-on-cancel (A1/A5): `zoe_flue_client.py` — flag-gated (`ZOE_FLUE_ABORT_ON_CANCEL`, default OFF, per-call env read). ON: the streaming turn POST carries `x-zoe-abort-on-cancel: 1` (the sidecar then aborts the run itself on stream cancel and arms its first-chunk/stall deadlines), and on GeneratorExit/CancelledError after admission the client fires ONE background guarded abort (`POST …/:id/abort` + `x-zoe-abort-submission: <x-flue-submission-id>`; never awaited, never raises) and logs `FLUE_ABORT side=zoe-data … reason=<speculative|shutdown|barge_in|disconnect> exit=… emitted_chars=… deltas=…` (`emitted_chars` = reply text already handed out, for A3). Never send an UNGUARDED instance abort: Flue aborts every unsettled submission of the session, so a late one kills the next turn; no echoed submission id = no abort. OFF = byte-identical request and paths. Pinned by `tests/test_flue_abort_on_cancel.py`.

### ZD116 Brain lane failover

- **`flue > core > legacy` is CONFIGURED LANE SELECTION, not runtime failover.** The order is resolved once per turn from `ZOE_BRAIN_BACKEND`/`ZOE_USE_CORE_BRAIN`; with `flue` selected and `:3579` down, every brain turn is answered by `zoe_flue_client._FALLBACK_TEXT` while the healthy core lane sits unused (#1613). Bounded runtime failover lives behind `ZOE_BRAIN_FAILOVER` (default OFF — brain dispatch is a gated voice path, so the operator flips it only after the three-step gate spelled out in `.env.example`: failover suite green, head-bound replay PASS with the flag exported, live stop-the-sidecar drill read from `BRAIN_LANE`; `ZOE_BRAIN_FAILOVER_COOLDOWN_S` default 45 s). Its trigger is deliberately narrow and must stay that way: **only** `zoe_flue_client.FlueTransportError`, which the client raises **only** under the opt-in `raise_transport_errors=True` and **only** for a pre-admission connect failure with no text yielded and no 2xx admission — proof the sidecar never executed the turn. A model error, an HTTP status error, a read timeout, or an empty 200 all mean the sidecar RAN the turn: they keep the sentinel and never re-dispatch (the #1137 duplicate-write class). **An HTTP 400 from a wire-mismatched sidecar is a REFUSAL, not an unreachable host** — the sidecar answered, so it is a config error to surface, never evidence a retry is safe. **The trigger is per-ROUTE, and `ZOE_FLUE_WIRE` adds routes:** wire 2 has no `?wait=result`, so its turns run through `_run_turn_aggregated_wire2` (non-streaming) or the streaming block's own wire-2 pre-admission branch. Each needs its OWN pre-admission raise, ordered BEFORE the wire-2 sentinel return — put it after and failover is silently dead on `ZOE_FLUE_WIRE=2`, the wire the 2.x sidecar actually speaks. Classification by exception class is never sufficient on its own: every raise site is also gated on `admitted`, because a connect-class error after a 2xx looks identical to a refusal and is not one. **A turn that has streamed its first token is NEVER re-dispatched under any condition** — the panel speaks each delta, so a replay makes Zoe say the reply twice. One retry, on the next configured lane; a short-TTL in-process circuit breaker then skips the dead lane so only one turn per cooldown pays the failed connect, and the first turn past the TTL re-probes. **Turns overlap, so the breaker is concurrency-safe by construction and must stay that way:** it is a `(deadline, generation)` pair, every mutation is a compare-and-set against the generation the turn OBSERVED (`_observe_circuit` → `_open_circuit`/`_close_circuit`), and the half-open probe is claimed by exactly one turn. Never make the close unconditional — an earlier turn's success would erase a later turn's open, and two turns crossing the same lapsed TTL would both re-probe a dead sidecar. This governs only WHETHER flue is attempted; the replay and exactly-one-retry invariants above do not depend on it. Every turn logs ONE greppable `BRAIN_LANE lane_attempted=… lane_served=… outcome=…` line (ids only, never message text) in BOTH flag states — that is observability, and it is how an operator asserts which brain answered (`grep BRAIN_LANE ~/.zoe-logs/*`; this service does NOT log to journald). Three properties keep that line trustworthy rather than merely present, and all three are easy to regress. **(1) Exactly one, on every path a turn can leave by — ONE-SHOTS INCLUDED.** The streaming wrapper is an async generator, so a consumer that disconnects after the first delta throws `GeneratorExit` at the yield and skips everything after it; a one-shot has the same hole with no generator to close, because it is routinely CANCELLED (the LiveKit lane awaits it under `asyncio.wait_for`, chat disconnect cleanup cancels its task) and cancellation exits the await without reaching any terminal branch. Both shapes emit through the once-only `_LaneRecord` wrapped in `try/finally`, so an interrupted turn logs `outcome=interrupted` (`reason=caller_cancelled` / `consumer_disconnected`, read from the live exception so an unexpected error is not mislabelled a cancel) instead of vanishing. Never put the only emission after the loop or after the await. **(2) The outcome is the client's verdict, not "the generator finished", IN BOTH FLAG STATES.** `zoe_flue_client` renders an HTTP error, a read timeout, an empty 200, a rejected wire-2 body and a post-admission stream death alike as its canned sentinel and ends the stream normally, so an INFERRED label calls every one of them `ok` — success reported for exactly the failed turns the line exists to diagnose. The client reports its terminal verdict through the opt-in `outcome_sink` and the line carries it (`ok`/`fallback`/`error`). The default-OFF flue path takes the same sink (`_flue_streaming_labeled`/`_flue_oneshot_labeled`) — it is the deployment actually running, and a pre-request `outcome=dispatched` label there was identical for a healthy turn and every failure mode. Its DISPATCH is unchanged: one client call, never `raise_transport_errors` (which would let `FlueTransportError` escape into a route with nothing to catch it), no lane hop, and **no breaker state touched in either direction**, so a later flag flip still starts from a closed breaker. The core/legacy lanes keep `outcome=dispatched`: they have no verdict to report, and wrapping them would move `_drop_flue_only_kwargs`'s fail-closed raise from call time to first-iteration time. Labels only: nothing in the sink is read before a dispatch decision, so a wrong label can misinform an operator but can never re-run a turn. `outcome_sink` and `raise_transport_errors` are both dispatch-INTERNAL kwargs, stripped from caller kwargs by `_sanitize_kwargs`. **(3) Breaker state must match the EVIDENCE, not the exit path.** The half-open probe re-arms the deadline as it claims the lapse, so only the probe's own outcome closes it — and reaching `_close_circuit` after the loop is not enough, because a consumer that disconnects after the first delta skips it and leaves a demonstrably reachable sidecar in the penalty box for another full cooldown. The streaming cleanup therefore closes the breaker (CAS against the observed generation, as always) when the turn YIELDED a flue delta before unwinding. The evidence is the yield and nothing else: `served_any` is set only inside the flue loop, a consumer that cancels before the first delta proved nothing and leaves the claim armed, and a one-shot never closes from cleanup at all (it yields nothing incrementally, so a cancelled await is not evidence flue answered). Pinned by `tests/test_brain_lane_failover.py` (`ci_safe`), whose load-bearing cases are the negative ones — the replay invariant, the four non-transport failure classes, the wire-2 route parity, the interrupted-consumer and cancelled-one-shot lines, and the guard-the-guard case where a probe that yielded nothing must NOT close the breaker.

### ZD118 Lazy lane context loader

- **Lane context can be LAZY: `context_loader`.** The Flue sidecar ignores `history` / `db_memory_context` / `portrait`, so a caller headed for Flue may pass an async zero-arg `context_loader` (returning those keys) instead of the values. `brain_dispatch` strips it from every Flue call (`_without_context_loader`) and resolves it only in `_fallback_streaming` / `_fallback_oneshot` — i.e. only when a lane that reads it is dispatched (configured core/legacy, circuit-open skip, failover hop). Only those three keys are merged, explicit kwargs win, a raising loader degrades to no context (never a failed turn), and `_drop_flue_only_kwargs`'s replay-isolation refusal still fires at call time. The voice brain turn uses it on the Flue lane (`routers/voice_tts._voice_brain_kwargs`, kill switch `ZOE_VOICE_MEMORY_PACKET_LAZY=false`), saving the ~500 ms packet gather per live turn. A lazy build on a failover hop must not eat the non-streaming lane's `ZOE_VOICE_CHAT_TIMEOUT_S` window: that lane awaits the brain through `_await_brain_with_packet_budget` (deadline extended by exactly the build's time), never a plain `wait_for`. Pinned by `tests/test_voice_memory_packet_lazy.py` (`ci_safe`).

### ZD119 Append only prompt prefixes

- **Prompt prefixes are append-only: mutate the tail, never the head.** llama.cpp reuses cached KV only up to the FIRST differing token, and exact common-prefix reuse is the only AFFORDABLE path on this box — a RAM-budget tradeoff, NOT an upstream limitation. `--cache-reuse` (KV-shift recovery from a partial divergence) is omitted from `llama-server.service` by CHOICE: #21468 was closed as fixed by #22288 and that fix is in our build (see `docs/knowledge/brain-kv-cache-tuning.md`), so there is no Gemma exclusion — `llama_kv_cache_iswa::get_can_shift()` merely requires `kv_base->get_size() == kv_swa->get_size()`, and SWA layers are sized by the 512-token window. `--swa-full` equalises them and re-enables it. It is now ON in the unit (replay-gated 2026-10-04, probe 18/18 OK, no latency regression), because the SWA cache growth is small on the live E4B at ctx 8192 + q8_0 K/V (≈ +150 MiB computed); the old ~50x (30 MiB -> 1,536 MiB) figure was **measured on Gemma E2B at a much larger context** and is not this box. `--cache-reuse` is therefore re-enabled as an option but stays OFF (optional, unmeasured). The other cache, `--cache-ram 1024` (halved from 2048 on 2026-10-04 because `--swa-full` halves each cached entry), is ALSO a prefix cache: `server_prompt_cache::load` (llama.cpp `tools/server/server-task.cpp`) picks among retained whole-prompt states by `get_common_prefix`, skipping candidates matching under 25% of their cached prompt — it widens the set of candidate prefixes but never makes a divergence cheap, and older states have older heads so they match a slid head no better. Prefix stability is therefore the precondition for BOTH caches. **`--swa-full` makes the in-slot KV complete, NOT the host cache's:** a state saved to `--cache-ram` (`llama_kv_cache::state_write` skips SWA-masked cells; `flags` is `GGML_UNUSED`) holds only the LAST 512 positions of the SWA layers, so a prompt that has left the slot and comes back from the host cache resumes only if the next prompt diverges from it within its last ~510 tokens — any deeper divergence is `first_cache_n=0`, a full re-prefill (measured 2026-10-12, `docs/knowledge/brain-prefix-cache-2026-10-12.md`). The slot is left by ANY other caller (`--parallel 1`), so **a background 4B call must hold `brain_slot_guard.background_slot(...)`** (`ZOE_BRAIN_SLOT_GUARD`, default on; `ZOE_BRAIN_SLOT_QUIET_S` 45, `ZOE_BRAIN_SLOT_MAX_DEFER_S` 240): it waits while a brain turn is in flight or ended under 45 s ago, then runs serially, and `run_flue_brain_streaming` brackets every turn with `turn_started`/`turn_finished`. Callers today: person_extractor_llm, latent_intent_detector, the per-turn digest, structural_reader, structural_verifier, memory_retire's judge; `tests/test_brain_slot_guard.py` pins the list. A NEW post-turn caller of `:11434` that skips the gate evicts the conversation again. All three citations were read in the RUNNING build, `~/llama.cpp` @ `f449e0553` (detached HEAD, matches the sha in `brain-kv-cache-tuning.md`): `src/llama-kv-cache-iswa.cpp:232-236` (`get_can_shift()`), `tools/server/server-context.cpp:2846-2855` (`can_cache_reuse` gate), `tools/server/server-task.cpp:1675-1700` (`server_prompt_cache::load`) — line numbers differ from the `~/.opensrc` upstream mirror, so cite the build path when re-checking. Hence keeping the system prompt byte-identical (`_ZOE_SOUL_STATIC`, with all per-turn memory/portrait/datetime in the USER message prefix) only pays off if the message AFTER it is stable too. `zoe_agent._compact_history` is the single history-window selector for both `run_zoe_agent` and `run_zoe_agent_streaming`: it pins the window head to a content-defined anchor so the head advances in occasional jumps instead of sliding every turn, and it ALWAYS opens on a user turn (Gemma has no system role — the template folds the system prompt into the first turn, so an assistant-led window folds it into a `model` turn). Do NOT "simplify" it back to a newest-N-that-fit walk — that walk moves the head every turn and re-prefills everything past the system prompt, measured 0% turn-over-turn prefix reuse versus ~56%. It deliberately keeps ~2.5 messages less depth (12.0 -> 9.5) to buy that. Pinned by `tests/test_zoe_agent_kv_prefix.py` (`ci_safe`), which renders fixtures through Gemma's actual template shape and whose negative control reimplements the old walk and asserts it FAILS. NOTE the co-dependent half is NOT fixed: `routers/chat.py` loads history as `ORDER BY created_at DESC LIMIT 12`, a window that itself slides two messages per turn, which bounds how long any anchor can survive — a deeper head (pinned oldest turns, or summarise-into-a-stable-head compaction) needs that query to supply more than the newest 12.
