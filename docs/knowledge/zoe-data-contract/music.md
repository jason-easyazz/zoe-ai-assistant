# zoe-data contract detail: Music, smart home and app connection

### ZD72 App connection handoff

- App-connection handoff (B7.5): `auth_handoff.py` (engine: status machine, `auth_handoffs` table from alembic 0031, secret-free `handoff_update` push + best-effort Pi `/wake`, Telegram send-to-phone via `ZOE_TELEGRAM_BOT_TOKEN`) + `routers/handoff.py`; see [docs/knowledge/app-connection-handoff.md](../../docs/knowledge/app-connection-handoff.md).

### ZD73 Telegram voice notes

- Telegram voice notes (flag-dark, 2026-10-04): `routers/telegram_media.py` — two INTERNAL contracts for the Telegram lane, mounted by `telegram_media.register(app)` in `main.py` ONLY when `ZOE_TELEGRAM_MEDIA` is on (off = routes absent, 404; pinned by `tests/test_telegram_media.py`). `POST /api/system/telegram/transcribe` (raw OGG/Opus body → ffmpeg decode to 16 kHz mono s16 WAV → `routers.voice_tts._transcribe_audio(path, capture=False)` → `{ok, text, duration_s}`) and `POST /api/system/telegram/synthesize` (`{text}` → `tts_waterfall._synthesize_kokoro_sidecar` → ffmpeg libopus → `audio/ogg`). **Never route Telegram audio through `/api/voice/transcribe`/`/turn`:** those broadcast `voice:transcript` to every panel and capture into the panel corpus; these do neither (capture only into the SEPARATE `ZOE_TELEGRAM_STT_CAPTURE_DIR` when set — never `~/.zoe-voice-samples`). Bounds: 8 MiB upload, `ZOE_TELEGRAM_VOICE_MAX_S` (60) measured on the DECODED audio (413), ffmpeg via argv subprocess with `ZOE_TELEGRAM_FFMPEG_TIMEOUT_S` (20) — never a shell; every failure is structured JSON. ffmpeg resolves `ZOE_TELEGRAM_FFMPEG` → PATH → `~/.local/bin/ffmpeg` (the unit's PATH lacks it). It only CALLS the voice helpers (Telegram STT serialises behind the panel's on `_moonshine_infer_lock`); no file in `VOICE_PATH_PATTERNS` changes, so the replay gate does not front it. Record: `docs/knowledge/telegram-voice-notes.md`.

### ZD74 Music setup bridge

- Music setup bridge: `music_service.py` (sole MA client) + `routers/music_setup.py` (QR→phone flow; its phone steps report to the handoff by token nonce, and `music_oauth.watch` / `ytmusic_signin.watch` report background outcomes; `setup_qr.py` serves the panel QR by a single-use handle (the touch card renews via `/start` on image error) so the setup token never lands in an access log). YouTube Music (`ytmusic`) requires MA's `po_token_server_url` to point at a local PO-token generator (the `ytmusic-potoken` bgutil service in `docker-compose.modules.yml`, :4416). `music_service` hides that field from the phone form and fills it server-side in `save_provider()`. URL override: `ZOE_YTMUSIC_POTOKEN_URL` (default `http://localhost:4416`). If the generator container is down, MA's ytmusic login fails, so it must run alongside `zoe-music-assistant`. The generator is **published on loopback only** (`127.0.0.1:4416:4416`) — it is unauthenticated, and every consumer is host-local (MA is `network_mode:host`; the healthcheck runs container-internally). Keep it that way: a bare `4416:4416` would let any host on the LAN mint YouTube tokens against Zoe's session (`tests/unit/test_potoken_loopback_bind.py` enforces this). A consumer on another host would need a real auth story, not a wider bind. `save_provider(provider, values, instance_id=None)` UPDATES the given instance in place when `instance_id` is passed (via `provider_instance_id(domain)`) — otherwise MA mints a duplicate on every save (a re-connect / cookie refresh must reuse the existing instance). **MA version switch (`ma_server_version()`, from MA's `/info`, cached per process with a TTL, dropped on any transport failure):** on MA ≥ 2.10 credentials live in setup-flow `setup_data`, and `config/providers/save` silently drops a cookie and refuses a new instance — so `save_provider` drives `config/providers/reconfigure` (re-auth, in place) / `config/providers/setup` (first connect) + `config/flows/submit`, `provider_setup_form` reads the flow's FORM entries (never `get_entries(provider_domain=)`, which 2.10 removed; free/OAuth providers start no flow because a zero-input `setup` CREATES the instance), `music_oauth` follows the flow's EXTERNAL step and takes completion ONLY from MA's `setup_flow_updated` WS event for its own flow_id (a finished flow leaves MA's registry at once, so polling cannot see FINISH and provider state is shared; no terminal event = failure + abort), and `get_recommendations` returns an empty shelf (one log line) because 2.10 removed `music/recommendations`. Credential writes (`save_provider`, `provider_setup_form`, OAuth start) re-read `/info` on entry and FAIL when it is unreadable — never guess the API; read-only paths use the cache, and an unknown version there takes the pre-2.10 path, byte-for-byte. Tests: `tests/test_music_ma_setup_flow.py` (fake 2.8.7 + 2.10.3 servers); music tests that stub the pre-2.10 API pin `_ma_info` to 2.8.7 so they stay hermetic on a box whose real MA is 2.10.

### ZD75 Smart home bridge

- Smart-home bridge: `smart_home_service.py` (sole HA MCP-bridge REST client for the Skybridge `smart_home` domain) — lists devices+scenes, toggles/dims devices, activates scenes via the bridge at `ZOE_HA_BRIDGE_URL` (default `http://127.0.0.1:8007`, same env the voice path's `intent_router._execute_smart_home_intent` uses). Device list = `/lights` (dimmable) + `/switches` + **`input_boolean` helpers pulled from `/entities`** (how a headless HA models a simulated home — the owner's real devices live here, NOT under `/lights`/`/switches`, which is why the card used to read empty); a display domain (light/fan/tv/switch) is inferred from the friendly name + mdi icon, and Zoe's own voice-satellite switches (`lva_*`, "zoe-touch", "thinking sound") are filtered out so only household devices show. Tiles carry an inferred `room` (name-word match) for a room-captioned grid; `get_climate()` adds a read-only current-temp + thermostat-setpoint strip (adjusting is deferred). Classified by `skybridge_service._classify_smart_home` (household-shared, NO identity gate — like clock/music); only entities returned by the live device list are ever controlled (the bridge 200s even on unknown ids). Every call is best-effort and never raises: a dead bridge degrades to a friendly offline `smart_home` card; a reachable-but-empty home is an inviting "ready to grow" card, not the offline one. **Add-a-device** (`action="add_device"`, classifier phrases like "add a device"/"set up a light"): a QR→phone flow (`smart_home_setup.py` HMAC single-use token + `routers/smart_home_setup.py` `/api/home/setup/qr/{handle}`+`/info` (token via `X-Setup-Token`, QR by `setup_qr.py` single-use handle — never a query-string token) + the branded `dist/setup-device.html` phone guide). The bridge exposes NO config-flow/discovery/pairing endpoint, so onboarding is honestly *guided* (steps per device type) — Zoe never fakes a completed pairing; full automation waits on a bridge pairing API. Doctrine: HA is a hidden organ — plain device names only, no "Home Assistant" jargon on the panel. The estate (`dist/touch/home.html`) renders the smart-home surface (its `rooms` screen) from this service's data; the old `skybridge-renderer.js` `renderSmartHome` card is retired with the Skybridge front-end.

### ZD76 Music browse surface

- Music browse surface (see-and-play your connected music): `music_service.search(query, media_types, limit)` returns hits grouped + normalized per media type (tracks/albums/artists/playlists/radio, each `{name, uri, media_type, artist, album, image}`; art bumped to a square via `_hi_res_art`, URI-less hits dropped) and `music_service.play_media(uri, player_id)` plays one picked result on a chosen player (queue_id == player_id; an explicit-but-unknown player fails loudly, no player falls back to the active/first-powered one). Both reuse the `_ma` client + args-nesting and never raise. MA/YT drops tracks on a combined query, so `search` fans out ONE `music/search` call per requested type. Endpoints `GET /api/music/search?q=&types=&limit=` + `POST /api/music/play_media {uri, player_id?}` (`routers/music.py`, session-free like the rest of the music proxy). The touch page `zoe-ui/dist/touch/music.html` (ds1, self-contained) IS this surface — the target of the now-playing card's "Browse" (`renderNowPlaying`, `data-route="/touch/music.html"`): connected-source chips (from `/available-providers`), live search, tap-to-play, speaker picker (`/players`), and a now-playing footer (`/now-playing` + `/control`).

### ZD77 Music radio and discovery

- Music radio mode + discovery (MA-native): `search_and_play`/`play_media` take `radio_mode: bool = False` (MA `player_queues/play_media radio_mode` — endless similar-tracks station, needs a SIMILAR_TRACKS provider like ytmusic); `set_dont_stop_the_music(enabled, player_id)` toggles MA's auto-continue (`player_queues/dont_stop_the_music`, MA rejects the enable without a SIMILAR_TRACKS provider → False); `get_recommendations()` (MA `music/recommendations` shelves, normalized to the flat search-hit shape) + `get_recently_played(limit, media_types)` (MA `music/recently_played_items`). Endpoints: `GET /api/music/recommendations`, `GET /api/music/recently-played?limit=&types=`, `POST /api/music/dont-stop {enabled, player_id?}`, and `radio: true` on `POST /api/music/play` + `/play_media`. Classifier: "play <seed> radio" → play with `radio_mode=True` (bare "play the radio" stays a normal search); "keep the music going" / "don't stop the music" / "play something like this" → `dont_stop` (checked BEFORE transport so it isn't read as a stop). All best-effort, never raise; tests in `tests/test_music_bridge.py`. **Read-back:** `now_playing()` surfaces `dont_stop` (the queue's `dont_stop_the_music_enabled`) beside `shuffle`/`repeat`, so a UI toggle renders true state on load instead of guessing.

### ZD78 Music Assistant idle reap

- **Music Assistant idle reap (flag-dark `ZOE_MA_IDLE_REAP`, default OFF; owner decision Q2 2026-10-04).** Off = byte-identical. On: `ma_ondemand.ensure_running()` `docker start`s a reaped `zoe-music-assistant` and waits for `/info` (bounded by `ZOE_MA_START_TIMEOUT_S`, default 25 s; MA serves ~3.5 s after start — the docker healthcheck is NOT the signal, its first tick can be 30 s out). `music_service._ma_response` wakes ONLY on `_MA_WAKE_COMMANDS` (explicit intent: search, play_media, playlists, favourites, provider setup); EVERY mutating service entry point (`control`/`seek`/`transfer`/`group_players`/`ungroup_player`/`search_and_play`/`play_media`/`queue_*`/`playlist_add`/`favorite_*`/`set_dont_stop_the_music`, `resolve_music` for every action but `status`, and `_ma_api_for_write()` — the credential-write funnel) calls `ensure_running()` first; `tests/test_ma_ondemand.py::test_mutating_route_table_is_complete` pins that every POST route in `routers/music.py` is either covered or explicitly local-only (`set_preferred_player`). All docker calls go through `async_subprocess.run_to_completion` (never a loop-thread fork), and every wake decision — cached, probed or started — runs under the shared file lock the reaper holds across stamp+stop; the cached "seen up" applies only to a REAL stamp (`_recently_up` treats the `0.0`/None sentinel as empty — `monotonic()` counts from boot, so a bare TTL compare read an empty cache as fresh for the first 30 s of uptime and the first wake after boot skipped the start). **Reads never wake MA** — the panel polls `players/all`+`player_queues/all` every 5 s and `music_history.observe_once` polls `recently_played_items` every 300 s; waking on those would undo every reap within seconds. Stamps in `ZOE_MA_REAP_STATE_DIR` (`~/.cache/zoe/ma-reap`): `activity` (any `player_queues/*`/`players/cmd/*` write), `inflight` (a wake in progress), `lock` (flock held across `docker start`→HTTP-up; the reaper takes the same lock before `docker stop`). The STOP side is `scripts/maintenance/ma_idle_reap.py` + `zoe-ma-idle-reap.timer` (scripts/AGENTS.md). Record: `docs/knowledge/music-assistant-idle-reap.md`. Pinned by `tests/test_ma_ondemand.py` (`ci_safe`, fake docker + fake HTTP; reads-never-wake and flag-off-touches-nothing are the negative controls).

### ZD79 Music favourites asymmetry

- Favourites are **asymmetric at the MA seam** — the trap to know: `music/favorites/add_item` takes a **uri**, but `music/favorites/remove_item` takes **(media_type, library_item_id)**. Adding a favourite forces the item into the library first, so `favorite_remove(uri)` resolves via `music/item_by_uri` and removes by the **library** row's id (the same ytmusic uri resolves `provider=ytmusic…` before and `provider=library` after — verified live on MA 2.8.7, state restored afterwards). An item with no library row was never favourited, so removal is a no-op returning **True**, not a failure. Endpoints: `POST /api/music/favorite {uri}` + `POST /api/music/unfavorite {uri}`. Note `now_playing()` deliberately carries **no `uri`**: favouriting what is on screen must take the uri from the queue item's `media_item`, never from now-playing. Tests: `tests/test_music_favorites_and_dontstop.py`.

### ZD80 Music discovery and journal

- Music discovery + listening journal: `music_history.py` (per-user `music_play_history` journal, alembic 0019) + `music_discovery.py` (taste seed, digarr-recommendations store, "Zoe Discovery" playlist bridge, `play_discovery` intent surface) + `scripts/maintenance/music_discovery_batch.py` (the ephemeral digarr container batch; see labs/digarr-spike/ for the engine verdict). **Attribution contract:** `zoe_user_id` is ALWAYS populated; the ONLY fallback point is `music_history.resolve_music_user()` — unidentified callers get the reserved `GUEST_USER_ID` ("guest", the kiosk-guest convention; an id constant, not a family-users row). Play-triggering callers thread the acting user (`resolve_music(intent, user_id)` from skybridge; the session-free `routers/music.py` proxy journals as guest by design). Guest history feeds the guest/household profile only — per-user profiles never mix in guest or other-user rows (`taste_seed(user_id=…)`). The batch builds the household playlist PLUS a personal "Zoe Discovery — <Name>" playlist per identified user with enough journal history (`music_history.users_with_history`, thresholds `ZOE_DISCOVERY_MIN_PLAYS`/`ZOE_DISCOVERY_MAX_USERS`); `play_discovery` resolves an identified requester to their personal playlist, else the household one. MA's playlog can't do any of this (single upserted row per item/user, 90-day retention, one MA-token user) — it's only a fallback seed. digarr is a HIDDEN engine: batch-only container (never resident, stopped+removed every run, memory + brain-idle gated), family only ever sees the playlist. Weekly cadence gated `ZOE_MUSIC_DISCOVERY` (default OFF; operator flips after a verified manual run); observed-events poll gated `ZOE_MUSIC_HISTORY` (default on, every `ZOE_MUSIC_HISTORY_INTERVAL_S`). Speaker-ID attribution for anonymous voice turns is Samantha-roadmap, not built.

### ZD81 YouTube Music sign in

- YouTube Music one-tap sign-in: `ytmusic_signin.py` — YT Music has no username/password and no OAuth; the only link is a browser login cookie containing `__Secure-3PAPISID`. `start_session()` spins up ONE phone-drivable rig (Xvfb + CloakBrowser headful + x11vnc on localhost + websockify/noVNC LAN-bound), returns `{session_id, view_url}`; a watcher polls the live browser's cookies and harvests → `save_provider("ytmusic", {username, cookie}, instance_id=…)` → tears the browser down. **Cookie present is NOT login happened** (live incident 2026-09-28: the persistent profile held a rotated, dead `__Secure-3PAPISID`, so every attempt "harvested" it in ~15 s, saved it, and tore the view down before the person opened it): at session start the watcher snapshots a one-way digest of the profile's `__Secure-3PAPISID`+`SID` and validates it (`_validate_cookie` — the youtubei `account_menu` POST with MA's SAPISIDHASH header, read through YouTube's own `logged_in`/`yt_li` flags; True/False/None). Signed in → saved at once (a real login); signed OUT → only the google.com/youtube.com cookies are cleared (`clear_cookies`, never the whole profile), the page reloads to the sign-in form, and the state is `stale_cookie_cleared` (phone text + the handoff card's `completing` detail via `watch(…, on_progress=…)`); inconclusive → re-judged every `_BASELINE_RETRY_S` (10 s), never harvested unverified meanwhile. After that the watcher harvests ONLY a cookie whose digest differs from the snapshot AND that validates True; a False verdict is not saved and does not tear down (the session stays up to `SESSION_TIMEOUT_S`); None retries next poll. `refresh_now()` also pushes only a cookie that validates True. `_report` awaits an in-flight stale notice before the outcome, so the handoff card never moves error → completing. CloakBrowser's per-launch pypi/github update check is disabled (`CLOAKBROWSER_AUTO_UPDATE=false`, setdefault). Pinned by `tests/test_ytmusic_signin.py`. Auto-timeout ~5 min (`ZOE_YTMUSIC_SESSION_TIMEOUT_S`). `refresh_now()` is the anti-expiry path: opens the persistent profile HEADLESS, re-harvests, re-saves in place, closes promptly (scheduled behind `ZOE_YTMUSIC_REFRESH_ENABLED`, default OFF, cadence `ZOE_YTMUSIC_REFRESH_HOURS` default 12, registered on the proactive APScheduler in `main.py`). Router endpoints (token-gated, ytmusic-only): `POST /api/music/setup/browser/{start,cancel}` + `GET /api/music/setup/browser/status`; the ytmusic catalogue entry's `auth` is `browser` so the phone page (`setup-music.html`) opens the embedded sign-in view instead of a cookie form. **Guardrails:** NEVER enter/request/store/log a Google password (the module only reads the cookie the browser already holds); the cookie is a SECRET — handed only to MA, never committed/logged in full (`_redact`); the persistent profile + secrets live under `$ZOE_YTMUSIC_SECRET_DIR` (default `~/.zoe-ytmusic/`, 0700, OUTSIDE the repo); ONE session at a time; raw VNC localhost-only (only noVNC is LAN-bound, and its WebSocket is refused pre-upgrade unless it carries the per-session secret — websockify `--token-plugin TokenFile` over `$ZOE_YTMUSIC_SECRET_DIR/viewer-token` (0600, deleted at teardown), the secret riding only in the view URL's `#fragment` as noVNC's `path`; never add a positional websockify target, which routes token-less clients straight to VNC); the browser is transient — torn down on completion, timeout, AND error, never left exposed.
