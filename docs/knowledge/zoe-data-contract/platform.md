### ZD13 Pi intent evidence JSONL

- Pi intent/hybrid evidence JSONL: `pi_intent_evidence.py` — every write goes through `_append_jsonl`, which holds an **exclusive `fcntl.flock` on the target across BOTH the append and the `_prune_jsonl` trim**. The trim is a read-modify-write (read all rows → `seek(0)` → rewrite → `truncate`), and `record_pi_hybrid_production_evidence` always passes a positive `max_records`, so the trim runs on EVERY write. Unlocked, concurrent writers silently lose records — `pi_hybrid_production.try_pi_hybrid_production`'s fast-accept branch has two (the awaited accepted-decision write and the fire-and-forget `_schedule_pi_audit_after_fast_accept` audit write, both via `asyncio.to_thread`), and the lane is SCORED on this evidence. Keep the inode (never rename/replace the file — flock follows the open file description, not the path), and keep `_prune_jsonl` lock-free so it can't deadlock against its caller's hold. Pinned by `tests/test_pi_intent_evidence.py::test_append_jsonl_does_not_lose_records_under_concurrent_writers` (`ci_safe`).

### ZD15 Browser broker text extraction

- Browser surface: `browser_broker.py` — plan/executor registry over ONE Zoe-native CloakBrowser surface (stealth Chromium, Playwright-compatible; `zoeCloak`, with `hermesCloak`/`harness` as execution aliases). Two output modes, and the mode is chosen by the PLAN ACTION: any action returns a base64 PNG (`image_base64`), **except** `extract_text`/`fetch_text`, which return page TEXT and deliberately skip the screenshot. Text mode is opt-in precisely so existing callers (chat.py research screenshots, the MCP browser tool) are byte-identical — pinned by `tests/test_browser_text_extract.py`. Extraction is `extract_main_text(html) -> ExtractedText`, a **pure stdlib function** (`html.parser`, no `readability`/`bs4`/`lxml` — none are declared deps here, so requirements.txt is untouched) doing readability-lite main-content selection: drop-list for `script`/`style`/`nav`/`header`/`footer`/`aside`; then the semantic shortcut over `<article>`/`<main>` containers clearing the 200-char floor — a `<main>` wrapping a qualifying `<article>` is DROPPED first (it always holds more text than the article inside it, so pure length could never pick the tighter node and the shortcut returned article + related-cards), then longest wins among the survivors. The drop is deliberately wrapper-shaped and NOT "any ancestor": `<article>` inside `<article>` is the spec's idiom for COMMENTS, and demoting the parent there would return one comment and discard the post; then container scoring by text volume discounted by **quadratic** link density plus a deepest-near-tie tie-break — linear discounting lets the outer wrapper beat the article by a hair and drags every nav/footer line in with it. Every tree walk is ITERATIVE (explicit stack, `_BLOCK_END` sentinel for the post-order newline): page depth is publisher-controlled, a recursive render raised `RecursionError` at ~1000 nested elements, and nothing on the text path catches it — pinned by `test_a_deeply_nested_page_extracts_instead_of_raising`. It reports its own `strategy` (`semantic:<article>` | `scored-container` | `fallback:whole-document` | `empty`), which is what the tests assert on. Callable three ways: the pure function (the offline test seam), `await fetch_page_text(url)` in-process, or `await execute_text_extraction(broker, url=…)` through the normal plan pipeline. Both live paths SSRF-guard via `assert_public_url` + `guard_browser_page` and return `{"ok": False, "error": …}` rather than raising, so a failed enrichment degrades a search packet instead of breaking the turn. NOT a voice-path file (verified against `voice_gate_check.VOICE_PATH_PATTERNS`) — no replay gate.

### ZD16 Agent security helpers

- Agent security helpers: `agent_safety.py` — the single home for the bash-tool shell-injection guard (argv parsing, no shell) and the SSRF guards: `assert_public_url` (web fetch), `assert_panel_host` (panels = private-LAN only; loopback/link-local/metadata/public always rejected, allowlist narrows but never bypasses), `guarded_urlopen` (validates + **pins the connection to the validated IP**, defeating DNS-rebinding), and `guard_browser_page` (Playwright `page.route` that validates every request/redirect hop pre-connect). Stdlib-only so it loads in slim CI.

### ZD70 Typed env parsing

- Typed env parsing: `typed_env.py` — the ONE canonical parse per type (`env_str/bool/int/float/list`), read at CALL time (never an import snapshot), unparseable → default + one journal warning. New env reads use it; existing reads migrate per the Wave-4 packet (`docs/architecture/chat-split-and-typed-config-plan.md`, byte-equivalence rule — never silently change a site's parse). It is parsers only: no key registry, and `gemma_base()` stays the sole `GEMMA_SERVER_URL` accessor.

### ZD112 requirements txt is a spec

- **`requirements.txt` is a DECLARED SPEC, not an installed manifest — upgrade the BOX first, the FILE second.** Nothing installs it (audited 2026-08-06 across every workflow, script, unit, compose file and doc): the service runs host-native from `/usr/bin/python3` against `~/.local/lib/python3.10/site-packages` installed out-of-band; `deploy.yml` installs its OWN hardcoded 9-package list (six unpinned, so they float on every deploy); the `Dockerfile` that `pip install -r`s it has no compose service and is dead; `voice_gate_check.py` reads the path only as a change-detector. **Consequence: editing a version here changes no executed byte, so a green voice-gate on a dependency PR is not evidence about the bumped packages** — it cannot be, they are never loaded. A pin edited ahead of the box is a wish, not an upgrade; install on the host, verify, then record it here. Drift is detected rather than assumed by `scripts/maintenance/requirements_drift_check.py`, which runs reporting-only on the Jetson lane (`self-hosted-tests.yml`) — the only host where the answer means anything — with its comparator negative-controlled offline in `tests/unit/test_requirements_drift_check.py`. Declare what the code IMPORTS even when it arrives transitively (`onnxruntime` was an undeclared voice-path dependency of `voice_vad.py`/`voice_turn.py` until 2026-08-06); mark a genuinely optional package `# drift-optional: <reason>` so its absence reads as INFO, which never excuses a version mismatch. Wiring a real `-r` install into the deploy path is an OPERATOR decision, not a drive-by: it would hand every merge the power to change a live voice box's runtime. **`requirements-py312.txt` is the one deliberate exception**: it is the INPUT that `scripts/setup/build_py312_venv.sh` installs into the B0.7 Python 3.12 venv (`~/.zoe/venvs/zoe-data-py312`), so there the file is the installer and the venv is the artifact — pins identical to the box wherever a cp312 wheel exists, Resemblyzer in a `--no-deps` second phase, torch pinned to the exact CPU wheel URL. Drift for that venv is the same `requirements_drift_check.py` run with the venv interpreter. **Once the cutover drop-in (`scripts/setup/systemd/zoe-data.service.d/60-py312-venv.conf`) is loaded, `deploy.yml` INSTALLS `requirements-py312.txt` on every deploy** (`build_py312_venv.sh --refresh`: both phases, `--offline` first) and runs Alembic with the venv — so from then on a pin edited there DOES change the live runtime at the next deploy, and that file is a voice-path pattern (replay-gated at PR and at deploy). Which interpreter the deploy feeds is read from systemd by `scripts/deploy/zoe_data_python.sh`, never from whether the venv exists; `requirements.txt` stays the 3.10 spec and keeps its box-first rule. Every package exact-pinned in both manifests must carry the same version (`tests/unit/test_zoe_data_py312_cutover.py`; a deliberate 3.12-only step-up is recorded in its `STEP_UP_DIVERGENCE`). Runbook (measured wheel table, drop-in switch, gates, rollback): `docs/knowledge/python-312-venv-migration.md`. Both manifests now declare `prometheus-client` and `livekit-protocol`, two direct imports that only ever arrived transitively (found by that venv build).

### ZD114 Executor board single seam

- **The engineering-board executor has ONE seam: `executors/kanban_adapter.py::_run`.** That method is the adapter's only coupling to an executor, and it dispatches on `ZOE_KANBAN_BACKEND` — code default `executor` (`executors/executor_queue_backend.py`, serving the same six verbs `list`/`show`/`create`/`block`/`archive`/`complete` against Multica's own `agent_task_queue` + `activity_log`) — or `hermes` (the retired-path `hermes kanban` CLI, still selectable as the one-env-var revert: `ZOE_KANBAN_BACKEND=hermes` + restart; note UNSETTING the variable keeps `executor`). **Do NOT rebuild or "clean up" `kanban_adapter.py`** — it encodes twelve PRs of discovered failure modes (stranded chains #592/#597, finish-without-shipping #520, PR-URL handoff #601, blocking verifiers #607/#632, flaky reviewers #672/#677, closeout-without-merge #679/#681, zombie workers #685, no-op implements #694); rebuilding means rediscovering all of it. A new executor plugs in at the seam, never by editing the phase/gate logic. Two rules bind the backend: it must return the exact row/detail fields the adapter reads (`id/title/body/status/block_reason/result/workspace_path` + `idempotency_key`; `task/latest_summary/comments/runs/events/metadata`), and **every transition must write a non-empty reason to `activity_log` in the same transaction as the status change** — an empty reason raises, because Hermes recorded `blocker_reason` 0 times across 128 blocked tickets and that silence cost weeks. Multica's schema is third-party: never alter it (create-idempotency uses an advisory lock, not a new index). Gate: `scripts/maintenance/verify_executor_queue_backend.py`. Plan: `docs/architecture/multica-executor-migration.md`.

### ZD115 Application logging setup

- Application logging is configured in exactly ONE place: `logging_setup.configure_logging()`, called from the `main.py` lifespan. Do not remove the call and do not add a second root-logger configuration. Background: uvicorn starts `main:app` with no `--log-config` and configures only its own loggers, so before this existed the root logger had **no handler** — every `logger.info()` in the service was silently discarded, and WARNING/ERROR fell through to `logging.lastResort`, which has no formatter and therefore emits **undatable** lines. That blackout is why runtime questions here have historically needed database forensics. Tuning is env-only (`ZOE_LOG_LEVEL`, `ZOE_LOG_DIR`, `ZOE_LOG_MAX_BYTES`, `ZOE_LOG_BACKUP_COUNT`); the handler rotates because systemd's `StandardOutput=append:` never does. Configure in the **lifespan, not at module import** — 10+ test modules import `main`, and configuring at import wrote test noise into the operator's real `~/.zoe-logs`. Pinned by `tests/test_logging_setup.py`, whose first test asserts the *broken* behaviour so the rest cannot pass vacuously. **Volume rules (2026-10-04 log review, `docs/knowledge/log-review-2026-10-04.md`):** the root JSON `StreamHandler` from `middleware.logging.setup_json_logging()` also writes every INFO record to stderr, and `append:` logs never rotate — so a new per-request/per-poll `logger.info` costs bytes in THREE places. Healthy kiosk polls log at DEBUG via `middleware.logging.is_quiet_poll()` (+ the `uvicorn.access` filter); add a new poll endpoint to `DEFAULT_QUIET_POLL_PATHS` (or `ZOE_LOG_QUIET_POLL_PATHS`). httpx/httpcore/apscheduler-executor are capped at WARNING in `logging_setup`. A call to a dependency that can be down on a poll loop logs through `log_throttle.log_upstream_failure()` (one throttled line, no traceback; real bugs keep theirs) — never `logger.exception`/`exc_info=True` in a poll path. Never log credential material (use `auth._session_digest`) or reply/utterance text in a trace. The two systemd-captured streams are bounded by `scripts/maintenance/rotate_service_logs.py` (`zoe-log-rotate.timer`, operator install). Pinned by `tests/test_log_noise_2026_10_04.py` + `tests/unit/test_rotate_service_logs.py`.

### ZD154 DB pool hardening

- DB pool hardening (post 2026-07-12 pool-exhaustion outage): every `db_pool` acquire is BOUNDED (`ZOE_DB_ACQUIRE_TIMEOUT_S`, default 10s) and raises `PoolExhaustedError` ("db pool exhausted — possible connection leak") instead of hanging; pool size/in-use/free are exported as `zoe_db_pool_*` gauges (updated on each acquire/release, fail-open); `/health` probes `db_pool.check_pool_health` (2s bound, verdict cached ~5s) and returns 503 ONLY on a genuine acquire timeout — every other condition fails open because /health consumers (watchdogs, deploy checks) restart the service on 503. Pinned by `tests/test_db_pool_hardening.py`.

### ZD155 Write path exception logging

- **Write-path DB exceptions log at WARNING+.** An `except Exception` guarding a SQL `INSERT`/`UPDATE`/`DELETE` must never end in bare `pass` or `logger.debug` — a swallowed write is a silent "Zoe forgot" with green health, the failure mode behind the FK trilogy (#1282) and the invisible pool leak (#1258). Log at `warning`/`error`/`exception` with enough context to diagnose (which write, which user/person, the exception). This is about VISIBILITY, not control flow: best-effort writers keep swallowing (a failed extraction must not break a turn) — they just say so. The Postgres→SQLite dialect-fallback `except` (the inner handler that retries the `?` param style) is dispatch, not a failure, and stays quiet. Enforced by `tests/test_write_path_exception_scan.py` (`ci_safe`, stdlib AST, sibling of `test_get_db_leak_scan.py`): modules join `WRITE_PATH_MODULES` as they are burned down; genuinely-harmless swallows need an `ALLOWLIST` entry with a one-line reason (today only `ui_layouts`, a self-healing compose-hint cache). `routers/voice_tts.py` is NOT yet listed — it is voice-runtime, so its handlers need the replay gate first.

### ZD166 No fork on event loop

- Background loops must not fork on the event loop thread. `asyncio.create_subprocess_exec` forks synchronously on the loop; in this large multi-threaded process a fork can deadlock pre-exec and freeze the whole API (live outage 2026-06-29: one wedged `hermes kanban` spawn made every endpoint, `/health` included, time out for days). The two safe patterns are centralised in `async_subprocess.py`: `run_to_completion` (spawn+communicate+timeout+kill entirely inside a thread pool via `subprocess.run`) and `spawn_pipe_process` (off-loop `subprocess.Popen` fork+exec, then wrap the already-open pipe fds in asyncio stream transports via `connect_read_pipe`/`connect_write_pipe`, which don't fork, so the rest of the worker keeps its async stdin/stdout interface). Prefer these for any new spawn — a coroutine-side `wait_for` alone cannot fire when the loop thread itself is blocked, which is why the fork must happen off-loop. Run-to-completion sites: `executors/kanban_adapter.py`'s `_spawn_cli`, `tts_waterfall.py`'s `_spawn_tts_cli` (espeak-ng/ffmpeg TTS fallbacks), `pi_intent_classifier.py`'s print-transport governor (`run_to_completion`), and `intent_router.py`'s `_run_mcporter` (MCP fallback subprocess). Long-lived streamed sites: `pi_intent_classifier.py`'s Pi RPC governor worker (`async_subprocess.spawn_pipe_process`) and `zoe_core_client.py`'s Pi RPC brain subprocess (its own `_spawn_pi_process` — a pre-existing specialised copy of the same logic; a follow-up may migrate it onto the shared helper).

### ZD167 Guarded subprocess and fetch

- The bash tool runs commands via argv (`create_subprocess_exec`), never a shell. Outbound fetch/browser tools and panel proxies must route through `agent_safety`: HTTP fetches use `guarded_urlopen` (IP-pinned, env proxies ignored), Playwright pages must `await guard_browser_page(page)` before any `goto` (per-hop pre-connect validation), panel hosts go through `assert_panel_host`, and panel-display navigation (e.g. `panel_browser_screenshot`) goes through `assert_panel_url` (LAN-panel-only). Don't reintroduce raw `create_subprocess_shell`, unguarded `urlopen`, or a `page.goto` on a user URL without the route guard. Validating `page.url` only AFTER `goto` is insufficient — the request was already sent.

### ZD176 HA media target resolution

- HA media target (`intent_router._resolve_media_player_entity(ha_url, room=)`): `ZOE_DEFAULT_MEDIA_PLAYER` is operator config and may be stale; order = configured id when HA lists it and it is not `unavailable` → an available player matching the intent's `room` slot (entity id / friendly name / area) → any available player (one warning per configured id naming the real entities; inventory cached 5 min) → `None`, and the music intents then answer `_NO_PLAYER_MSG` instead of driving the wrong speaker; a bridge-list failure keeps the configured id; `media_player.all` skips the lookup.
