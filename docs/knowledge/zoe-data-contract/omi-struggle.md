### ZD100 Omi pendant recordings

- **Omi pendant recordings (flag-dark): `omi_recordings.py` + `routers/omi_recordings.py`, migration `0045`.** `ZOE_OMI_SYNC_ENABLED` (default OFF; off = routes absent, no loop) + `ZOE_OMI_OWNER_USER_ID` (the LEGACY single owner while `ZOE_OMI_DEVICE_OWNERS` is off — unset = uploads 503; with the registry on it is only the one-time seed). "Record on the pendant, sync when in range": the Pi service (`services/omi-sync`) uploads each recording; `store_recording` answers `ok` + the echoed SHA-256 ONLY after the WAV is fsynced and the row inserted (that answer lets the Pi free the pendant's ring — see `routers/AGENTS.md`). Idempotent by `(user, device, key)`; a deleted recording leaves a content-free tombstone so a Pi retry is acknowledged, not resurrected. A background `run_loop` transcribes with the EXISTING Moonshine (`routers.voice_tts._transcribe_audio(capture=False)`, ~20 s chunks cut at the quietest point, silence skipped), and defers to `may_transcribe_now`: never in the night window (household-local 02:30–04:30 OR the `WINDOW_OPEN` marker), never within 45 s of a voice turn (a NEW recording also waits for `ZOE_OMI_IDLE_S`, default 120 s of panel quiet), never under `ZOE_OMI_MIN_MEM_MB` (default RAM floor to START a recording, measured — see `docs/architecture/omi-integration-plan.md` 4.3a — 800 MB; a RUNNING job yields only below half of it and WAITS OUT a transient closure up to 5 min rather than aborting, because an abort re-transcribes every chunk from zero). The WAV is streamed from disk (`iter_wave_chunks`) — never read whole. Deferral is visible: `OMI_TRANSCRIBE_DEFERRED reason=… avail= floor= backlog=` at INFO (≤ once per reason per 10 min, only with a backlog) and `transcription{backlog,transcribing,deferred,reason,since,…}` on `GET /api/omi/recordings` (counts/codes only). `transcribe_pending` enforces `audio_expires_at` at CLAIM time too: a pending row past its retention (judged at each claim's own clock, not the pass's start) is never transcribed — it is marked `failed` with its WAV removed (`OMI_EXPIRED_AT_CLAIM`) and the pass takes the next row; the claim UPDATE re-checks it. The WAV is deleted right after transcription unless `keep_audio` (`ZOE_OMI_KEEP_AUDIO` / PATCH) or, with `ZOE_OMI_KEEP_AUDIO_FOR_TAGGING` (default OFF), the voices were split and a line still needs a name (other / unsure / mixed, untagged, not marked not-a-person): then it is held so the member can play a clip on the Pendant page, and `release_tagged_audio` drops it the moment nothing in it needs a name (after each tag route, and hourly in `run_retention_loop`, which also releases every such WAV once the flag is off); `ZOE_OMI_AUDIO_RETENTION_DAYS` (default 7) bounds any WAV that remains. An EMPTY transcript keeps its WAV (`empty_transcript`); the `OMI_EMPTY_TRANSCRIPT` reason reads transient-robust levels (`measure_wav`: `clipped`, `rms_median`, `active_s`) and says `transient_only` for a click over a quiet room (the pendant's mic-wake transient, plan 4.3b) — a LABEL, never a gate. Held `empty_transcript`/`failed` rows with their WAV still on disk are requeued by `requeue_held` (owner: `POST /api/omi/recordings/retranscribe`, `/{id}/retranscribe`) and ONCE per `TRANSCRIBE_PIPELINE` value by the loop (marker `<ZOE_OMI_AUDIO_DIR>/.transcribe-pipeline`) — bump it with any transcription/diagnostic change; retention is never extended. **The transcript is unverified and unreviewed (`speaker_state='unverified'`, `reviewed=0`): NOTHING else may read `omi_recordings` — no fact extraction, recall, digest or prompt** (`test_nothing_else_reads_pendant_transcripts` is the static guard; the only other mentions are the main.py mount/loop, the two forget hooks, `omi_devices.py`'s device-id/user-id seed read and `omi_day_review.py`, which only PROPOSES candidates the owner approves). Forgetting: `MemoryService.delete_user` → `forget_user` (tombstones everything), the forget cascade → `erase_entity` (redacts the name, drops that recording's audio); both take `user_erase_gate`. The sync notice is the existing `notifications` row + `notification_created` broadcast. Voice path untouched — no `VOICE_PATH_PATTERNS` file changes.

### ZD101 Pendant ownership registry

**Pendant ownership (flag-dark `ZOE_OMI_DEVICE_OWNERS`, default OFF; `omi_devices.py`, migration `0047`, table `omi_devices`).** Table choice: `omi_devices`, not a general `ble_device_owners` — ownership only matters to recording attribution, which is Omi-specific; generalise when a second owned device type exists. ON: an upload is attributed ONLY to the owner the registry names for `X-Omi-Device` (16-hex `device_hash`, identical to Settings > Bluetooth's `device_id`) — never the panel's bound/signed-in user, never `ZOE_OMI_OWNER_USER_ID`, never an admin; an unassigned/inactive/unknown pendant gets 409 `device_not_registered` (the Pi keeps the audio and retries slowly), and `store_recording(registry=True)` re-checks the owner INSIDE the member's erase gate so an erase or reassignment between lookup and write wins. Viewing (GET/PATCH/DELETE) = any signed-in non-guest HUMAN member, own rows only (every query filters `user_id`; no admin override; a device token — even one bound to a member — is refused). Admin API (`/api/omi/members|devices`, HUMAN admin only, device tokens refused like Settings > Bluetooth) assigns/reassigns/unassigns; a reassignment moves NO existing recording (rows keep the `user_id` they were stored under; ownership is resolved at upload time, so audio still on the pendant or the Pi spool goes to the new owner), and every change is audited fail-closed to `ZOE_OMI_AUDIT_PATH` (default `~/.zoe/omi-audit.jsonl`, 0600; no audit line = no change). The registry API never lists recordings or counts. Seed: with `ZOE_OMI_OWNER_USER_ID` set and exactly one pendant ever uploaded under that owner, that pendant is registered to them once; any existing row (even unassigned) blocks a re-seed, so neither an unassign nor an erase is undone by a restart. Erase: `omi_recordings.forget_user` (called by `MemoryService.delete_user`) also unassigns the member's pendants and scrubs them from `registered_by` (committed after the recordings so an un-migrated registry never blocks erasing audio). The sync notice goes to the pendant's owner only (`device` in the body; rate-limited per owner). Pinned by `tests/test_omi_device_owners.py`.

### ZD102 Omi speaker turns voices

**Speaker turns + learned voices (flag-dark; `omi_diarize.py`, `omi_voices.py`, `routers/omi_voices.py`, migration `0055`; design `docs/architecture/memories-space.md` 2.4 / 2.6 / 3, record `docs/knowledge/omi-voice-tagging.md`).** `ZOE_OMI_SPEAKER_TAG` = off (DEFAULT) | shadow | on: inside the SAME transcription claim and gate, before the WAV is unlinked, Silero VAD regions → 2 s / 1 s-hop windows embedded by the panel's OWN pinned ResNet34 INT8 file (`scripts/setup/zoe_speaker_resnet34.py` loaded by path, sha256 + centring pin + self-test, the COMMITTED artifacts JSON; ONE ORT thread and BLAS pinned to one thread via `threadpoolctl` — the numpy fbank otherwise burns every core; model loaded per pass and released, +41 MB measured) → centroid-linkage turns, labelled against the wearer's own consented panel profile in that model (`you` / `other` / `unsure` / `mixed`; no profile = `unverified`); a line or an unknown voice the member marks "not a person" (`not_person` = zoe / tv / radio / media; later matching lines are marked on arrival; `omi_voices.zoe_spoken_spans` is the seam for Zoe's own replies, empty until TTS playback is logged with wall-clock times) leaves suggestions and the day review. Moonshine (unchanged) then transcribes EACH TURN on its own (text aligned to speakers without word times); off = byte-for-byte today's path. Segments land before the row says `done`; a tagger failure is `speaker_state='untaggable'` and never costs the transcript; a child's pendant (not positively adult, `manner_block.eligible`) is not tagged. `ZOE_OMI_LEARN_VOICES` (default OFF) holds the embedding of `other` / low-margin `unsure` turns (never the wearer's `you`) for 14 days, files it under an unknown voice of THAT member (`omi_voice_clusters`), and suggests a learned voice (`suggested_person_id`, NEVER a tag). The member's tag (`tagged_person_id` + `tag_source`) creates or links THEIR OWN `people` row (`visibility='personal'`, name field `provenance=entered_by_member`, `provenance_ref=omi_tag:<id>`) and, when learning is allowed and the person is not (possibly) a child, feeds `learned_voiceprints` via `learned_voiceprint_segments` (rebuildable mean, leave-one-out outliers). **Never auth:** only the allow-listed modules may name these tables (`test_no_auth_identity_or_session_path_can_reach_a_learned_voice`). A correction un-learns: re-tagging a line moves its contribution from the old person's voiceprint to the new one's (old print rebuilt, or dropped when empty), and marking a tagged line not-a-person, or correcting it to "you", untags it and removes its contribution. Erasure: deleting a recording drops its segments and contributions and REBUILDS the voices it fed (voice cleanup runs BEFORE the tombstone, so a failed delete is retryable); `forget_user` drops every voice row and FAILS CLOSED (`omi_recordings.VoiceEraseIncomplete` after the audio erase, surfaced by `MemoryService.delete_user` as `MemoryServiceError`, never reported as forgotten); "forget <name>" → `contacts_store.forget_voiceprints` → `omi_voices.purge_people` (voiceprint, contributions, tags, suggestions); `erase_entity` redacts turn text; `omi_recordings.run_retention_loop`'s `sweep` (hourly, started by `main.py` whatever `ZOE_OMI_SYNC_ENABLED` or the learn flag say, so biometrics and WAVs still expire with sync off) expires embeddings / clusters / provisional voices (30 d) / idle confirmed voices (365 d) and purges soft-deleted people. The nightly backup carries no row data of the four biometric tables. **The day review reads `omi_voices.review_segments` only** (confirmed tags, never suggestions; a model-only speaker label counts only when `ZOE_OMI_SPEAKER_TAG=on`, in shadow it reads `unverified`), through `omi_day_review.voice_segments` + the adapter `segment_map` (you -> you; someone_else and a tagged person -> someone_else; not_sure / unverified -> not_sure; not-a-person lines dropped — a recording that HAS segments is read turn by turn even when nothing is left, so an excluded TV/Zoe line never comes back from the joined transcript; a recording with none keeps the joined transcript; an unreadable segment read stops the day BEFORE the claim, a missing 0055 table is the joined path); facts about a tagged person reach memory only as approved day-review candidates. Hardening: a PATCH carrying both `not_person` and `owner_label` is a 400 that applies nothing; a "no" on a suggestion moves the rejection count only of a print still learning; forgetting or expiring a voice withdraws only the suggestions whose `omi_segments.model_id` has no print left for that person (a suggestion with no model goes too); `scripts/perf/omi_voice_calibrate.py` keeps ONE variant (farfield preferred) per source clip, so thresholds derived before 2026-10-18 must be re-derived (`docs/knowledge/omi-voice-tagging.md`). Pinned by `tests/test_omi_voices.py` (negative controls in its docstring).

### ZD103 Pendant day review

- **Pendant day review, Phase 1 (flag-dark): `omi_day_review.py` (analysis, no writes) + `omi_review_apply.py` (the ONLY writer) + `routers/omi_day_review.py`, migration `0054`** ([design](../../docs/architecture/memories-space.md) sections 4-5). `ZOE_OMI_DAY_REVIEW` = off (DEFAULT; a typo is off) | shadow | on (`on` is reserved for the next phase's first-turn mention; both analyse + serve the API). For a member's PAST household day of `done` recordings it proposes candidates (calendar_event, list_item, reminder, follow_up, person, owner_fact) into `omi_day_candidates` (payload, exact quoted evidence + recording ids, confidence, `speaker` in the omi_segments vocabulary you | someone_else | not_sure, `speaker_state`, `provenance=pendant`, status pending -> approving -> approved | dismissed); counts in `omi_day_reviews`; analysed recordings get `omi_recordings.day_review_id` (`reviewed` stays the owner's flag). Model points, code decides: broadcast stretches (cue words, whole-recording rule), Zoe's own voice and the enrolment script are dropped before the model; every candidate must cite chunk ids with an exact quote; `heard_from=media` drops; actions need a first-person + intent cue; an owner fact must be first-person-singular, durable, not reported speech, not `someone_else`, not identity, not restraint-sensitive; a person needs an interaction cue and is never the owner's own name; dates use `reminder_service.normalize_due_date` anchored at the moment said, past dates drop; FLOORS from the first live shadow run (2026-10-18): a list item / reminder / follow-up / event title with no content word left after stopwords and generic verbs ("that", "it", "look", "forget it") or only a generic noun (a bare "meeting") drops as `vague`; a person whose name is a pronoun, stopword or sentence-initial filler ("She", "Then") drops as `bad_person`; a person's relation is stored ONLY from "my <relation>, <Name>" / "<Name>, my <relation>" ("I'm X's son" makes X the parent, so the model's own `relation` is never trusted and the person is stored with an empty one); an action line that reports speech ("I said I'll ...", "I was like I'll ...") drops as `narrative`; owner facts of one day with high token overlap AND the same predicate classes and polarity (`fact_predicate`: "I like coffee" / "I hate coffee" / "I don't like coffee" never merge) merge into one candidate with both quotes (`near_duplicate`); dedup per `(user, day, dedup_key)` (`ON CONFLICT DO NOTHING`) plus pending-elsewhere / known contact / on the list / on the calendar; the forget ledger is checked before storing and fails CLOSED there too (an unreadable ledger stores nothing, releases the claim and leaves the day for a retry). FLOORS (gap audit P0-3): a line with ANY `distress_handoff.detect` tier is left out with the conversation around it (+/- 8 lines of that recording; no model call, no candidate); an owner fact also passes `own_words.analyze` (no quoted or read-out speech); at APPROVAL the distress check and the forget ledger run again (a forgotten name deletes the candidate, 410; an unreadable ledger refuses the write, 503) and an owner fact that contradicts any approved row at or above user_stated is `held_conflict`, never written (trust order user-stated > confirmed > inferred; the scan is `_protected_conflict(strict=True)`, so an unreadable index writes nothing); `MemoryService.delete_user` runs `omi_day_review.forget_user` BEFORE its memory lock (an approval writes under the erase gate and its ingest needs that lock) and fails closed if it cannot erase them (a missing table or no database is nothing to erase); every evidence entry records `clock` (the recording's time_quality) and `tz` (the household zone `day_local` was cut in). LANES (`ZOE_OMI_DAY_REVIEW_LANE` night | day | both, default both): NIGHT = the night window's best-effort last job `omi_day_review` (`scripts/maintenance/zoe-omi-day-review.py`, 12B; no time/timeout never fails the night); DAY = `run_loop` here, the resident 4B only, past days after 05:00, panel idle `ZOE_OMI_DAY_REVIEW_IDLE_S` (600), MemAvailable >= `ZOE_OMI_DAY_REVIEW_MIN_MEM_MB` (1000), no busy llama-server slot, outside night hours; every call STREAMS and is dropped on a voice turn (the day is retried from scratch). `ZOE_OMI_DAY_REVIEW_MAX_CALLS` (8), `_MAX_AGE_DAYS` (7). Approval writes through `calendar_service.create_event_record` (personal, provenance `metadata`), `list_service.add_item_to_list` (follow_up -> the personal `tasks` list, D5 pending), `reminder_service.create_reminder_record`, `contacts_store.ensure_person` (personal row), `MemoryService.ingest(source=origin="omi_review")` (`memory_authority` class `user_confirmed`, add-only); a failed or `None` write returns the candidate to `pending` with `write_error`. Forget: `erase_entity` (cascade step `omi_day_review`), `forget_user` (`delete_user`) and `forget_recording` (`omi_recordings.delete_recording` calls it BEFORE its tombstone: pending candidates of that recording are deleted, an approved one keeps only its `written_ref`). Seam for the next phase: `pending_counts(user_id)`. Pinned by `tests/test_omi_day_review.py` (synthetic transcripts only).

### ZD104 Pendant health warnings

- **Pendant health (gap audit P0-2; `omi_health.py`, `routers/omi_recordings.py`, migration `0056`, table `omi_device_health`; record [`docs/knowledge/omi-pendant-health.md`](../../docs/knowledge/omi-pendant-health.md)).** The panel Pi's `POST /api/omi/device-status` (DEVICE TOKEN only; body `extra=forbid`, numbers/bools/one short firmware token, NO audio, transcript, address or free text) is stored as ONE latest row per pendant under the owner the registry (or the legacy configured owner) names for the device id, never the panel's session; an unregistered pendant is 409 and stores nothing. `overwritten_delta` derives "overwritten since the last report" from the pendant's ABSOLUTE counter (first report = baseline), so a repeat cannot double count. `GET /api/omi/health` is OWNER-ONLY like the recordings (the pendant's CURRENT owner is re-checked at read time; a device token never reads; no admin override) and evaluates `evaluate()` live: `overwrite` (72 h), `no_sync` (> 36 h while the Pi reports), `ring_fill` (> 75 %), `battery_low` (< 20 %), `bridge_silent` (Pi silent > 3 h; mutes `no_sync`). A warning becomes ONE bell `notifications` row (type `omi_health`, 6 h re-notify cooldown, 10-minute sweep from `main.py`) and at most ONE line in the member's first-turn brief (`morning_items` -> `_build_morning_context` `pendant_items` -> `brief_first_turn.day_items`) - it NEVER speaks and adds no spoken path. `ZOE_OMI_HEALTH` (default ON; `0` = no warnings, numbers still stored). The erase cascade deletes the member's rows (`omi_recordings.forget_user`) and FAILS CLOSED: only a missing table is "nothing to erase"; any other failure raises `HealthEraseIncomplete` after the rest of the erase ran. `record_report` and the sweep run inside the member's `user_erase_gate` lock (generation snapshotted at the route, ownership re-checked inside; a stale or reassigned write is dropped with 409), so a racing heartbeat cannot recreate a forgotten member's row and a heartbeat and the sweep never both ring. The bell row is written BEFORE `warn_state` is saved, with an id derived from (pendant, kind, episode) and `ON CONFLICT DO NOTHING`: a crash between the two neither loses nor doubles the bell, and a failed bell insert saves nothing (the Pi retries the report). A failed live push is logged, not retried; a reassigned pendant starts the new owner from a clean `warn_state` AND a fresh overwrite baseline (`_rebaselined`: the old owner's overwrite total, last-overwrite time and counter are dropped). The owner check and the save (and the sweep's) run under `omi_devices.device_lock(device_id)`, the same lock `assign`/`unassign` hold, so a reassignment cannot land between them. With `ZOE_OMI_HEALTH=0` the read also returns no warnings and `status: warnings_off` (the numbers stay). Tests: `tests/test_omi_health.py`.

### ZD105 Struggle detector phase 1

- **Struggle detector (Phase 1 of the self-correction loop): `struggle_signals.py` (pure signals) + `struggle_detector.py` (runtime: notes, queue, worker, store, forget/delete) + `struggle_digest.py` (the read side: clusters, nightly line, morning line) + `routers/struggles.py`, migration `0050` (`struggle_events`); contract [docs/architecture/struggle-detector.md](../../docs/architecture/struggle-detector.md).** `ZOE_STRUGGLE_DETECT` = off | **shadow (default)** | on, per-call read (`off` runs no detector machinery - no queue, worker, notes or rows - the hooks only bump the `observed` / `dropped_off` counters); `ZOE_STRUGGLE_WINDOW_S` (45), `ZOE_STRUGGLE_RETENTION_DAYS` (90), `ZOE_STRUGGLE_QUEUE_MAX` (256). Rules that keep it safe: (1) OFF THE TURN PATH - the only in-turn work is O(1) deque appends (`note_route` at the end of `semantic_router.route`, `note_brain` in `brain_dispatch._log_lane`, `note_skybridge` after the Skybridge router gate); `observe` sits at the top of the EXISTING post-turn tasks (`routers/voice_tts._run_voice_memory_passes`, `routers/chat._persist_memory_candidates`), is a bounded `put_nowait`, and never raises (every failure is a counter in `stats()`); never add a hook that awaits on a turn. (2) Words only where the transcript keeps them: a member's own words in display form (lower case, NOT folded - a forget's name pattern must find them), PII-scrubbed on the RAW text (<= 160 chars), never for a guest / an off-the-record or distress turn / a forgotten entity / a pair across two identities; reports show example words only from the viewer's own rows. (3) Forget and delete FAIL CLOSED: `memory_forget_entity` -> `erase_entity`, `MemoryService.delete_user` -> `delete_user`; only a missing table is "nothing stored". (4) `shadow` changes nothing user-facing; `on` adds the one-line ack of a bare "that was wrong" (`fast_tiers._struggle_ack`, only when no tier answered) and the admin's morning-brief line. Harness / test panels and synthetic users are never recorded. Pinned by `tests/test_struggle_signals.py`, `tests/test_struggle_recall.py`, `tests/test_struggle_detector.py`, `tests/test_struggle_digest.py`, `tests/test_struggle_e2e.py`, `tests/test_migration_0050_struggle_events.py` (all `ci_safe`, with negative controls). VOICE-PATH files touched: `routers/voice_tts.py`, `fast_tiers.py`.

### ZD106 Struggle proposals phase 2

- **Struggle proposals (Phase 2 of the self-correction loop): `struggle_proposals.py` + migration `0057` (`struggle_proposals`, `struggle_proposal_events`) + the `/api/system/struggles/proposals` routes in `routers/struggles.py` + `scripts/maintenance/zoe-struggle-proposals.py` (the night window's `struggle_proposals` job and the operator CLI); contract [docs/architecture/struggle-detector.md](../../docs/architecture/struggle-detector.md) -> *Phase 2* (built) and *Phase 3* (design only).** `ZOE_STRUGGLE_PROPOSALS` = off | **shadow (default)** | on, per-call read (`off` = the job is a no-op; `on` adds the admin's morning-brief line); `ZOE_STRUGGLE_PROPOSAL_DAYS` (7), `ZOE_STRUGGLE_PROPOSAL_MIN_EPISODES` (3). Rules that keep it safe: (1) CODE groups, counts and thresholds (a cluster needs >= 3 separate episodes - one user's events within 10 min are one - on >= 2 user-days, mean confidence >= 0.6); the night model only rewords the COUNTS as one sentence (`facts_of` is the whole of what it sees; `valid_summary` rejects an invented number, markup or a URL and the template stands). (2) A proposal row holds counts, a text-free shape and evidence EVENT ids - never a household utterance; a `router_example`'s words are resolved at read time by `queued_router_examples` (the Phase 3 seam) from the member's own `struggle_events.summary`, the failed turn only, forget-ledger re-checked, a failing check drops the example. (3) A failed turn is labelled by what happened next: `struggle_detector._follow_up` records the fast domain that answered the revealing turn (`sig.resolved_route`), `struggle_proposals.classify` makes it a `router_example` (`label_source=followup`) only if that follow-up was not itself a struggle; no proof = a weaker `label_source=router` example the seam does not hand out by default. (4) Forget / delete cascade FIRST: `struggle_detector.erase_entity` / `delete_user` call `struggle_proposals.forget_events` / `forget_user` before the events go (fail closed, idempotent on retry); every read joins back to `struggle_events`. (5) NOTHING APPLIES ITSELF: the pass creates / updates / withdraws `proposed` rows only; `accept` records a queue marker (router_example) or a task stub (others), never a PR; only `mark_applied` (Phase 3, `accepted` rows) reaches `applied`. Pinned by `tests/test_struggle_proposals.py` (real SQLite + the real migrations; negative controls in its header), `tests/test_migration_0057_struggle_proposals.py` (both `ci_safe`), and the window's job in `tests/unit/test_night_window.py`. Migration `0057` chains onto `0056` (omi device health); the relay migration follows it as `0058`.

### ZD107 Open loop lifecycle

- **Open-loop lifecycle (flag-dark): `open_loop_lifecycle.py`.** `ZOE_LOOP_LIFECYCLE` (default OFF, per-call read; off = byte-identical). Four day-sim gaps, each in its owner: (1) `selector.ask_phrasing` — loop/moment raises ask ONE gentle question (the `follow_up_hint` quoted as the example when it is a question) and forbid the "I don't have any information" disclaimer; the flag is snapshotted on `Raise` at `prepare`; events keep the old body. (2) `brief_first_turn.mentioned` + `selector.mark_brief_surfaced` — at settle (reply text went out) the loops/moment whose rendered line IS in the `[Today]` brief are marked surfaced like a raise (count, cooldown, session, ONE shared stamp; an unranked item gets an already-expired cooling row); the morning context carries loop `id`s and `emotional_moment_ids`; lanes pass `session_id` to `brief_first_turn.prepare` POSITIONALLY; `_spacing`'s daily cap counts DISTINCT stamps (one brief = one delivery). (3) `resolve_for_supersede` — `MemoryService.review(edit)` (after the lock) and `memory_supersede` (turn + nightly) close loops resting on the retired fact (pure `retired_match`: an anchor the retirement removed, or for a cue-driven ending a shared anchor + topic containment; an enrichment edit closes nothing), expire their candidates, log `OPEN_LOOPS user= resolved_by_supersede=N source=`; never raises. (4) horizon — `selector.loop_relevance(decay=True)` 0.4 ≤7 d / 0.25 beyond instead of excluding, the extractor prompt gets `_OPEN_LOOPS_HORIZON` (worry/health → 1 day) and dedupes against loops resolved in the last 2 days, and `open_loop_quality.loop_anchors` adds `HEALTH_NOUNS` (named conditions only — anchors are cue words). Voice path: replay-gate before enabling. Pinned by `tests/test_open_loop_lifecycle.py`; record: `docs/knowledge/synthetic-users-and-proactive-recipients.md#open-loop-lifecycle-flag-dark`.
