# Panel relay R1 - the box side

Design: [panel-anywhere.md](../architecture/panel-anywhere.md) (sections 5, 6, 10 R1). The relay itself (frps, plugin, the411) is the F0 lab / `labs/relay/RUNBOOK-R1.md` (PR #2094). This page is
the other end: what the household's box does when a request arrives through the relay. **Everything is flag-dark and the LAN is byte-identical with the flags off** (measured: 68 of 68 LAN probes
reach the upstream with the same headers as `origin/main`, except that a client-sent `X-Zoe-Ingress` / `X-Zoe-Client-Cert-Fp` is now dropped, where it used to pass straight through).

## What is built

| Piece | Where | Rule |
|---|---|---|
| zoe-data ingress gate | `services/zoe-data/relay_ingress.py`, `auth.get_current_user`, `panel_principal.py`, `main.py` | `ZOE_RELAY_INGRESS` (default off) + `ZOE_RELAY_HOSTNAME` (`<hid>.zoe.internal`). A request is relayed only when the flag is on, the TCP peer is the zoe-ui nginx container itself (`ZOE_RELAY_TRUSTED_PEER`, ONE address - not the docker `172.16/12` that `ZOE_TRUSTED_PROXY_NETS` trusts for `X-Real-IP`, which is unchanged) and it carries `X-Zoe-Ingress: relay`. With the flag on, the marker from any other peer (a forgery, or a stale address after the container was recreated) is refused 403, never judged by the LAN rules; an unset peer trusts nobody. Relayed = never guest (no device token / kiosk credential for the certificate's panel = 401), no address, the panel principal only, a member only with a fresh sign-in at the panel, no home control without a member. |
| certificate binding | alembic `0059` (`panel_client_certs`), `routers/panel_relay.py` | the SHA-1 nginx forwards is bound to ONE panel; revoke = refused at once; a fingerprint never moves or un-revokes. |
| nginx relay listener | `services/zoe-ui/nginx.d/relay-listener.conf` (+ `ingress-lan.inc`, `ingress-headers.inc`, `lan-only.inc`), `nginx.conf` glob, `docker-compose.yml` `127.0.0.1:9443` | TLS 1.3, `ssl_verify_client on` against the household CA, PROXY protocol, headers set absolutely, no address, off unless `ssl/relay/listener.conf` exists. |
| box tooling | `scripts/setup/relay/{frpc_config,household_pki,enable_relay_listener}.py` | the frpc config + its safety check (never `127.0.0.1:8000`), the household CA / leaf / panel certificate, the guarded enable. |

## Measured (2026-10-17, Jetson, nginx:alpine, throwaway PKI)

- `tests/unit/test_relay_nginx_listener.py`, `test_relay_frpc_config.py`, `services/zoe-data/tests/test_relay_ingress.py`: green in the `ci_safe` lanes. Every negative control was run by breaking the code under test:
  24 zoe-data mutations (trust any peer, ignore the flag, keep the address, drop the credential / mismatch / freshness / revocation / inactive-panel checks, skip the websocket gate, un-install the middleware, drop the origin, ...)
  all went red, and 9 nginx mutations (a location without the ingress headers, an empty marker, optional client certificate + no 444, forwarded X-Forwarded-For / X-Real-IP, `/ha/` reachable, TLS 1.2 allowed, LAN blocks forwarding the marker, fingerprint taken from the client header) all went red in the static file and in the live file.
  One live mutation (`ssl_verify_client optional`) survives alone BY DESIGN: the `$ssl_client_verify != SUCCESS` -> 444 backstop catches it; removing both is red. A review round (read-only adversarial agent; codex was over its quota and the one lean pi pass hit its $1.50 cap before a verdict, so the cross-VENDOR review is still outstanding) found and this PR then fixed: member sessions on the websocket handlers (no freshness check), the voice-session leg of the freshness rule (the panel could mint it), zoe-auth routes reachable with a revoked certificate (now `auth_request`-gated), open sockets outliving a revocation, a non-atomic leaf renewal, the enable script checking only one env file. 5 more zoe-data mutations and 2 nginx mutations cover those; all red.
- `services/zoe-data/tests/test_relay_nginx_live.py` (opt-in, `ZOE_RELAY_NGINX_TEST=1`, docker): 13 cells against a real nginx container in front of the real zoe-data auth code: T5 header overwrite (relay) / drop (LAN) / no address, no certificate and a foreign-CA certificate never reach zoe-data (hit counter), TLS 1.2 and a missing PROXY header refused, T10 (credential-less 401, `POST /api/ha/control` refused, the LAN request behaves per #2089), T11, the fingerprint mismatch and its revocation, 404 for Music Assistant / HA UI / Multica / LiveKit, the websocket upgrade through the same gate, HTTP/2 + client certificate.
- Not run: the full F0 lab (frps/frpc hop). `labs/relay` (#2094) is on main; the lab runner needs `MemAvailable >= 1500 MB` and the daytime Jetson sat at ~1.3-1.5 GB. Plan once #2094 and this PR have landed: replace the lab listener stub's fake upstream with the stack from `test_relay_nginx_live.py` and add cells T5 / T10 / T11 to `run_lab.py`.

## Owner steps, in order (nothing here has been run on the live box)

1. Merge #2089 (the home-control / device-token fix) first, then this PR. Alembic `0059`'s `down_revision` is `"0060"` (#2146, phone app; re-pointed 2026-10-19). If #2141's `0058` lands first, re-chain whichever of the two lands second onto the other, or the single-head test in `test_relay_ingress.py` goes red - expected, do not edit it away. Run the migration (`alembic upgrade head`, as for any migration).
2. In the zoe-data env: `ZOE_RELAY_INGRESS=1`, `ZOE_RELAY_HOSTNAME=<hid>.zoe.internal`, `ZOE_RELAY_TRUSTED_PEER=<the zoe-ui container's address>` (`docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' zoe-ui`; it changes when the container is recreated - re-check after every `docker compose up` that recreates zoe-ui; `enable_relay_listener.py` refuses a stale or non-single-address value), `ZOE_PANEL_KIOSK_CREDENTIAL=1` (the kiosk browser's only credential over the relay). Restart zoe-data and poll `/health`. (`/api/panels/{id}/client-certs` now answers.)
3. `python3 scripts/setup/relay/household_pki.py init-ca` then `issue-leaf --hid <hid>`; back up `~/.zoe/relay-ca/ca.key` offline. On the panel generate a key + CSR (`openssl ecparam ...; openssl req -new ...`); `household_pki.py sign-csr --csr panel.csr --panel-id <panel_id>` prints the fingerprint.
4. Bind it: `PUT /api/panels/<panel_id>/client-certs/<fingerprint>` with an admin session. Copy `panel.pem` and `ssl/relay/ca.pem` to the panel.
5. `python3 scripts/setup/relay/enable_relay_listener.py` (refuses unless step 2 and 3 are done), run the printed `nginx -t` pre-flight, `docker compose up -d --no-deps zoe-ui && docker restart zoe-ui`. Check `docker exec zoe-ui ls /etc/nginx/ssl/relay` and `ss -ltn | grep 9443` (loopback only).
6. Install frpc v0.71.0 (arm64 tarball, verify the published sha256), render its config with `scripts/setup/relay/frpc_config.py` `render()`, and run `python3 scripts/setup/relay/frpc_config.py frpc.toml <hid> <relay-ip>` BEFORE starting it (non-zero = do not start). The systemd unit is not shipped yet.
7. Panel side (see pending): switch the hosts mapping, install the CA root and client certificate, `VERIFY_SSL=true` with the CA pin, X-Device-Token as before.
8. Replay gate and the L6 time-to-first-audio comparison before calling R1 live (design section 10).

**Rollback:** `enable_relay_listener.py --disable` + `docker restart zoe-ui` removes the listener FIRST; only then unset `ZOE_RELAY_INGRESS` and restart zoe-data (the header becomes inert; the admin routes 404); revoke a single panel with `DELETE /api/panels/<panel_id>/client-certs/<fingerprint>` (HTTP at once, open websockets within 15 s, zoe-auth routes at once via the gate). Order matters when turning ON: flag first, then the listener. A revoked certificate still completes the TLS handshake (nginx has no CRL here); everything behind it answers 401.

## Still pending

- **C3** (design section 10): kiosk Chromium presents its client certificate with no prompt (`AutoSelectCertificateForUrls` policy for `https://<hid>.zoe.internal`); needs headless/real Chromium on the panel and the memory for it. R1 does not go live without it; the fallback is a loopback forwarder in the kiosk gate.
- **Panel side**: the voice daemon (`scripts/setup/zoe_voice_daemon.py`: `requests` with `verify=<household CA>` and `cert=(client cert, key)`, the hosts mapping, `VERIFY_SSL=false` retired) and the kiosk gate are NOT changed here (the daemon is a voice-path file; replay-gated). `curl --cacert` is not a pin on Debian (lab finding 7).
- **Voice lanes over the relay (R1 must not go live before this)**: `voice_tts.py`'s HTTP lanes take `identified_user_id`, a voice-claim score and even `panel_id` from the device's OWN payload, so a stolen panel's certificate + device token can run member voice turns (memory, personal data, home control - the resolver gets a bare user id) from anywhere. On the LAN that needs physical presence; over the relay it does not. The fix is a voice-path change (replay-gated): for a relayed request force `panel_id` to the proven panel and accept a member only from a server-verified claim or the fresh PIN session. Also `livekit-token` computes `livekit_available` from addresses (nginx answers "unavailable" for the relay instead). Open-problems ledger 2026-10-17.
- **Listener on + flag off = LAN rules** (owner spec, confirmed by the coordinator: with the flag off the relay header is ignored; the 503 option below is recorded, not adopted). Nothing then checks the certificate binding, a relayed request looks like a private-address client, and `ZOE_UNAUTHENTICATED_ROLE` / `ZOE_HA_CONTROL_SCOPE=open` / the `lan` list scope apply to it. The enable script refuses without the flag and the rollback below removes the listener FIRST; the alternative the review suggested is to answer 503 to a marker that arrives while the flag is off (the LAN blocks always drop the marker, so only the listener can send it) - a one-line change in `relay_ingress.is_relay` that contradicts the "ignored" spec, so it is left for the owner to choose.
- Host port `127.0.0.1:9443` is published unconditionally by compose; it was free on this box on 2026-10-17 (`ss -ltn`), but if anything else holds it the zoe-ui container will not start - check before the deploy that carries this PR.
- **`/ws/push?panel_id=`** IS narrowed now: a relayed socket may only join the channel of the panel it was proven to be (the RESOLVED id, so an alias of its own panel works; an alias that resolves elsewhere is refused). Proven against the real `main.app` handlers by `test_relay_ws_live.py`.
- The full lab cells T5 / T10 / T11 inside `labs/relay` (#2094 is on main now; needs MemAvailable >= 1500 MB).
- **CI does not run the opt-in suites** (`test_relay_nginx_live.py` needs docker, `test_relay_ws_live.py` needs the full `main` dependency set). Run both before `ZOE_RELAY_INGRESS` is ever enabled: `ZOE_RELAY_NGINX_TEST=1 flock -x -w 3600 /tmp/zoe-test-lane.lock nice -n 10 pytest services/zoe-data/tests/test_relay_nginx_live.py services/zoe-data/tests/test_relay_ws_live.py`.
- `test_a_relayed_voice_command_ignores_a_forged_panel_id_and_identified_user_id` is SKIPPED on purpose: the voice-path PR `fix/voice-path-identity` un-skips and implements it.
