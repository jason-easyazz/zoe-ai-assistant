### Wire the relationship graph into recall (GBrain lesson) — ⚠️ boost merged (#1199); live-state UNVERIFIED
- **Core:** feed Zoe's existing `people_relate` graph into the memory recall ranking, so asking about one person also surfaces facts about the people/things connected to them. Source: Jason shared [github.com/garrytan/gbrain](https://github.com/garrytan/gbrain) 2026-07-09.
- **Why it's the one gap:** GBrain benchmarks **+31.4 P@5 from a knowledge graph over vector-only RAG.** Audit (2026-07-09) found Zoe already has the *rest* of GBrain's playbook, mostly LIVE — multi-signal hybrid recall (`memory_service._semantic_search._blend`: vector + keyword/BM25 + salience/access_count + confidence + time-decay + recency, `ZOE_HYBRID_RETRIEVAL_ENABLED=1`), an idle enrichment "dream cycle" (`MEMORY_DIGEST_ENABLED`), and recall injection (`ZOE_SEAM_RECALL_INJECT`) — and it's local/private where GBrain defaults to hosted embeddings. The signal GBrain adds — a graph-adjacency boost inside `_semantic_search._blend` — was **built and merged in #1199** (2026-07-09); `relationship_graph.neighbors()` + `GET /people/{id}/graph` exist (ADR #1022). What remains is not *building* it but **confirming and measuring its enablement** — see Status/Next, which are less certain than an earlier revision of this entry claimed.
- **Status (2026-07-29) — merged, enablement UNVERIFIED & contested (do not treat as confirmed-live):** the graph-adjacency boost to `_blend` is **built and merged** (PR #1199, 2026-07-09 — pure Postgres recursive-CTE, no new models, ~zero RAM). Its *enablement* is where the uncertainty is: (a) both `ZOE_RELATIONSHIP_GRAPH_ENABLED` and `ZOE_GRAPH_RECALL_BOOST` appear in `services/zoe-data/.env` (enable-runbook Enable log: “2026-07-22, verified in live `.env`”), **but** flags are read from `os.environ` lazily and only take effect after a **service restart** ([`relationship-memory-flag-enable.md`](knowledge/relationship-memory-flag-enable.md):30-32) — so `.env` presence ≠ running-process active, and the running state is **unconfirmed here** (health endpoints unreachable from this review); (b) two authoritative docs **conflict**: the enable runbook records it live 07-22, while [`gbrain-memory-graph-recall.md`](architecture/gbrain-memory-graph-recall.md):153-155 requires enabling the boost **“only after W0 clears the replay gate. Never before.”** — the gate did not pass until #1572 (07-27), so a real 07-22 enable **preceded its required verification by five days (an acceptance gap, not a non-applicable gate)**; (c) migration 0015 is a hard precondition, but without it the graph queries do **not** error — they catch and return `[]` (`relationship_graph.py:174-178`, `memory_service.py:1242-1244`), i.e. **silent no-boost**, so a fresh deploy cannot rely on an error to reveal missing schema.
- **Next:** (1) **verify running state** — confirm both flags are actually live in the running `zoe-data` process (or run a functional recall probe), not merely present in `.env`; (2) **resolve the acceptance gap** — reconcile the two conflicting docs and confirm the replay-gate / functional verification the gbrain doc mandates was actually run post-enable (or record a deliberate decision that waived it); (3) **measure lift on real data** — the #1199 eval (`test_graph_recall_boost_eval.py`) is a **synthetic unit proof** (canned Chroma distances, injected graph depths, 2 multi-hop queries, P@5 0.0→0.2 — validates the ranking *mechanic* only) and is **not** comparable to GBrain's +31 P@5 benchmark; measure against a held-out Zoe corpus. Any rollback/re-enable names **both** flags (flag-off only, never schema-downgrade). **Reject from GBrain:** hosted embeddings (breaks the local/private rock) and a resident local reranker like Qwen3-Reranker (breaks the RAM budget — see the 2026-07-08 25 GB-swap incident).

### Forget tombstones — a forget blocks in-flight/late memory writes for that name — ✅ IMPLEMENTED (#1304 + #1307, 2026-07-13)
- **Core:** memory extraction runs seconds behind the conversation, so a fact mentioned just before "forget everything about X" can finish saving just AFTER the forget — one straggler row resurrects the forgotten person (seen live 2026-07-13 during the F14 verification: a digest row "User has a friend named Delia" landed post-forget; a repeat forget swept it). Idea: `memory_forget_entity` writes a short-lived per-user tombstone for the name (e.g. a row in Postgres or an in-process TTL map, ~2–5 min), and every writer's ingest path (memory_extractor / digest / person_extractor / expert_dispatch — they already share `reconcile_for_ingest`) checks it and drops name-anchored candidates for tombstoned entities.
- **Shipped:** in-process 5-min TTL map (`memory_tombstones.py` — in-process is *correct*, not just cheap: zoe-data is one process, so the in-flight writes a tombstone must block die with it on restart); the drop lives at the `MemoryService.ingest` chokepoint so no writer can miss it; explicit teach HANDLERS (memory_store / store_fact) bypass at ingest and clear only after their store succeeds, while an explicit "remember (that) X …" UTTERANCE clears up front in the extraction hooks — deliberately pre-mining, because the mined ingests are otherwise shadow-dropped (shared `is_explicit_teach`, structural verb detection). Live-proven: seed → immediate forget → zero stragglers; re-teach within the TTL stores. Source: Jason, 2026-07-13 (from the live forget test, PR #1295's known race).
